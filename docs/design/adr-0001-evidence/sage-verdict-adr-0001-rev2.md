## 2. ADR-0002
- Fix 1 (locks before units): REJECT as specified. Exclusivity is already checked before units are granted (scheduler.rs:254-266, 306-307, 434-436; grant at 502-523; service.rs:1199, 2746-2768). lockWaitMs counts Cargo "Blocking waiting for file lock on" lines (service.rs:6330-6341, job.rs:412-445); RK_LOCK_WAIT_TIMEOUT is a Cargo file-lock timeout (service.rs:6318-6320). In 72 h (6,911 receipts, 948 with waits) all 12 longest waits are waiting-on-package-cache-lock. Named holders are candidates only (service.rs:2165-2169): cargo update -p rightkit-app-settings, MailRight's stalled cargo test --lib webimg:: (6,667 s), a cargo run --example. Real fix 1: a root blocked on a Cargo cache lock must not hold units: package cache becomes a scheduler class (wait in the queue) or the root returns units while waiting.
- Fix 2 (QA feature set, own warm generation): OPEN. PostRight root b3ceaed6 (cargo test -p postright-engine --features test-mode, 8,268,709 ms) started with unitsAtStart 0, 0/251 fresh, lockWaitMs 150 s: an empty target, not eviction; Cargo keeps feature-set variants side by side. Why it was empty (generation rotation, GC at 310 GB vs the 150 GB cap, a spare slot) and how much was compiling are not proven.
- Fix 3 (--locked --offline after one fetch): OPEN. An offline build still takes the package-cache lock; cargo 1.98 lock modes per command are not established.
- Fix 4 (600 s run cap): APPROVE in shape with §4. Default-on would kill GenRight's in-broker e2e runs until its migration; rollout is Adrian's call.
- The ADR-0002 file must state: the corrected problem with receipt ids; cargo 1.98 package-cache lock modes per command and the chosen fix (scheduler class / return units / CARGO_HOME per class), acceptance "no root holds units in waiting-on-*-lock longer than X s over 72 h"; the mechanism that emptied b3ceaed6's target (else W1-B stays OPEN); cap semantics (commands covered; start detection via stderr Finished and JSON build-finished; fail-closed when neither appears, e.g. -q; applies with the watchdog off; default and per-repo rollout; Windows tree kill alongside #134); a structured contract for the build record's broker request id and attested exit (today only a stderr line, rustright-cli/src/cli.rs:350); whether test execution ever gets a RUN lane; one integration owner for rustright main.

## 5. Adrian's four questions
- Necessary? The build/run split and the persistent engine: yes, proven. cargo test is BUILD (command_policy.rs:330-331) and holds units through the run; 40f7ad68 held them 3,344 s after a 2.26 s compile; the sidecar alone took PostRight from 4,323 s to 304 s (ca1839f). Truthful evidence: yes; today orphans are silently killed (scenario.rs:434-435; PostRight opts in at scenarios.rs:2571), skips pass the wrapper (scenarios.rs:2579), release admission only warns (release-qa-audit.mjs:25-32), the Node gate always exits 0 (gate.ts:137). The pool is not shown necessary for 2–5 min on PostRight, only for sub-1-min warm or the other serial apps. ADR-0002 fix 4 necessary; fixes 1–3 not yet shown necessary as proposed.
- Why? A cold engine per step (postright engine main.rs:165-175 takes the store lock and opens the store on every call); the serial design (suite.rs:1-2, 417); runtime held inside a compile permit; Cargo package-cache waits counted as run time while holding units (service.rs:6330-6341). The cap exists because the stall watchdog does not fire while a test spins CPU.
- All apps? Split, truthful evidence and admission: all nine (CutRight running cargo test outside the broker is itself a violation). Persistent engine: PostRight and GenRight (one-shot engine per step); others unknown. Package-cache contention: every repo sharing the single cargo-home (GenRight, CutRight, ViewRight, HeardRight, ScrapeRight, MailRight, CodeRight in receipts). Cap: every repo; harms GenRight until it migrates.
- Missed how? The 10-21 standard left execution placement advisory and its gate cannot fail (gate.ts:137); serial is the documented design (suite.rs:1-2); cargo test as BUILD was inherited from the Node broker (command_policy.rs:330) with #135 open; PostRight's single test (scenarios.rs:2554) hid per-scenario time; lockWaitMs was in every receipt (service.rs:5371) but Cargo's Finished time includes those waits, so they read as compile time; the D2 record attributed them to broker exclusivity without reading cargo_lock_signal (service.rs:6330).
- Which app? PostRight e2e: run 40f7ad68 / request 096d6843, 1,531 cold steps, p50 1.38 s. GenRight: 178 serial journeys, 2,987 s. Lock waits: MailRight cargo test --lib webimg:: (stalled at 6,667 s, 2,873 s waiting); GenRight check 3,821 / 3,694; ViewRight check 6,234 / 3,119; CutRight, HeardRight, ScrapeRight checks (RK_LOCK_WAIT_TIMEOUT); candidate holders cargo update -p rightkit-app-settings jobs and long test runs. Cold empty targets: PostRight b3ceaed6 (8,269 s), HeardRight a2759d16 (8,864 s, 573/676 not fresh).
