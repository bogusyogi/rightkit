# Gate and broker reset: target spec, interface, delete list

Draft for Adrian, 2026-11-07. Written by Legion from both contracts and both codebases as they stand (rightkit `67515ffb5`, rustright `0bbd1e3`). Nothing here is decided until Adrian says so. It replaces no contract yet.

## 1. The requirement

Adrian's three lines, unchanged since 2026-10-28 (GATE-CONTRACT §1):

> rightkit releases from mac, dell or linux / on dell and mac, via broker / on linux no broker / but in all cases single point of entry with class a first, local compile, qualification on CI and auto publish from git
>
> private repo apps built on mac, dell or linux / on dell and mac, via broker / on linux no broker / but in all cases single point of entry with class a first, local compile, qualification held for dell or mac
>
> public repo apps built on mac, dell or linux / on dell and mac, via broker / on linux no broker / but in all cases single point of entry with class A first, local compile, qualification on CI. signed installers available

Everything below exists to make those three lines true and nothing else.

## 2. Target spec (one page)

**Entry.** `rightkit-gate --to <check|compile|dev|test|package|qualify|release> --commit <sha> [--unit <id> | --units-file <f> | --changed]`. One command on every host. Nothing else builds.

**Snapshot.** The gate syncs the commit into `<data root>/snapshots/<repo-key>` by content, keeps timestamps of unchanged files, and verifies the tree id once after the sync. The checkout is never read by a build. One snapshot, one target directory, one warm cache per repository per host.

**Class A.** Runs first, in the gate's resident process, outside the broker, keyed per row on the inputs that decide the row. Red Class A starts no compile. The 42 non-negotiables of GC-A27 stay, as test names.

**Class B.** The gate plans one invocation per workspace, stage and feature round (`-p a -p b --keep-going`, every `--target` in one call). On the Mac and the Dell it runs each through `rustright cargo`. On Linux it runs cargo directly with `CARGO_TARGET_DIR` pinned to the workspace's one target.

**Broker.** Owns the machine. Decides how many cargo processes run and in what order. One cargo process per app at a time (Adrian, 2026-11-07: "One per app"; section 8), duplicates refused, different commands queued. Pins the target directory, the release profile and the host triple. Contains the job's process tree; no filesystem write confinement: the snapshot tree is verified once more after the job, and a job that changed it fails with its own refusal code (Adrian, 2026-11-08; section 8). Priority tiers reorder waiting jobs and never cancel a running one (Adrian, 2026-11-08; section 8). Runs `cargo test` with `--no-run`; the gate runs the binaries. Returns an exit code, the output directory and a receipt file. That is its whole job. GAP (fresh review, 2026-11-09): the Mac's live config sets `coalesceIdenticalRequests: true`, a `development` default profile and three allowed profiles, against "duplicates refused" and "release profile only" here; which gives way is Adrian's decision, not yet taken.

**Cutover.** No overlapping brokers, no handover, no job replay (Adrian, 2026-11-07: "If live broker handover is complex. Let’s kill it. I would rather have a working implementation where I have to kill the queue and restart then be stuck trying to do seamless handoff"). Installing a broker: pause admission, cancel every queued job and stop every running job tree the broker owns, record each as cancelled in its receipt, prove the old processes are gone, start the one new broker on the same warm target and cache. A job that completes before its cancellation lands keeps its completed outcome, with its durable receipt and the complete process-tree proof; the installer arbitrates on the resulting state, never on the phase it saw earlier (rustright#236). Cancelled work requires explicit resubmission; the gate does not automatically resume it. A rollback is the same procedure with the previous build. Process containment and clear failures stay. Implementation in the installed and source brokers: pending, not delivered.

**Trust.** The gate trusts the broker's receipt. The gate owns Class A and its completeness: it writes the verdict only when the whole planned set for the workspace at the commit passed. The broker admits a compile on the section 3 checks: the working directory lies under `<data root>/snapshots/`, the snapshot is locked for the commit by a live holder, and the request names a Class A verdict the gate wrote for the same commit, tree, repository and workspace with status pass (Adrian, 2026-11-04: "class a outside broker, needs completion before admitting to broker. enforced by broker. class a enforved by gate"; GATE-CONTRACT line 36, broker item 24). Neither re-hashes the other's admission inputs (no declared-input digests, no tree hashing for admission); the broker's one post-job tree check (today `verify_snapshot`, which leaves `check_admission.rs` for `finish_impl.rs` when section 5 deletes that module) stays, and the gate verifies no signature: a same-user agent can read any key the gate holds, so a signature proves nothing against the only adversary there is on the host. The guard against an agent bypassing the gate is the pre-tool hook on the agent host and the publish step's receipt check. The broker still signs its receipt (`attestation.rs`, key readable only by the broker's user on that host): the gate does not verify it locally, CI's publication admission does (`qualification-verify.mjs`, enrolled pins in `ci/rk-pipeline.json`), because an agent that is not on a managed host cannot read the key, and that is the one adversary a signature stops. One lease stays, in its smallest form: the gate takes the snapshot lock for the commit before the sync and holds it through every queued and running job and its own test execution, releasing it only after the batch, so a second gate process cannot refresh the snapshot under a queued compile; the broker refuses a request whose snapshot is not locked for its commit, and a stale lock is reclaimed only once the broker proves that all prior use of that snapshot ended (section 3).

**Tests.** Every gate test that touches the broker runs against the installed broker on the live data root with a real small commit, never a mock and never a test broker (Adrian, 2026-11-05; decided 2026-11-08, rightkit#1536). The broker's own tests keep the harness its parity crate already has, which starts the real broker in a temp root under `/Volumes/D/scratch` for seconds, so a broker bug is found before the cutover. One installed probe command runs after every cutover: wiring, service, OS process checks, warm repeat, cancellation, concurrency, owner death. No test needs the second machine.

**Publication.** Unchanged: RightKit through CI from git; private apps through local qualification then R2; public apps through CI with signed installers.

## 3. The interface (the one seam; agreed fab and astra, 2026-11-09, after both adversarial reviews; rustright#235; pending Adrian's word, as everything in this plan)

One request, one reply, the existing CLI. The gate spawns `rustright cargo <argv>` (or `rustright run <adapter-id> -- <argv>` for an adapter) with the working directory inside the snapshot and two environment variables. No carrier file, no nonce, no grant, no lease handle, no capability query, no signature the gate verifies. The client builds whatever framing the broker speaks; the gate never sees it.

**Request.**

| Field | Carried as | Value |
|---|---|---|
| `cwd` | the process working directory | a workspace directory under `<data root>/snapshots/<repo-key>`; the broker maps it to the app's one target through `${snapshot}.state.json` (`rightkit.snapshot-state/1`: `repo`, `repoKey`, `commit`, `tree`), which the gate already writes and keeps |
| `argv` | the argv | the cargo (or tool) argv as the gate planned it |
| `env` | the process environment | the environment the gate constructed; the client forwards the managed Rust subset it documents, and the receipt records which variables reached cargo, as audit evidence. Row cache keys are not derived from it: a key uses the canonical compilation-relevant inputs known before the invocation (features, toolchain, compiler and linker flags, Cargo configuration, the row's command and files) and excludes incidental machine paths, transport variables and scheduling knobs (rightkit#1540) |
| `gateCommit` | `RUSTRIGHT_GATE_COMMIT` | the full sha |
| `classA` | `RUSTRIGHT_CLASS_A` | absolute path of the Class A verdict file for this commit and workspace |

**Class A verdict** (`rightkit.class-a-verdict/1`, written by the gate atomically, only after the whole planned Class A set for that workspace and scope at that commit passed, cache hits counting as passes): `{ schema, commit, tree, repoKey, workspace, scope, status: "pass", scans: [{ id, status: "pass" }] }`. `workspace` is the normalized snapshot-relative workspace path (`"."` for the root). The verdict means every applicable Class A row for that workspace completed; no partial-unit verdict qualifies another scope: the verdict records the scope its class A covered (`scope`: `"full"`, or the sorted `--scope` directories; the broker ignores this field, the gate reads it) and its file name carries that scope; a class B run reads a verdict whose scope covers its own (the same directories, a superset of them, or full), never another unit's (gate-seam.mjs `verdictForRun`, `CLASS_A_VERDICT`). The broker checks the schema, the bindings (`commit`, `tree` and `repoKey` against the snapshot state, `workspace` against `cwd`), `status`, and that `scans` is non-empty with unique passing ids; the gate owns the expected scan set and its completeness (writer regression: an incomplete or red plan cannot publish a pass). The broker does not re-plan Class A and keeps no per-unit grant ledger. Trust boundary: these fields bind the verdict to the inputs; they do not authenticate a same-user file, and nothing here claims to (section 2, Trust). Class A is mandatory: a compile request with neither variable, one variable, a missing file, a red verdict or a wrong binding is refused with its own code. Non-compiling observations and version probes are exempt.

**Snapshot lock** (`${snapshot}.lock`): `{ pid, identity, commit, token }`. `identity` is the process-birth token in the exact format `rustright-process` documents (`crates/rustright-process/src/identity.rs:91-121`), literal prefixes included: `darwin:<pid>:<lstart>` (`LC_ALL=C LANG=C ps` lstart, trimmed), `linux:<pid>:<starttime>` (field 22 of `/proc/<pid>/stat`), `win32:<pid>:<Unix ms>` (process creation time); `token` names this hold. The gate takes the lock before the sync and holds it through every queued and running job and its own test execution; the broker validates it at submission and again immediately before spawn, and cancels the holder's jobs when the holder dies. Release: the gate releases its own lock at the end of the run only on positive evidence that every seam row settled: a parsed result line with a durable receipt read (the job reached its terminal state) or an explicit before-execution refusal, a cache hit, or a lookup that submitted nothing; a missing or malformed line, a missing receipt, a killed client or a spawn error is not settled, and the gate leaves the lock, and the next run reclaims it through the stale-owner proof below once the holder is gone. SNAPSHOT_STATUS is stale-owner proof only and is not asked for a live holder. A stale lock (dead pid) is reclaimed only after the broker proves that all prior use of the snapshot ended: no queued, admitting, running or FINALIZING job, no unreaped process tree, no persisted writer ownership. A broker that cannot be reached, or a proof that is inconclusive, means no reclaim. No per-job handles.

**Reply.** Exactly one line on stderr, `rustright-result <json>`, for every outcome including refusals and client errors; the gate parses that line and nothing else:

| Field | Value |
|---|---|
| `requestId` | correlation; null when nothing was admitted |
| `exit`, `signal` | the executed command's actual result (a cargo failure is its own non-zero exit, not a refusal); `signal` is null, or the signal as the broker reports it (a number) or as node names it (a string); a client or admission failure, where nothing was executed, is `exit: 125`, `signal: null` |
| `outputDir` | the pinned target directory, absolute; null when nothing ran |
| `receipt` | absolute path of the durable receipt the broker wrote; null when none; a broker-recorded refusal may carry one |
| `receiptPersisted` | true only when `receipt` is durable; the gate requires it on success |
| `code`, `message` | on a refusal or client error: a stable code (`<2-3 upper-case letters>_<NAME>`, `RK_` today) from the documented refusal classes and one line of text; absent when the command executed, whatever its exit. GAP: the candidate answers every reset refusal with one code, `RK_GATE_ADMISSION`, and the class in `message`; distinct codes per class are owed |

**Receipt** (JSON, read by the gate directly): the request as admitted, the transformations applied (`--target-dir`, `--profile release`, `--no-run`, `--keep-going`), timings, `testExecutables` for a test compile (the gate runs them; nothing is verified locally against a signature), the diagnostics path, the environment variables forwarded, and `gate { commit, tree, snapshot, classA, snapshotUnchanged }`. A job that changed the snapshot tree fails `RK_SNAPSHOT_CHANGED`. GAP: the receipt does not yet name the admitted `cwd` and `argv` in a form the gate compares with its row; once it does, a receipt for another command is `RECEIPT_MISMATCH`. The gate reads the receipt's postconditions before the exit code: a broker postcondition failure (`snapshotUnchanged: false`, a missing durable receipt) fails the row even when the child exited 0; an ordinary child failure keeps its actual exit and signal. The receipt is signed by the broker for CI's publication admission (`qualification-verify.mjs`, enrolled pins in `ci/rk-pipeline.json`), which migrates to this receipt shape; the gate does not verify the signature.

**Refusal classes** (each a stable code, no text scraping): cwd outside the snapshots root; snapshot not locked for `gateCommit`, or the lock's holder dead; Class A absent, incomplete, red or wrongly bound; the snapshot state missing or not matching `gateCommit`; a second identical command for the workspace (`RK_APP_BUILD_IN_PROGRESS`); a path-valued option leaving the snapshot or the output directory; `--target-dir`, a profile other than release, `--config`, `-Z`; `cargo test --doc`, `nextest`; recovery pending after a restart. The list is the documented interface classes; a new code enters `BUILD.md` with its test (section 6).

**Removed from the interface:** `callingGate`, `snapshot{path, expectedTree}`, `declaredInputs`, `ownership{handle}`, `primaryCwd`, the snapshot carrier and its sha256 descriptor, the attest nonce, stage grants and their ledgers, `SNAPSHOT_LEASE_STATUS`, `GRANT_RECEIPTS`, `QUALIFY`, `CONSUME_PREPARE` and `CONSUME_COMMIT`, signed `snapshotEvidence`, `stageEvidence` and `resultEvidence`, `freshness` cause evidence, `failureClass`, `nestedChildren`, broker capabilities for adapters, live handover, restart replay, priority preemption, write confinement (Seatbelt; rustright#234, required scope). The broker digest pin stays where CI's publication admission reads it (`ci/rk-pipeline.json`).

**Adapters** (pnpm, node, xcodebuild, gradle, cmake, QA) go through the broker as the same request with the tool's argv in place of cargo's, carrying the same two variables and returning the same result line and receipt. Their runs invoke cargo inside (a Tauri, Xcode or Gradle build step), so the `rustright cargo` shim on the child's PATH submits each nested cargo as a NESTED job under the parent's admission, with its target a fixed subdirectory of the app's one target (`nested_target`, as today); the nested job inherits the parent's binding. No capability table, no adapter grammar, no signed `nestedChildren` evidence in the gate. A nested cargo reached by absolute path bypasses the shim: a listed gap, not silently accepted. On Linux (no broker) the gate runs cargo and the adapters directly with the same pinned environment and `CARGO_TARGET_DIR` pinned to the app's one target.

**Test rows.** `cargo test` compiles once per crate and configuration with `--no-run`; the gate runs the listed executables, and a serial row (`--test-threads=1`) reuses the plain row's executables instead of compiling again (rightkit#1539; the duplicate refusal above makes a second compile a failure, so the planner never plans one).

**Class A reads** (`cargo metadata`, `cargo tree` for the feature partition, `cargo fetch`, deny, audit, `fmt --check`) never reach the broker (GC-A11): the gate runs the host's real cargo directly in the snapshot. Nothing compiles, so no scratch target is created; a read that needs `CARGO_TARGET_DIR` is pointed at the app's existing pinned warm target.

## 6. The contracts

Both contracts are replaced by one file, `rightkit/docs/BUILD.md`, of at most three pages:

1. The three-line requirement.
2. The interface of section 3, verbatim.
3. One list of invariants, each with the test name or refusal code that enforces it. An invariant with neither is not written.
4. A decision log: date, one line, the commit. No quotes, no relays, no history of what was superseded.

Rule for the file from then on: a new sentence enters only with its test name or refusal code in the same commit, or an explicit GAP marker that names what is not yet enforced; an obligation without a test is listed, never deleted. A check that exists today goes only in the commit where its replacement's test passes; a GAP marker covers obligations that have no implementation yet and never licenses removing one that has. The GC-A27 table survives as the test list in `packages/release/gate.test.mjs` and nowhere else.

## 7. Order of work

Each step is one agent, one repository. A step's tests name the broker they run against: the broker's parity harness (a real broker in a temp root under `/Volumes/D/scratch`) before a cutover; the gate's pure writer and parser checks (verdict file, lock body, result-line parsing, receipt reading) before a cutover with no broker at all; every gate-to-broker integration test against the installed broker after the cutover of step 4. The Mac and the Dell are delivered independently: each host runs steps 2 to 4 and 8 on its own, and neither waits on the other (AGENTS.md: one machine never blocks the other). Every compile, parity run, install and cutover is Adrian's approval, asked with the Class A output on the exact commit.

1. **The inner loop, decided (rightkit#1536).** Gate tests: the installed broker on the live data root, a real small commit. Broker tests: the parity crate's existing harness in a temp root. After every cutover: the one installed probe command. Adrian, 2026-11-08: "Choose what you think is better shape"; the split was chosen because with handover retired a broker build reaches the live root only by cutover, and both real broker bugs of 2026-11-05/07 were found after install. No `--lab` flag is added to the broker.
2. **Broker: the section 3 seam, proven on the harness (rustright#235).** `gateCommit` and `classA` admission with every binding, the snapshot lock checked at submission and before spawn, the result line for every outcome, the receipt `gate` object, `testExecutables` from a real test compile, owner-loss cancellation, cancel/restart cutover with the completion race fixed (rustright#236). The intermediate candidate may keep the legacy carried path for the installed gate, labelled with its exact removal point (step 6); the reset is not accepted while a compile with no verdict is admitted anywhere. Candidate 9617baa (after d49f270 and 809e057) is unbuilt: compile and parity need approval.
3. **Gate: write the verdict, take the lock, send the request, read the reply.** Against section 3 as written: the Class A verdict writer (atomic, whole planned set, writer regression), the lock body and lifetime, one spawn of `rustright cargo` from the snapshot with both variables, one `rustright-result` line parsed, the receipt read, test executables taken from it, the serial row reusing the plain row's executables (rightkit#1539), row keys reduced to the canonical compilation-relevant inputs of section 3 (rightkit#1540, required for "always warm"), the direct Linux path. Pure writer and parser checks before the cutover, integration tests after it (step 4); GC-A08 and GC-A24 amended in the same commits. No deletion yet.
4. **Cutover on the Mac (approval): the step 2 broker, then the step 3 gate.** The gate reaches the Mac only through its own pipeline: push approval, CI qualification, CI publication of `@rightkit/release`, then the trusted-gate install; none of that is implied by this step and each is asked for. Acceptance: the probe passes and one real door run compiles a commit through the seam with a durable receipt and a verdict written by an unscoped class A.
5. **Gate: delete.** The carrier, ownership, handshake, capability, grant and local-verification modules of section 4, in the same commits as the replacement tests that cover what they enforced; `qualification-verify.mjs` migrated, not deleted. Adapters go through the broker (section 3), not direct. Acceptance: the package suite and the gate's seam tests pass with the modules gone, and CI publication still verifies the new receipt.
6. **Broker: delete the legacy request path and section 5's modules**, Seatbelt included (rustright#234). Acceptance: a compile with no verdict is refused on the installed broker (the absent case, not only the red one), RESET-A/W/C/O pass on the harness with the legacy path gone, and the post-job tree check still fails a changed snapshot.
7. **Contracts: write `BUILD.md`, delete both contracts.** Acceptance: every sentence of `BUILD.md` names its test or refusal code or a GAP marker (section 6).
