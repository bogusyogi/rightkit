# RightKit vs the Fastframe family (ZapFast, Spotifast): component matrix

Date: 2026-10-24. Read in full: `/home/user/rightkit` (69 crates, 26 npm packages, Swift package), the eight Right Suite app repos, Ember, SwiftRight, and fresh clones of `crmne/fastframe` v0.14.1, `crmne/zapfast` v0.20.0 and `crmne/spotifast` v0.14.1. Nothing was built or run; line counts are `wc -l`, test counts are `#[test]` attributes.

## 1. Verdict

1. **RightKit's infrastructure layer is right and is deeper than theirs.** `rightkit-fs`, `-credentials`, `-logs`, `-crash`, `-app-settings`, `-db`, `-http`, `-child-process`, `-license`, `-oauth`, `-daemon`, `-sandbox` are runtime-neutral pure Rust, far larger and better tested than the Fastframe equivalents, and would survive any UI change unchanged.
2. **RightKit's shell layer has the wrong shape.** `rightkit-tauri-shell` (37.5k lines, 191-crate dependency subtree) fuses runtime-neutral capabilities (autostart, single instance, clipboard, notifications, presence, OS settings panes) to the `tauri` dependency, so no non-Tauri host (Ember's egui app, SwiftRight, the Swift menu-bar helper, overlay apps) can use them. Fastframe's "one small crate per capability" is the better shape.
3. **Fastframe is better in five places, and all five are gaps rather than rivals:** power/sleep/network conditions, notifications with actions outside Tauri, now-playing/media keys, Rust-side localisation, and a self-updater with rollback and key rotation (RightKit removed rollback in decision D01).
4. **Do not move the hubs to egui.** The suite has about 317k lines of TypeScript UI across eight apps plus ~17k in the shared React packages. MailRight (HTML email), ViewRight (HTML, Markdown, DOCX, PDF), CodeRight (code, diffs, Markdown) and every compose box need the browser's HTML and text engine. Stock egui still lacks bidi (emilk/egui#8577 is an open draft; the Fastframe apps carry ~1.1–1.5k lines of bidi code each plus a fork), has no spellcheck, autocorrect or dictation, and needs hand-labelled accessibility. Fastframe itself is 196 stars, one author, git-tag-only, "APIs can change", and sits on a 13-patch fork of egui and winit. Your documented native direction is SwiftRight on GPUI; egui would be a third UI stack.
5. **The idle-RAM problem is real on Windows and is not about egui.** Your own HeardRight measurement: 504 MB working set across 8 WebView2 processes with the hub hidden, versus 47.6 MB for the Rust host; 72% of it is per-environment overhead that `TrySuspend` does not release. ZapFast's 150–200 MB idle on Linux is comparable to a Tauri hub on macOS. The 10x win is available without a UI rewrite: no WebView2 environment while idle (resident native host, on-demand hub process).
6. **Zig: no case.** Everything they do is in Rust, and everything you own is in Rust.

## 4. What to take from them, ranked by payoff

1. **Measure before anything else.** Publish a ZapFast-style benchmark for each hub on macOS and Windows: PSS or private working set summed over the process tree, process count, process start to first window, usable UI. No Right Suite hub has an idle or cold-start number today, and MailRight's homepage figure is marked unverified in your own repo.
2. **Remove the idle WebView2 environment on Windows for tray-resident apps** (HeardRight, MailRight closed to tray, Pulse). Your own correction doc has the ladder: ~504 MB today, ~458 MB suspended, ~48 MB with the environment gone. Run the experiment first: do the `msedgewebview2` processes exit when the last Tauri window closes? If yes, destroy on hide and recreate on show. If no, make the hub its own process launched by the resident Rust host. This is the 10x, and it keeps every line of React.
3. **Split `rightkit-tauri-shell`** into runtime-neutral crates plus a Tauri adapter. The agent survey found autostart, single instance, clipboard, presence, OS settings panes and deep links already have no Tauri references. The split also serves SwiftRight through a C ABI and Ember's egui host, and it shrinks the 191-crate subtree.
4. **Add the four missing owners, designed after Fastframe:** `rightkit-power` (sleep, resume, lock, battery, metered network, with the macOS resume event they lack), neutral notifications with actions and replace keys, now-playing over souvlaki, and a Rust localisation owner fed from the same catalog as `@rightkit/i18n`. Emit resolved theme tokens as JSON for non-web UIs.
5. **Reinstate updater rollback and add key rotation.** Fastframe rolls back when the new build does not report started within a minute and carries `additional_publisher_keys` for rotation; RightKit's D01 removed the retained previous copy and boot probation now says "reinstall".
6. **Get RightKit a 3-OS CI matrix.** Their every-PR compile on ubuntu/macos/windows is the single biggest process advantage they hold over you; your shell shipped Windows paths uncompiled.
7. **Small borrows:** `fastframe-file`'s UI-thread write guard; Spotifast's DPAPI sealed credential fallback and revocation markers; Spotifast's CI gate on new settings; `fastframe-audio`'s pause-when-idle output and allocation-free callback test; package-manager-installed detection in the updater; system-proxy and SOCKS in `rightkit-http`; GitHub artifact attestations.
8. **Do not:** rewrite the hubs in egui; add git-tag dependencies on fastframe (your own release checks refuse them; fork and publish as `rightkit-*` if you take one); copy their assets (ZapFast ships GPL-2.0 Pidgin sounds; code is MIT, assets are not all MIT); choose Zig.

## 5. Should the hubs leave React + Tauri at all?

What the browser engine gives the suite that egui cannot today: HTML email bodies, Markdown and HTML documents, DOCX (ViewRight vendors a docx editor), PDF (pdf.js), code editing with diffs, rich text compose, OS spellcheck/autocorrect/dictation, TSF/IME, screen-reader trees, bidi and complex-script text, printing. Ember's egui app had to write its own text field, i18n, theme, icons, docking, date picker, menus, colour-profile handling and control channel, and still has no tray, no single instance, no notifications and no updater. ZapFast and Spotifast each needed 60k+ lines of UI Rust for one product and still reimplement bidi.

What egui gives: one process, 50–200 MB idle, 150 ms first window, no renderer processes, Linux for free. The suite does not ship Linux, and most of Fastframe's hardest work (Wayland occlusion, portals, Flatpak, ksni, MPRIS, RTKit) is Linux-driven.

If you do leave WebView for some surfaces, you already have two native paths: `rightkit-overlay-win` + Swift panels for always-on surfaces, and SwiftRight (SwiftUI semantics on GPUI 0.2.2, with a ≤110%-of-Tauri non-regression contract). Adding egui would be a third stack with a weaker text engine than either.

## 6. The streaming-browser idea, in short

Hotstar, Prime Video and Apple TV require Widevine/PlayReady/FairPlay; no third-party native client can obtain those CDMs lawfully. The low-resource version of that product is therefore a resident native shell that creates an OS WebView window only while something plays and destroys it afterwards, not a new engine. Spotify is the exception: Spotifast (MIT) over librespot is already the native answer, with Premium required and the usual unofficial-client risk. YouTube has no DRM for most content but a native client is a terms-of-service question, not a technical one.
