# RightKit dependency audit, batch 3 (12 crates) with inventory sections A-C and F

Date: 2026-10-08. Read-only. No source, manifest, lockfile or repository state was edited. Nothing was committed or published.

## Method and measurement limits

- **Workspace blocker.** `rightkit cargo` fails on the real workspace: `crates/rightkit-align/` is a directory with `src/` and `tests/` but no `Cargo.toml`, and the root `Cargo.toml` lists `crates/*` as members. Every cargo command in the repository fails with "failed to read crates/rightkit-align/Cargo.toml". Another worker is creating align, compose and contracts, so I did not touch them.
- **Workaround.** I built a scratch workspace outside the repo at `scratchpad/ws/`. It holds a copy of the root `Cargo.toml` and `Cargo.lock` plus symlinks to every crate directory except `rightkit-align`. All cargo queries ran as `rightkit cargo tree` from that scratch workspace, so resolved versions match the real lock.
- **Host target.** Counts are for the default host target (aarch64-apple-darwin). The Windows target is not registered with the RightKit broker (`managed Rust target must be registered by broker: x86_64-pc-windows-msvc`), so Windows-only trees are **estimated** from manifests, not measured.
- **Counting.** "Transitive crates" are unique crate versions reachable through normal and build edges, excluding the crate itself. "Crates added by D" is the set of crates reachable only through direct dependency D, computed from the complete edge graph of `cargo tree -e normal,build`. That set includes D itself, so subtract one for a true add count. These are **measured**.
- **Use sites** were grepped in `src/` and `build.rs`. Tests are listed separately. "UNUSED" means no reference in src, build.rs or tests.
- **Not checked.** No network advisory lookup was done (no `cargo audit`), so security statements are limited to the code and manifests.

## Cross-cutting findings (short)

1. **ONNX Runtime is wired directly in five crates, not through rightkit-ort.** Direct `ort` pins: `rightkit-ocr` (Cargo.toml:23, and Windows at :41, with `directml`), `rightkit-qts` (Cargo.toml:47; source `src/pipeline/vocoder.rs:9-12`, about 25 `ort::` sites), `rightkit-asr` (Cargo.toml:32), `rightkit-vad` (Cargo.toml:17), `rightkit-embed` (Cargo.toml:13, beside `rightkit-ort` at :14). `rightkit-ort` already re-exports `ort` (`crates/rightkit-ort/src/lib.rs:26`). The direct pin duplicates the suite pin (`=2.0.0-rc.13`) and bypasses the shared environment and provider setup. The pin itself is consistent (one `ort` in the lock).
2. **download-binaries is not enabled anywhere I measured.** Every direct `ort` spec uses `default-features = false` (ocr:23, ort:35, qts:47, asr:32, vad:17, embed:13). `ureq` (the ort-sys download path) is absent from every normal and build tree of the 12 crates. I did not inspect the ort-sys source to confirm no other download path exists; that remains **estimated**.
3. **Version drift in consumers.** App repos pin RightKit crates behind the published versions (see each C section and the table at the end).
4. **Duplicate versions cost real crates.** sha2 0.10 vs 0.11, prost 0.13 vs 0.14, windows 0.61 vs 0.62, nix 0.28 vs 0.30, getrandom 0.3 vs 0.4, rand 0.9 vs 0.10 (workspace lock, measured by the Cargo.lock parse).
