## Confirmed findings

### F1 — `ParakeetEngine` advertises Sendable while exposing unsynchronised mutable vocabulary and concurrent runtime access (high)

`ParakeetEngine` declares `SpeechTranscribing, @unchecked Sendable` (`Sources/RightKitSpeech/SpeechEngines.swift:61`). Its public `vocabulary` is mutable (`:88`), async methods read it then launch independent `Task.detached` operations against the same `runtime` (`:90-103`), while blocking/static/prime methods call that runtime directly (`:106-132`). Two tasks can race a vocabulary mutation and can enter shared Core ML stage instances concurrently; the package provides no actor/single-flight gate. `WhisperEngine` supplies `PredictionExecutor` serialization (`:157-227`), showing this is not an unavoidable package pattern. Existing Parakeet tests are serialized and sequential (`Tests/RightKitSpeechTests/ParakeetEndToEndTests.swift:13-116`), so they do not disconfirm concurrent use. Add an actor gate or immutable per-call options, then stress concurrent async/blocking calls under strict concurrency.

### F2 — stopping legacy live dictation during setup can install stale audio state after teardown (high)

`stop()` increments generation, cancels `startTask`, and immediately calls `teardown()` (`Sources/RightKitSpeech/LiveDictationSession.swift:77-81`). `beginLegacy` starts `AVAudioEngine`, creates the recognition task, then stores `engine`, `tapInstalled`, `request`, and `task` only at `:161-166`; it does not recheck generation after the potentially blocking `engine.start()`/`recognitionTask` calls (`:145-160`). If `stop()` runs between `engine.start()` and that store, teardown sees nil, then stale resources are stored after stop; `run` emits `.status(nil)` at `:120-121` without a post-setup generation check. Current tests cover stop while permission awaits (`Tests/RightKitSpeechTests/AppleSpeechAndDictationTests.swift:165-186`), not this setup interleave. Publish setup into a generation-owned state machine, recheck after every setup await/blocking boundary, and tear down local resources when stale.

### F3 — shared `FileSyncStateStore` can lose state across app/extension processes (high)

The type documents app-group use (`Sources/RightKitCloudSync/SyncStateStore.swift:73-75`), but `load` reads directly (`:80-91`) and `save` performs temp replace/readback without `AppGroupFileLock` (`:94-112`). Two CloudSyncEngine instances can load the same token/version/tombstone document, save disjoint updates, and last-writer-wins; concurrent corruption quarantine can move a newly replaced file. Atomic replace prevents torn bytes, not lost read-modify-write state. Existing tests prove restart/corruption recovery only (`Tests/RightKitCloudSyncTests/PersistenceAndCloudKitTests.swift:7-23`). Add a shared lock configuration or make this store depend on the existing locked App Group primitive, with two-process merge/lost-update tests.

### F4 — macOS watcher has unbounded event buffering (medium)

`RightKitWatcher` creates an unbounded `AsyncStream` (`Sources/RightKitWatch/RightKitWatch.swift:181`) and documents that events buffer until iteration (`:159-172`). A stalled or abandoned consumer can accumulate arbitrarily many FSEvents, consuming memory; `stop` is the only release path. Existing live tests consume promptly and do not exercise a burst with a stalled reader (`Tests/RightKitWatchTests/RightKitWatchTests.swift:101-170`). Use a bounded policy with explicit drop/rescan semantics, or expose a caller-selected buffering policy and document memory limits.
