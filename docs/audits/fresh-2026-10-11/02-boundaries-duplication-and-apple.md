Keep both boundaries pending reconciliation; acceptance is one current ownership statement plus an API/platform matrix and concrete same-host consumer evidence before any migration. A versioned evidence/receipt contract may be shared without merging runners.
2. `rightkit-qts-ggml` is a direct deprecated wrapper over `rightkit-qts-ggml-sys` ([crates/rightkit-qts-ggml/Cargo.toml:8](</Volumes/D/claude/rightkit/crates/rightkit-qts-ggml/Cargo.toml:8>), [crates/rightkit-qts-ggml/src/lib.rs:1-7](</Volumes/D/claude/rightkit/crates/rightkit-qts-ggml/src/lib.rs:1>)). Keep only as a no-new-API compatibility package; acceptance is zero in-tree dependants (current `rightkit-qts` depends on `rightkit-qts-ggml-sys`), then deprecate/remove on next breaking release.
3. `rightkit-send` has private `write_atomic` code beside `rightkit-fs`'s shared atomic writer ([crates/rightkit-send/src/lib.rs:213-237](</Volumes/D/claude/rightkit/crates/rightkit-send/src/lib.rs:213>), [crates/rightkit-fs/src/atomic.rs:1-14](</Volumes/D/claude/rightkit/crates/rightkit-fs/src/atomic.rs:1>)). Its current caller persists host trust records ([crates/rightkit-send/src/trust.rs:244-255](</Volumes/D/claude/rightkit/crates/rightkit-send/src/trust.rs:244>)). Semantics overlap but are not identical: send creates parent dirs, writes `0600` on Unix, `sync_all`s the file, renames, and cleans a failed temp ([crates/rightkit-send/src/lib.rs:215-237](</Volumes/D/claude/rightkit/crates/rightkit-send/src/lib.rs:215>)); `rightkit-fs` additionally supports owner-only/private-dir policy, no-follow temp creation, existing-mode handling, configurable replacement/retry, and directory `fsync` ([crates/rightkit-fs/src/atomic.rs:21-29](</Volumes/D/claude/rightkit/crates/rightkit-fs/src/atomic.rs:21>), [crates/rightkit-fs/src/atomic.rs:175-237](</Volumes/D/claude/rightkit/crates/rightkit-fs/src/atomic.rs:175>), [crates/rightkit-fs/src/atomic.rs:260-287](</Volumes/D/claude/rightkit/crates/rightkit-fs/src/atomic.rs:260>)). Treat as shared-contract candidate, not proven removable duplicate: acceptance is trust-store persistence review covering directory durability, owner-only result, Windows behavior, symlink/mode handling, and failure cleanup, then either delegate with matching options or document protocol-specific exception.

## Internal decomposition priorities

Public package split & internal component decomposition are different decisions. Keep published entry points stable while making resource/state ownership explicit:

| Component | Internal boundary to tighten | Why / acceptance |
|---|---|---|
| Swift Speech | Generation-owned capture session & serialized/immutable decode configuration | S01/S02: single cleanup owner, stop/start interleavings & concurrent decode tests. |
| CloudSync persistence | Cross-process transaction or elected writer, separate from transport actor | S03: an actor serializes only its process; ownership must cover load/modify/save. |
| Watch/index/service/jobs | Bounded ingress/subscriber queues, admission limits & visible pressure counters | Declare overflow/rescan/reject semantics; benchmark stalled consumers & connection storms. |
| Release readiness | Evidence schema/validator separate from README presentation | P02: bind real measurements, workload, platform & source identity to qualification. |
| Send persistence | Protocol caller separate from filesystem durability policy | A03/F01: shared atomic writer only after permission/rename/durability parity; unique owned partials. |
| UI media stage | Focus/keyboard interaction contract explicit in stage component | U01: keyboard reachability becomes independently testable without app-specific wrappers. |

No automatic merge is justified for `update`/`updates`, JS/native logging or licensing, shell/app-shell, speech client/inference, jobs/scenario, or filesystem/index/search. Language, process & policy boundaries are meaningful. Similar names alone are not duplication.

## Source findings — see independent adjudication below

### F1 — `ParakeetEngine` advertises Sendable while exposing unsynchronised mutable vocabulary and concurrent runtime access (high)

`ParakeetEngine` declares `SpeechTranscribing, @unchecked Sendable` (`Sources/RightKitSpeech/SpeechEngines.swift:61`). Its public `vocabulary` is mutable (`:88`), async methods read it then launch independent `Task.detached` operations against the same `runtime` (`:90-103`), while blocking/static/prime methods call that runtime directly (`:106-132`). Two tasks can race a vocabulary mutation and invoke shared Core ML stage instances concurrently; runtime thread safety remains separately unqualified; the package provides no actor/single-flight gate. `WhisperEngine` supplies `PredictionExecutor` serialization (`:157-227`), showing this is not an unavoidable package pattern. Existing Parakeet tests are serialized and sequential (`Tests/RightKitSpeechTests/ParakeetEndToEndTests.swift:13-116`), so they do not disconfirm concurrent use. Add an actor gate or immutable per-call options, then stress concurrent async/blocking calls under strict concurrency.

### F2 — stopping legacy live dictation during setup can install stale audio state after teardown (high)

`stop()` increments generation, cancels `startTask`, and immediately calls `teardown()` (`Sources/RightKitSpeech/LiveDictationSession.swift:77-81`). `beginLegacy` starts `AVAudioEngine`, creates the recognition task, then stores `engine`, `tapInstalled`, `request`, and `task` only at `:161-166`; it does not recheck generation after the potentially blocking `engine.start()`/`recognitionTask` calls (`:145-160`). If `stop()` runs between `engine.start()` and that store, teardown sees nil, then stale resources are stored after stop; `run` emits `.status(nil)` at `:120-121` without a post-setup generation check. Current tests cover stop while permission awaits (`Tests/RightKitSpeechTests/AppleSpeechAndDictationTests.swift:165-186`), not this setup interleave. Publish setup into a generation-owned state machine, recheck after every setup await/blocking boundary, and tear down local resources when stale.

### F3 — shared `FileSyncStateStore` can lose state across app/extension processes (conditional P2)

The type documents app-group use (`Sources/RightKitCloudSync/SyncStateStore.swift:73-75`), but `load` reads directly (`:80-91`) and `save` performs temp replace/readback without `AppGroupFileLock` (`:94-112`). Two CloudSyncEngine instances can load the same token/version/tombstone document, save disjoint updates, and last-writer-wins; concurrent corruption quarantine can move a newly replaced file. Atomic replace prevents torn bytes, not lost read-modify-write state. Existing tests prove restart/corruption recovery only (`Tests/RightKitCloudSyncTests/PersistenceAndCloudKitTests.swift:7-23`). Add a shared lock configuration or make this store depend on the existing locked App Group primitive, with two-process merge/lost-update tests.

### F4 — macOS watcher has unbounded event buffering (medium)

`RightKitWatcher` creates an unbounded `AsyncStream` (`Sources/RightKitWatch/RightKitWatch.swift:181`) and documents that events buffer until iteration (`:159-172`). A stalled or abandoned consumer can accumulate arbitrarily many FSEvents, consuming memory; `stop` is the only release path. Existing live tests consume promptly and do not exercise a burst with a stalled reader (`Tests/RightKitWatchTests/RightKitWatchTests.swift:101-170`). Use a bounded policy with explicit drop/rescan semantics, or expose a caller-selected buffering policy and document memory limits.

## Swift skeptic review — 2026-10-11

Independent static control-flow review of F1–F4 in `swift-review.md`. No build, test, network, install, or source edit was run; prior audit reports were not used. Review is bounded to cited Swift paths and does not claim whole-repository coverage.

F1 is confirmed in narrowed form. `ParakeetEngine` declares `@unchecked Sendable` at `SpeechEngines.swift:61`, exposes mutable `vocabulary` at `:88`, and reads it from async and synchronous decode paths at `:90-113`. A concurrent caller mutation can race those reads, so Sendable safety is not established. `Task.detached` at `:93-103` shares one runtime, while `ParakeetCoreMLStage.predict` calls the same `MLModel` objects at `ParakeetCoreMLStage.swift:117-131`; concurrent Core ML safety is a separate unqualified risk, not needed to confirm the public Array race.

F2 is confirmed. `stop()` increments generation, cancels `startTask`, then calls `teardown()` (`LiveDictationSession.swift:77-81`). `beginLegacy` installs a tap, synchronously starts the engine, creates recognition task, then publishes resources under lock (`:144-166`). There is no generation check between `engine.start()`/`recognitionTask` and publication. A stop interleaving therefore tears down nil state, after which stale engine/request/task are stored and remain active; callback generation checks suppress output but do not release resources.

F3 is confirmed as an App Group design gap. `FileSyncStateStore` explicitly supports an app-group URL (`SyncStateStore.swift:73-75`), but `load`, corrupt quarantine, and `save` (`:80-112`) have no shared file lock. `CloudSyncEngine` owns state only per actor (`CloudSyncEngine.swift:48-112`) and persists whole snapshots (`:693`), so separate app/extension processes can perform load-modify-save interleavings that lose one writer’s token, version, or tombstone. Atomic replace protects byte integrity, not merge integrity.

F4 is confirmed, with impact kept medium. `RightKitWatcher` uses `.unbounded` buffering (`RightKitWatch.swift:181`) and yields from every callback record (`:261-269`). The stream’s termination hook stops only on cancellation/finish; a retained watcher with a stalled consumer can accumulate events without a cap. Existing `mustRescan` flags describe FSEvents loss but do not bound this Swift-side queue.

The packet covered 29 of 1,996 denominator paths and omitted the remainder under its byte cap. Result therefore sets `complete: false`; findings are source-anchored and verified only for cited paths.

## Send receive collision skeptic review

Existing `reasoning.data-safety` finding `send-f1-partial-path-overwrite` is technically reproducible as a conditional data-loss hazard, with narrower reachability than finding text suggests.

- `crates/rightkit-send/src/receive.rs:468-486` sanitizes sender-controlled `file_name`, atomically reserves only `final_path`, then derives deterministic hidden `part_path`.
- `crates/rightkit-send/src/receive.rs:485-493` opens hidden path with `create(true).truncate(true)`, so pre-existing `.name<temp_suffix>` is truncated before bytes, checksum, or rename.
- `crates/rightkit-send/src/proto.rs:179-211` proves final-name collision handling is atomic, but it does not reserve/check derived partial path.
- `crates/rightkit-send/src/receive.rs:544-549,552-569` removes both paths on stream, checksum, or rename failure, so cleanup can also remove a pre-existing partial file.

Skeptic verdict: retain as `HARDENING_GAP`, medium severity, confidence likely. Sender cannot directly write receiver save storage; exploitation needs a stale/manual partial file whose predictable name matches accepted sender filename, or a local concurrent actor racing before open. Fix by reserving partial path with `create_new` plus retry, or using unpredictable per-transfer temp name, and track ownership before cleanup. Add regression test precreating expected partial path and proving it survives.
