### Terms & fixed boundaries

- **Origin host** is Adrian's Mac, Dell, or Linux host where the shared gate runs & performs the required local compile for its supported local target. That compile proves only the source/target it actually compiled.
- **Native build target** is an artifact target declared by the product manifest. Use the origin's local compile output when it can produce the required target. Add a native build only when origin cannot produce that target; Mac/Windows final artifacts must be constructed on their native platform, never cross-compiled from Linux. RightKit/public qualification runs on CI & may qualify already sealed native bytes unchanged; private qualification runs on Mac or Dell. When a private manifest declares Linux target, qualify exact sealed Linux bytes from Linux-origin candidate in compatible Linux runtime/architecture hosted by Mac or Dell; do not rebuild those bytes there. The runtime/architecture must match target. WSL2 counts as Linux for origin & acceptance, whether alone or hosted on Dell; no extra machine is required. The same WSL2 host may provide Linux-origin compile & Mac/Dell-hosted qualification if compatible, as distinct stages on exact bytes unchanged. Compatibility remains OPEN/unproven; no environment is claimed provisioned. Linux origin remains direct, without broker routing or spoofed host identity.
- **Qualification runner** is CI for RightKit/public & Mac or Dell for private apps. Private qualification need not run on both hosts unless a target requires it. Private Linux does not acquire a mandatory GitHub CI path.
- **One entry** means one shared gate entry on each supported origin, not one executor everywhere. Adrian's native Mac & Windows gate invocations use the broker regardless of human/agent caller. Every Linux execution host always runs direct with no broker, whether WSL2, VM, standalone/cloud, or hosted on Dell; RustRight on PATH and physical host do not change that route. Hosted CI retains its runner path.
- **Class A first** means agreed deterministic/mechanical checks classified as Class A by a complete command-behavior inventory run before first local compile. Current scans place some tests in B because they may indirectly spawn a compiler. The inventory must identify actual dependency/launch behavior; neither all-tests-A nor all-tests-B is presumed. Class A placement changes in either direction require dependency/launch evidence & preserve approved coverage. Compiler-backed commands such as `cargo check` & `clippy` remain B. Sage/Astra may adjudicate the inventory; Fable is the designated Oracle contract reviewer. These roles add no extra mandatory review gate. Inventory & placement remain OPEN.
- **Commit-only build** is the binding model (Adrian, 2026-10-28: “it only builds from the committed tree, not from the uncommitted … the changes can go on separately in the tree”). The gate selects a commit SHA and builds a snapshot of that commit from a gate-owned, persistent source directory, one per repository per host; build outputs go to the repository's existing build-output directory and the existing warm cache is reused. Only the source is separate. The primary checkout stays free for ongoing edits and uncommitted changes never enter a build. The candidate identity is the commit SHA. Every stage, `--to dev` & `--to test` included, builds a commit; there is no dirty-tree condition on the checkout and no push prerequisite (CI qualification & the trusted publisher need the commit on origin by construction). Warm cache is a requirement, not an option: the snapshot is synced into the persistent source directory by content, writing only files whose bytes differ and leaving timestamps of unchanged files untouched, so cargo & pnpm rebuild only what changed; a fresh export per build, or a second output/cache directory, is a defect. The sync produces an exact snapshot of the commit, not merely changed bytes: files absent from the commit are removed, tracked file types & modes are preserved, and no link inside the snapshot may resolve into the editable checkout. Warm is required, not measured only: every build, check, Clippy, test and package stage on every host uses the repository's single existing output directory and caches (Cargo target, sccache, pnpm store, the gate's own result cache); the only permitted cold build of a repository on a host is its first-ever build there, and any later rebuild not explained by changed inputs, dependencies, configuration or toolchain fails the stage. Cache reuse is required and measured. Source-path changes may invalidate cached work. Record rebuilt units & invalidation reasons per stage; flag rebuilds unexplained by changed inputs, dependencies, configuration, or compiler cache rules. The gate acquires the host's build ownership before syncing the snapshot and holds it until the stage completes, so no other request can replace the snapshot while a compiler reads it. The build reads the gate-owned copy, so an edit to the checkout during a compile cannot reach it; no freeze or in-run detection is needed.
- **Qualification policy** is pinned by immutable version/digest before a run. Required checks, target/runtime/architecture coverage, & approved baseline are fixed independently of self-reported results, bound to exact final bytes, & recorded with check IDs, results, expected coverage, & executed coverage. Missing/skipped checks, empty mandatory suites, wrong policy/target, or policy/coverage changes fail or invalidate affected evidence; no silent weakening.
- **Linux headless** means installation, gate/build/CLI use, & Pulse guest operation need no browser or interactive browser authentication. CLI token/input remains allowed. Owner-side approval may happen on Mac/Dell. Pulse's original guest use is shell/script join & messaging; [pulse#492](https://github.com/bogusyogi/pulse/issues/492) & [acceptance comment](https://github.com/bogusyogi/pulse/issues/492#issuecomment-6466661659) describe desired headless join, two-way messaging, reconnect within a valid lease, & revoked/expired denial; neither source proves a runtime result.
- Linux needs no broker or build-service prerequisite solely to invoke the shared gate. Existing app runtime services are allowed. A Linux CLI may have a package/version pin; it must not require Mac/Dell broker trust or service to run.
- Product manifests define target artifact kinds. Pulse's headless Linux bundle is required. Do not infer Linux GUI installers for every app.
- Preserve existing product signing & authentication. Native target builds are distinct provenance stages, not signing transformations. Sign once, qualify the final sealed bytes, then promote those bytes unchanged.
- **One signing identity per product, every build** (Adrian, 2026-10-29: "every build has to have the same signing identity … else how will permissions granted stay the same"). Every build of a product on every host and stage (`dev`, `test`, package, qualify, release, native target builds) carries the product's one stable identity: the same bundle/application id, the same signing identity (Apple Developer ID team & certificate; Windows publisher certificate & app user model id) and the same designated requirement. No build is unsigned, ad-hoc signed or given a new id, so permissions the operating system granted once (privacy/TCC, keychain, firewall, notifications, login items) persist across builds. Bytes and hashes change between builds; the identity never does. A stage that cannot sign with that identity is refused, not shipped unsigned.
- The shared gate applies to managed agents & human invocations through that entry. It does not globally intercept a personal terminal outside the entry. Do not fork per-app gates or add agent bypasses.
- For local managed builds, the primary checkout is the source of the selected commit, the gate-owned persistent snapshot directory supplies the source bytes, and outputs land in the existing build-output directory with the existing cache; each repository on each host has exactly one primary checkout, one gate-owned snapshot directory and one output directory; no clone, worktree, branch, export, archive or copy of the source, ever, and no second output, target or cache directory (a stage that would need one is refused); the gate's own snapshot of the selected commit (one per repository per host, kept warm by content sync) is how a build reads the commit and is not such a copy (Adrian, 2026-10-29: "i had already stated that build should be based on a commit, so even if other files are edited, it doesn't matter. the build is from the commit"); a stash is allowed only to set uncommitted work aside in the primary checkout and restore it there, never as a build source and never left behind (Adrian, 2026-10-29); no agent-run check or build reads the checkout's uncommitted state (`--worktree` or any equivalent); the gate reuses every unchanged scan result by its full input key, and its cache bypass (flag or environment form) is for Adrian alone in his own terminal outside every agent harness, refused under any agent harness and never written in any document, script, test or CI file; warm cache preserved by content sync; one build per host. Hosted CI uses its normal source checkout for native jobs. Keep Mac scratch at `/Volumes/D/scratch`, Dell scratch at `D:\scratch`; configure suitable durable Linux state per host policy. Temporary directories may hold disposable pack data, not durable pipeline state.
- Commit and push run no gate and no local hook checks; the gate is for building (Adrian, 2026-10-28: “Why would push and commit need a gate? … The gate is for building.”). Shared hook generation/installation stops installing the pre-push gate; CI runs preflight and the full check on every push as it does today. Adrian disputes the 2026-10-22 pre-push authorization recorded in `.rightkit-local-build.json`; it is not a source for this contract and that record needs correcting. RightKit's Git-triggered release is separate: absent required local-compile or CI evidence blocks release eligibility, not Git transport.
- Concurrent retries require durable shared authoritative coordination at existing dispatch/publication boundaries, with no new Linux broker/service prerequisite. Candidate/dispatch identity binds repository, source/tree, policy, artifact, & route. Publication conflict identity is registry+package+version, independent of origin. Atomically claim identities; same identity/digest joins or reconciles; conflicting bytes reject; query lost acknowledgements rather than blindly retry; ambiguous/unavailable state stays blocked. No mechanism is selected.
- **Publication runs through CI by default** (Adrian, 2026-10-29). Local publication of a build happens only when Adrian asks for or approves it in his own words for that named build; the agent quotes his words in the record. No other route, flag, hook or agent decision grants it.
- Only RightKit explicitly requires automatic Git-triggered publication. Public apps require CI qualification & signed installers available. Latest user requirements do not specify private-app publication or public-app auto-publication; do not infer either here. Existing distribution policy remains separately applicable.

### Broker interface (the single definition; the broker contract references it)

Agreed with the RR chat (Fable, rustright session fdd027b9) on 2026-10-28. Names below are the contract's field names; the broker contract mirrors them.

**Snapshot root.** Mac `/Volumes/D/.rightkit-managed/snapshots/<repo-key>`, Dell `D:\.rightkit-managed\snapshots\<repo-key>`, so the broker's volume & disk-floor checks cover it; `repo-key` = `sha256(canonical repository path)[:16]`, the key `checked-trees` uses. The path follows the managed root through root migration (rustright#91). Linux: a durable root named in gate configuration, default `$XDG_STATE_HOME/rightkit/snapshots/<repo-key>` (fallback `~/.local/state/rightkit`). Phase 0 verifies the gate can create & write under the managed root on Mac & Dell; scratch is never the snapshot root because it is disposable.

**Output directory & cache.** The gate creates no output directory of its own. The executor's existing build-output directory & cache are used: on Mac & Dell the broker keeps pinning `--target-dir` to the repository's managed generation target (`ws/<repo-key>/g/<gen>/target`), `CARGO_HOME`, `sccache` & temp as today; on Linux the gate resolves the output directory before it changes the source location: `cargo metadata --format-version 1 --no-deps` run in the primary checkout with the stage's environment yields `target_directory` (it honors `CARGO_TARGET_DIR` & `.cargo/config.toml` `build.target-dir`), and the gate passes that absolute path as `CARGO_TARGET_DIR` to every Cargo invocation in the snapshot. Cargo would otherwise resolve `target/` relative to the snapshot and a relative `build.target-dir` relative to the snapshot's config file, which is a second output directory & a defect under the commit-only build bullet. `CARGO_HOME`, `sccache` & temp directories are inherited as absolute values, never snapshot-relative. Every receipt records the resolved path as `outputDir` (on Mac & Dell the broker's pinned target directory).

**Class A on managed hosts** runs, for the unit being built, `rightkit-gate check --commit <sha> --unit <kind:name> --snapshot <dir>`: only what that build reads (the unit and its dependency closure: typecheck, lint, the tests that start no compiler) plus the repository-wide file-only scans (lockfile, audit, secret scan, workflow and file hygiene), never another unit's typecheck, lint or tests (Adrian, 2026-10-29: "If one package is being built, why the fuck would the whole repo be scanned?"); the whole-repository `--full-a` is CI's, on every push, with the primary checkout as `cwd` (commit lookup & object database) and the snapshot as the checked file root, never `--worktree`. This is a gate-owned change: the current `--full-a --commit` path (`bin/rightkit-gate.mjs:1789-1797`) refuses unless the commit is HEAD of a clean checkout and then rewrites itself to `--worktree`, which the editable checkout can never satisfy under the commit-only build. In snapshot mode the gate reads neither the checkout's HEAD nor its status; the file list is `git ls-tree -r <sha>` from the checkout; every scan runs with the snapshot as its working directory; the snapshot's tree id is computed against the checkout's object database with a temporary index (`GIT_INDEX_FILE=<tmp> git --work-tree=<snapshot> add -A` then `write-tree`) and must equal `<sha>^{tree}` before & after the check, or the result is `RK_CHECK_ERROR`. The broker's own `snapshot_tree` verification uses the same method so the two agree. `--worktree` remains for a developer's own run on a dirty tree and never admits a build. Linux runs the same snapshot-aware check direct. The broker runs no gate and no RightKit code (Adrian, 2026-10-29: "nothing rk is needed to build and manage the broker. at all." and "rk uses broker, not the other way around"): Class A, its verdict reuse and the admission check are the gate's, done before the gate calls the broker; the broker admits a compile only on checks that execute nothing (the request names the host's configured trusted gate entry by path & sha256, the snapshot carrier and tree bind). The gate reuses a Class A verdict keyed on: commit tree id; gate entry sha256 & checker tree digest; `classAEnvironmentDigest`; declared-input digest; broker toolchain identity (cargo & rustc digests, toolchain name); `CARGO_HOME` registry state; & the advisory-database state of the day (`~/.cargo/advisory-db` revision) plus the `cargo-deny`, `cargo-audit` & `actionlint` tool digests. The last two items are explicit because `classAEnvironmentDigest` (`bin/rightkit-gate.mjs:468`) covers the gate package including its shipped advisory data, node & pnpm versions, platform/arch, each package's `node_modules/.modules.yaml`, the installed dependency bytes & tool caches under `node_modules`, but not `CARGO_HOME` or the cargo advisory database; the gate itself never caches the live scans (`cargo-deny`, `cargo-audit`, `pnpm-audit`, `pnpm-lockfile`, `advisory-exceptions`, `:1058`), so a reused verdict is valid only while those inputs are unchanged. Reuse covers the deterministic scans only: `pnpm-audit` (`deterministic-scans.mjs:851`) queries the registry's advisory service live and has no local pin, so its answer can change while every key item is identical; `cargo-deny` & `cargo-audit` read the pinned advisory-database commit (`advisory-db.json`, `--no-fetch`) and are covered by the key. Before a reused verdict is accepted, the executor re-runs the live remote scans (`pnpm-audit`, per root) against that commit's snapshot; the reused verdict is green only if they pass, and its receipt names them under `refreshed`. Binding reuse to an upstream freshness signal instead of a re-run is allowed only when the registry exposes one; none is known today.

**Request** (gate → broker, new fields on the existing managed-agent request beside `callingGate`, `argv`, `env`):

| Field | Content |
|---|---|
| `commit` | `{ sha, tree }` of the selected commit |
| `snapshot` | `{ path, expectedTree }`; the gate guarantees content equals the commit tree at hand-off; the broker re-verifies (`snapshot_tree`) before spawn & refuses `RK_CHECK_ERROR` on mismatch, re-verifies after exit & discards the result on mismatch |
| `declaredInputs` | `.rightkit/compile-inputs.json` read from the snapshot; the broker digests in place, no copy |
| `ownership` | `{ handle }`, the gate's build-ownership handle id; enforced by the gate, correlated by the broker |

**Returned evidence** (receipt, consumed by the gate):

| Field | Content |
|---|---|
| `requestId`, `brokerVersion`, `executor` | correlation |
| `commit`, `snapshot.path`, `snapshot.treeAtStart`, `snapshot.treeAtExit` | identity bind |
| `declaredInputDigests` | as digested in place |
| `verdict` | Class A result; `reusedFrom` when reused |
| `freshness` | `{ unitsAtStart, fresh, notFresh, invalidationReasons }`: the census the measured-cache rule is judged from; the broker promises no rebuild count |
| `timingsMs` | `{ admission, queue, bind, cargo, afterExitBind, diagnostics }` |
| `exit`, `diagnosticsPath` | exit status & structured diagnostics |
| `outputDir` | the absolute output directory the stage wrote to (broker-pinned on Mac & Dell; resolved from the primary checkout on Linux) |
| `refreshed` | the live remote scans re-run before a reused verdict was accepted (`pnpm-audit` ids); empty when nothing was reused |

**Broker lease.** From admission to reap the broker holds a per-snapshot lease: it refuses or queues any request naming that snapshot with another commit, or a path inside it, whatever `buildConcurrency` says. The broker never creates or syncs a snapshot & never compiles the primary checkout.

**Linux** uses the same sync & ownership with direct Cargo & no broker fields; the gate writes its own receipt with the same field names minus the broker-only ones (`admission`, `queue`, `reusedFrom`).

### Clippy route & batching (gate-owned; carried from the broker contract's D4)

The diagnostic route is a gate-owned destination for a request such as `cargo clippy --workspace --all-targets -- -D warnings`. Source today exposes `--to check|compile|package|qualify|release` & per-unit stages; `check --only` is app rules only & not a Class A result. The gate owner inspects whether an existing destination preserves the exact requested scope & stops after diagnostics; if none does, the smallest interface change adds one. This contract names no flag.

The route must preserve the selected workspace, packages, feature sets, targets, profile & lint policy; run Mac & Dell through the broker & Linux direct; keep the aggregate **FAILED** when any requested unit fails while collecting every feasible independent diagnostic (Cargo `--keep-going`, structured messages); run no package, sign, publish or release stage; & stay distinct from full-gate qualification.

**Batching.** `clippyArgs(units)` already takes several packages (`packages/release/deterministic-scans.mjs:188`); the planner at `:882-888` emits one call per crate & lint set. Batch packages that share workspace, feature set, target, profile, lint policy, toolchain & environment into one invocation; keep a separate invocation only for a required incompatible configuration (for example `rightkit-db` SQLCipher variants, `rightkit-qa-driver` wv2 generations, per `scripts/ci/shards.mjs`) & record why. Preserve `--locked` & `--no-deps`. Do not widen a selected package set to `--workspace` unless equivalent. Feature unification can change what compiles: qualify batch output against the per-crate configurations before the per-crate production path is removed. Do not keep per-crate admissions for granular reporting; the structured diagnostics carry package & target. Sidecars: `--to compile` stages declared sidecars before `main --all` (`bin/rightkit-gate.mjs:1500-1512`); run the independent batch first & schedule a dependency-bound crate only after its minimum sidecar prerequisite. The broker's obligation is to admit a batched invocation & attribute diagnostics per package in its receipts.

## 4. Candidate, native artifact, & qualification binding

This is a required evidence relationship, not a proposed new cryptographic protocol. Use existing authenticated storage/admission where adequate. Record at minimum:

1. Origin repository, commit SHA, & the snapshot directory's content digest (equal to the commit's tree), lockfiles, manifests/build configuration, gate/check policy & command identity; host/target/architecture/toolchain; installed gate/broker versions; entry & stage; command result. A snapshot whose content differs from the commit's tree at start or end refuses the stage; the state of the primary checkout is irrelevant.
2. Local compile output digests & candidate identity, kept separate from final artifact identity.
3. If origin cannot produce a required target, record additional native target-build host, source input, output digest, helper identity/digest, & stage result. If no additional build occurs, carry sealed origin output forward unchanged. Record any allowed assembly/signing transformation; do not count qualification as compilation.
4. Final sealed artifact digest; immutable qualification-policy version/digest pinned before run; required checks & target/runtime/architecture coverage & approved baseline fixed independently of reported results; check IDs/results & expected vs executed coverage tied to exact final bytes. Missing/skipped checks, empty mandatory suite, wrong policy/target fail; policy/coverage changes invalidate affected evidence. Publication promotes unchanged qualified bytes.
5. For RightKit/public CI, preserve existing authenticated GitHub workflow identity & source/stage/digest/run/attempt correlation. For private apps, qualification evidence comes from Mac/Dell, not a newly required GitHub CI path.

An origin candidate and final signed artifact need not have equal hashes. Their relationship must be traceable & verifiable. Qualification of an earlier candidate does not qualify a later sealed artifact. A receipt stored only in the tree it attests is invalid because recording it changes tree identity.
