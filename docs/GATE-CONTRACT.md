[GC-A14] 2026-11-02: **Every gate run checks every crate for all three OS targets.**

### Broker interface (the single definition; the broker contract references it)

Agreed with the RR chat (Fable, rustright session fdd027b9) on 2026-10-28. Names below are the contract's field names; the broker contract mirrors them.

**Snapshot root.** [GC-I01] Mac `/Volumes/D/.rightkit-managed/snapshots/<repo-key>`, Dell `D:\.rightkit-managed\snapshots\<repo-key>`, so the broker's volume & disk-floor checks cover it; `repo-key` = `sha256(canonical repository path)[:16]`, the key `checked-trees` uses. The path follows the managed root through root migration (rustright#91). Linux: a durable root named in gate configuration, default `$XDG_STATE_HOME/rightkit/snapshots/<repo-key>` (fallback `~/.local/state/rightkit`). Phase 0 verifies the gate can create & write under the managed root on Mac & Dell; scratch is never the snapshot root because it is disposable. On the declared Linux broker route the root is the answering broker's `<data root>/snapshots`, compared before ownership or sync ([GC-I12]).

**Output directory & cache.** [GC-I02] The gate creates no output directory of its own. The executor's existing build-output directory & cache are used: on Mac & Dell the broker keeps pinning `--target-dir` to the repository's managed generation target (`ws/<repo-key>/g/<gen>/target` or `ws/<repo-key>/g/<gen>/t`: either leaf is the broker's; the gate takes the leaf from the signed `outputDir` and never infers or picks one), `CARGO_HOME`, `sccache` & temp as today; on Linux the gate resolves the output directory before it changes the source location: `cargo metadata --format-version 1 --no-deps` run in the primary checkout with the stage's environment yields `target_directory` (it honors `CARGO_TARGET_DIR` & `.cargo/config.toml` `build.target-dir`), and the gate passes that absolute path as `CARGO_TARGET_DIR` to every Cargo invocation in the snapshot. A repository with several Cargo workspaces (rightkit#1310, Pulse has nine) is never refused for that and never shares one directory: each workspace of the commit resolves its own `target_directory` the same way (`cargoOutputPin`, from the commit's snapshot manifests, mapped to the checkout's counterpart), and the runtime cargo wrapper (`cargo-target-shim.mjs`, installed by `bindUnitCargo` for every unit, dev, test and package stage and by `bindCargoWrapper` for class A and the compile) binds each Cargo call, right-release's and its children's included, to the target directory of the workspace it builds, or refuses it; the package stage binds the workspaces that hold the app's release config. Cargo would otherwise resolve `target/` relative to the snapshot and a relative `build.target-dir` relative to the snapshot's config file, which is a second output directory & a defect under the commit-only build bullet. `CARGO_HOME`, `sccache` & temp directories are inherited as absolute values, never snapshot-relative. Every receipt records the resolved path as `outputDir` (on Mac & Dell the broker's pinned target directory).

**Class A on managed hosts** [GC-I03] runs, for the unit being built, `rightkit-gate check --commit <sha> --full-a --snapshot <dir> --scope <unit or app directory>` (the implemented form of the earlier wording `check --commit <sha> --unit <kind:name> --snapshot <dir>`; `--scope` limits the scans that execute repository code to the dependency closure of the units under that directory, read from the committed manifests, and every file-only scan stays repository-wide; the door passes it for a nested app and for each `--unit` stage, GB-15): only what that build reads (the unit and its dependency closure: typecheck, lint, the tests that start no compiler) plus the repository-wide file-only scans (lockfile, audit, secret scan, workflow and file hygiene), never another unit's typecheck, lint or tests (Adrian, 2026-10-29: "If one package is being built, why the fuck would the whole repo be scanned?"); the whole-repository `--full-a` is CI's, on every push, with the primary checkout as `cwd` (commit lookup & object database) and the snapshot as the checked file root, never `--worktree`. **Class A runs once, before the compile, under the runtime cargo wrapper** (rightkit#1328, Adrian 2026-11-01: "Class A before the compile is the requirement"): the gate installs the wrapper (first on `PATH`, named in `CARGO`, with its per-scan sentinel and ledger; it needs only each workspace's output directory, resolved from the manifests, and compiles nothing) before the full Class A pass of the snapshot, so a Cargo scan that bypasses it fails that pass before any compile starts. The compile pass that follows (`--all` on the same snapshot, started by the door only after its check stage passed) runs class B alone under the same wrapper and repeats no Class A scan; the snapshot's byte check after the compile stays. A run that goes on to package (desktop platforms) then runs the release admission read-only before the compile stage starts (rightkit#1462, ADR-001 section 7): `right-release build --platform <p> --dry-run` runs the rows the build itself runs at its start (config and inputs, host tools, credentials and signing hosts, pin freshness against the registries) and exits non-zero on a finding before any lock, cache, install or child build, so a refusal costs seconds, not a class B; the gate stops there with nothing compiled. Before any Class A row launches, the gate also checks every `packageManager` pnpm pin of the commit against the pnpm on `PATH` (rightkit#1329, #1468): pins under a directory `ci/gate.config.json` lists as `fixtures` are skipped, as every other scan skips them; a pin that differs from the pnpm on `PATH` is probed directly by running `pnpm --version` inside the pinning package's directory, where pnpm's `packageManager` self-switch (or corepack) resolves it, and is admitted only when that prints the pinned version; if the probe fails the gate refuses with `RK_PNPM_VERSION_MISMATCH`, naming both versions and the migration path. On Windows the self-switch is a shell relaunch, which the launch guard never admits, so there the pin must equal the pnpm on `PATH`. This is a gate-owned change: the current `--full-a --commit` path (`bin/rightkit-gate.mjs:1789-1797`) refuses unless the commit is HEAD of a clean checkout and then rewrites itself to `--worktree`, which the editable checkout can never satisfy under the commit-only build. In snapshot mode the gate reads neither the checkout's HEAD nor its status; the file list is `git ls-tree -r <sha>` from the checkout; every scan runs with the snapshot as its working directory; the snapshot's tree id is computed against the checkout's object database with a temporary index (`GIT_INDEX_FILE=<tmp> git --work-tree=<snapshot> add -A` then `write-tree`) and must equal `<sha>^{tree}` before & after the check, or the result is `RK_CHECK_ERROR`. The broker's own `snapshot_tree` verification uses the same method so the two agree. `--worktree` remains for a developer's own run on a dirty tree and never admits a build. Linux runs the same snapshot-aware check direct. The broker runs no gate and no RightKit code (Adrian, 2026-10-29: "nothing rk is needed to build and manage the broker. at all." and "rk uses broker, not the other way around"): Class A, its verdict reuse and the admission check are the gate's, done before the gate calls the broker; the broker admits a compile only on checks that execute nothing (the request names the snapshot carrier and tree bind; the trusted gate entry path and sha256 it once named were retired 2026-11-03, see [GC-T17]). The gate reuses a Class A verdict keyed on: commit tree id; gate entry sha256 & checker tree digest; `classAEnvironmentDigest`; declared-input digest; broker toolchain identity (cargo & rustc digests, toolchain name); `CARGO_HOME` registry state; & the advisory-database state of the day (`~/.cargo/advisory-db` revision) plus the `cargo-deny`, `cargo-audit` & `actionlint` tool digests. The last two items are explicit because `classAEnvironmentDigest` (`bin/rightkit-gate.mjs:468`) covers the gate package including its shipped advisory data, node & pnpm versions, platform/arch, each package's `node_modules/.modules.yaml`, the installed dependency bytes & tool caches under `node_modules`, but not `CARGO_HOME` or the cargo advisory database; the gate itself never caches the live scans (`cargo-deny`, `cargo-audit`, `pnpm-audit`, `pnpm-lockfile`, `advisory-exceptions`, `:1058`), so a reused verdict is valid only while those inputs are unchanged. Reuse covers the deterministic scans only: `pnpm-audit` (`deterministic-scans.mjs:851`) queries the registry's advisory service live and has no local pin, so its answer can change while every key item is identical; `cargo-deny` & `cargo-audit` read the pinned advisory-database commit (`advisory-db.json`, `--no-fetch`) and are covered by the key. Before a reused verdict is accepted, the executor re-runs the live remote scans (`pnpm-audit`, per root) against that commit's snapshot; the reused verdict is green only if they pass, and its receipt names them under `refreshed`. Binding reuse to an upstream freshness signal instead of a re-run is allowed only when the registry exposes one; none is known today.

### Native tool adapters (audit GB-51) [GC-I08]

A declared native build tool runs on a broker host as one snapshot-bound adapter job of its own constrained adapter, never in a direct session and never around the broker. The capability names below are the contract with RustRight: a broker advertises `adapter:<name>` in its capabilities (`rustright doctor --json` `.broker.capabilities`), RustRight registers **exactly** these adapters (`adapters.<name>` in the broker config; the gate's reference registrations are `packages/release/native-adapters.mjs` `NATIVE_ADAPTERS`), and the gate plans a stage that uses the tool only when the capability is advertised (`native-tool-planning.mjs`); a missing capability or an unsupported custom command refuses at planning, naming it, before any stage builds.

| Tool (command) | Adapter id = capability `adapter:<id>` | Grammar the gate sends (the registration) | Pinned executable identity |
|---|---|---|---|
| xcodegen | `rightkit-xcodegen` | `generate [--spec <relpath>] [--project <relpath>] [--quiet] [--use-cache]`; snapshot subcommand `generate` | the registration's digest |
| xcodebuild | `rightkit-xcodebuild` | flags `-project <relpath> -scheme <any> -configuration <id> -destination <any> -sdk <id> -quiet -allowProvisioningUpdates -allowProvisioningDeviceRegistration -testPlan <id> -exportArchive -exportOptionsPlist <relpath>` and the word prefixes `-only-testing:<Target[/Class[/test]]>` and `-skip-testing:<Target[/Class[/test]]>`; positionals: one action (`build`, `build-for-testing`, `test`, `test-without-building`, `archive`) and `NAME=value` build settings (never a path-redirecting or signing setting: `SYMROOT`, `OBJROOT`, `BUILD_DIR`, `CONFIGURATION_BUILD_DIR`, `CODE_SIGN_IDENTITY`, `CODE_SIGN_STYLE`, `OTHER_CODE_SIGN_FLAGS`, `PROVISIONING_PROFILE*`, ...). Shape: `archive` is the only action of its call; `-exportArchive` stands alone (no action, build setting, `-project`, `-scheme`, `-configuration`, `-destination`, `-sdk`, test plan or selection) with its `-exportOptionsPlist`, which belongs to nothing else; a `-testPlan`, `-only-testing:` or `-skip-testing:` needs a test action (`build-for-testing`, `test` or `test-without-building`) | the selected Xcode's, by digest |
| gradle (`gradlew`) | `rightkit-gradle` | flags `--offline --no-daemon --console <id> --stacktrace --quiet -q -p/--project-dir <relpath>`; positionals: task names (`:app:assembleDebug`; never `publish*`, `upload*` or a Release `assemble`/`bundle`/`install` task) | the committed wrapper, its `distributionSha256Sum` pinned in `gradle-wrapper.properties` (a wrapper without it refuses at planning) |
| cmake | `rightkit-cmake` | flags `-S <relpath> -G <any> -A <id> --build --config <id> --target <any> --parallel --install` and the cache entry prefix `-D<NAME>[:TYPE]=<value>` (never `CMAKE_COMMAND`, `CMAKE_MAKE_PROGRAM`, `CMAKE_PROJECT_INCLUDE*`, `CMAKE_MODULE_PATH`, `CMAKE_PREFIX_PATH`, `CMAKE_PROGRAM_PATH`, nor an entry that moves an output: `CMAKE_INSTALL_PREFIX`, `CMAKE_STAGING_PREFIX`, `*_OUTPUT_DIRECTORY`, `EXECUTABLE_OUTPUT_PATH`, `LIBRARY_OUTPUT_PATH`, `FETCHCONTENT_BASE_DIR`, `CMAKE_*_MODULE_DIRECTORY`). `--build` and `--install` are no-value modes that must be the first argument, take no directory (there is no `-B`: the broker names the one managed build tree) and no configure flag (`-S`, `-G`, `-A`, `-D`); a configure takes no `--config`, `--target` or `--parallel`; `--build` and `--install` are not combined. Pending: RustRight's request policy currently refuses `--config`; the gate's registration lists it, but it is not accepted at the broker until RR-NATIVE lands the fix, so a stage must not rely on it | the registration's digest |

For every adapter: committed cwd (the snapshot counterpart of the step's directory); path values relative to it (the gate rewrites an absolute path it generated under the step's directory to a relative one, and refuses one outside); **one persistent output root owned by the broker**: a caller never names where the build writes (`-derivedDataPath`, `-resultBundlePath`, `-resultStreamPath`, `-archivePath`, `-exportPath`, `-clonedSourcePackagesDirPath`, `-packageCachePath`, `--gradle-user-home`, `-g`, `--project-cache-dir`, `--init-script`, `-I`, `--include-build`, `-B`, `--install-prefix`, `--toolchain`, `--preset`, `--workflow`, `--cache-path` are refused with the canonical route named, never stripped), and the receipt's signed `outputDir` is where the product is read (an iOS dev install reads the `.app` from it). The broker rewrites the call into one managed call under its per-tool state directory (`<outputDir>/native/<tool>/<sha256 of the step's snapshot-relative directory>`) and the signed receipt's `executable.managedOutputs` names each written location by role; the gate reads these roles back and requires the same roles, in the same order, at the paths it derives, never guessing a location. Roles by tool: xcodegen `cache` (only with `--use-cache`); xcodebuild `derived-data`, plus `archive` for `archive`, plus `result-bundle` (run-unique, under `results`, named by the job id) for a test action, and `archive` then `export` for `-exportArchive` (which reads the managed archive); gradle `gradle-user-home`, `project-cache`, `build-tree`, `init-script`; cmake `build-tree`, plus `install-tree` for a configure or `--install`; no request environment (`env` is empty for all four); the tools' child processes are attributed to the job by the broker's capability token and reaped on cancellation; no signing material is passed (signing stays in the provisioned identity and session, evidence handed off). **Signing file.** An Android release's one transient signing-properties file is a path-only handoff (`RIGHTKIT_ANDROID_SIGNING_PROPERTIES`, `SIGNING_FILE_ENV` in `adapter-env.mjs`) that no broker adapter can carry: every adapter's environment is empty, no RustRight broker advertises the typed `native-signing-file-v1` capability, and the release `assemble`/`bundle` task itself is refused by the Gradle grammar. On a broker route the gate therefore refuses a signing-file handoff before launch with `RK_NATIVE_SIGNING_FILE_UNSUPPORTED`, sends nothing and never forwards the path in an argument or an environment (a direct Linux host has no broker and is unaffected). The signed Android release phase is OPEN (Adrian decision 6, bogusyogi/rustright#200); this refusal records that state and is not a decision. **Native client.** A native tool is launched through the resolved RustRight client of the host: `executor.client` (the declared Linux broker client) or else `managedRuntimeClient` (the live runtime at its final RustRight path, the control root's, or the pre-cutover link on a Mac or Dell). It is never found by a PATH lookup, and a host with neither refuses with `RK_NATIVE_CLIENT_UNRESOLVED` before anything is sent. The package-recipe helpers (`recipe-build.mjs`, `create-mac-updater.mjs`) are the package's own release operations, run in the gate's session at their exact installed paths, and route every build-capable child through these adapters (audit GB-06). Tested only through the fixture broker, which is to be deleted under BROKER-CONTRACT GB-82 (it still exists in the gate's tests: `bin/rightkit-gate.mjs` fixture seam, `door-route.test.mjs`, `snapshot-request.test.mjs`): each stage that changes still needs its real-host witness, and an unsupported host is not presented as a tested success.

**`cargo ndk` (audit GB-62).** [GC-I09] `cargo ndk` is a pinned **external** tool, not an adapter and not a free Cargo subcommand: RustRight registers it as an `externalCommands` entry (shim `cargo`, command `ndk`, a `toolId` and the tool's `digest`; policy BUILD, so it runs snapshot-bound and carried, with `--locked` after the inner Cargo subcommand). The broker advertises it as capability `external:cargo-ndk`. A stage that builds JNI libraries (`development.targets.android.ndk` for a dev or test run, `targets.android.ndk` for a package or release) is planned only when that capability is advertised (`native-tool-planning.mjs`); otherwise it refuses at planning, before Class A or any build, naming `external:cargo-ndk`. The declared block must be one RustRight's ndk grammar accepts: ABIs `arm64-v8a` and `x86_64` only (`armeabi-v7a` and `x86` refuse naming the ABI), and `ndk.jniLibs` is the controlled generated output (a directory called `jniLibs` inside the app, emptied before every build, bound as the run's output ledger): a commit that holds a file under it refuses.

**QA journeys on a snapshot stage (audit GB-79, capability `journeys-prebuilt-input`).** [GC-I10] **Superseded by [GC-A07] (2026-11-02):** journeys run after the build against the installed dev copy, never inside a build stage, and nothing is built for them. The gate asks QA what it would build (`journeys run ... --print-build-plan`), carries that build once (one signed, ledgered broker request), has QA name the executable each declared role resolves to in the carried listing (`--print-build-plan --from-cargo-json <listing>`; each must lie in the receipt's verified output directory), signs every product (a role whose marker is required) with the product's one identity outside the broker, writes the attestation (`rightkit.journeys.prebuilt-input/1`: the broker request id and the request digest the receipt was verified against, the listing's sha256, the carried command, the sha256 of every executable QA will launch) and runs QA directly with `--from-cargo-json <listing> --prebuilt-attestation <file>` and the signing evidence in its environment (`packages/release/qa-journeys-prebuilt.mjs`; QA side `crates/rightkit-qa/src/journeys/prebuilt.rs`). QA re-verifies and refuses a changed listing, a build other than the manifest's declared one, a changed or unattested artifact, a product with no signing record or whose signed copy no longer matches its `sha256After`, an empty listing and an unattested document; a product is launched only as the signed copy. A step may not name its own listing, attestation or plan flag; a `rightkit-qa` that does not advertise the capability (`journeys run --help`) fails the suite at planning, naming it, before any suite runs.

### Linux direct origin trust & private Linux qualifier (audit GB-29: OPEN; proposed implementation, acceptance NOT RUN, activation held)

The two items "Direct Linux origin trust & existing admission" and "Private Linux qualification environment" are **OPEN** in the bound contract text f9c1d1b14: no design choice below is decided. [GC-L01] to [GC-L03] record a proposed implementation for owner review, with acceptance NOT RUN and activation held. The proposal keeps the current admission guards, adds no custom signature scheme, no self-admission path and no CI-only substitute for the origin compile, and leaves native Mac/Windows builds unchanged; it asserts no Linux broker requirement either way (see [GC-T04]). The reserved decision (publication authorization, [GC-T22]) is unchanged.

**Direct-origin trust (OPEN; proposed, not decided).** [GC-L01] Proposed: a Linux origin runs the gate direct and its compile and package stages leave **direct-origin records** (`packages/release/direct-origin.mjs`, schema `rightkit.direct-origin/1`): the gate's own evidence (commit, the snapshot tree at stage start and at exit, the command identity, the output digest), taken only after the snapshot stage guard confirmed the snapshot was the commit's bytes. A direct record never carries, and is refused if it carries, a field of a broker's signed receipt (`verdict`, `refreshed`, `provenance`, `signature`, `payload`, `jobId`, `requestId`, `brokerVersion`, `nonce`, ...): there is no fabricated broker receipt. It is a **claim, never authority**: the hosted side recomputes from the dispatched commit alone the real git tree, the unit and its version, the registry and the unit's content digest (npm: the pack content digest; a crate: its archive digest) and runs its own full gate, and admits only a record whose every bound field equals ITS value. What it cannot recompute (that a local compile ran) is recorded as the origin's claim and grants nothing. The candidate identity (repository, commit, tree, unit, version, registry and the exact bytes) is what dispatch and publication join or reject on: the same identity and bytes JOIN the existing claim, different bytes under one dispatch key are REJECTED, never replaced ([GC-T21]). Refused by name: a broker executor or a Mac or Windows (`darwin`, `win32`) direct record (those hosts always run through their broker), another repository, commit, tree, unit, version, registry or content digest, a stage whose snapshot tree changed, a package output that is not the record's artifact, and a record whose candidate identity is not the one its own fields give (`direct-origin.test.mjs`). A direct Linux unit run writes this record into its qualification (`directOrigin`, with no broker receipts) and verifies it locally exactly as the hosted side will; its scratch is the gate's own XDG state directory, never a Mac volume.

**Private Linux qualifier (OPEN; proposed, not decided).** [GC-L02] Proposed: only where the product manifest **declares** a Linux target (`targets.linux`, one object or a list of `{ arch: x86_64|aarch64, libc?: glibc|musl }`; never inferred from another target) are there a Linux artifact and a Linux qualification at all (`packages/release/linux-qualifier.mjs`); with none declared nothing is created (`NOT_APPLICABLE`). The exact sealed Linux bytes from the Linux origin are qualified, unchanged and never rebuilt, in a **compatible** Linux runtime (Linux, the same architecture, the same libc when the target names one, available now) hosted by the Mac or the Dell (the Dell first, then the Mac, so the choice is stable); private Linux acquires no GitHub CI path. With no compatible runtime the candidate is **pending (WAITING)**: the pending record keeps the candidate identity, the exact sealed digest, the target and the policy digest pinned before the run, and discards nothing. It resumes only on evidence that binds the same candidate, the same sealed bytes, a Mac or Dell host with a compatible runtime, the pinned policy digest, no rebuild and every expected check executed once with a pass; an empty mandatory suite, a missing, skipped or failed check, an unexpected check or a changed policy refuses and leaves the record WAITING (E4).

**Activation (held).** [GC-L03] Neither model is accepted or verified (acceptance NOT RUN); the publication-side step below is proposed, not decided. Admitting a direct-origin qualification at publication means widening the committed publish workflow's `admission` input beyond `broker` (and `publish-admission.mjs`'s one accepted mode), which is the reserved publication authorization ([GC-T22], retired hosted self-admission, 2026-10-27): until that input exists, `--to release` from a direct Linux origin writes and verifies the direct-origin qualification and then stops with `RK_DIRECT_RELEASE_HELD`, dispatching nothing; `--to qualify` is proposed behavior, not verified. The current admission guards stay as they are ([GC-T17], [GC-A05]).

### Clippy route & batching [GC-I11] (gate-owned; carried from the broker contract's former Clippy decision, now BROKER-CONTRACT §5 and B4 to B6)

The diagnostic route is a gate-owned destination for a request such as `cargo clippy --workspace --all-targets -- -D warnings`. **Batching.** `clippyArgs(units)` already takes several packages (`packages/release/deterministic-scans.mjs:188`); the planner at `:882-888` emits one call per crate & lint set. ## 4. Candidate, native artifact, & qualification binding

This is a required evidence relationship, not a proposed new cryptographic protocol. Use existing authenticated storage/admission where adequate. Record at minimum:

1. [GC-Q01] Origin repository, commit SHA, & the snapshot directory's content digest (equal to the commit's tree), lockfiles, manifests/build configuration, gate/check policy & command identity; host/target/architecture/toolchain; installed gate/broker versions; entry & stage; command result. A snapshot whose content differs from the commit's tree at start or end refuses the stage; the state of the primary checkout is irrelevant.
2. [GC-Q02] Local compile output digests & candidate identity, kept separate from final artifact identity.
3. [GC-Q03] If origin cannot produce a required target, record additional native target-build host, source input, output digest, helper identity/digest, & stage result. If no additional build occurs, carry sealed origin output forward unchanged. Record any allowed assembly/signing transformation; do not count qualification as compilation.
4. [GC-Q04] Final sealed artifact digest; immutable qualification-policy version/digest pinned before run; required checks & target/runtime/architecture coverage & approved baseline fixed independently of reported results; check IDs/results & expected vs executed coverage tied to exact final bytes. Missing/skipped checks, empty mandatory suite, wrong policy/target fail; policy/coverage changes invalidate affected evidence. Publication promotes unchanged qualified bytes.
5. [GC-Q05] For RightKit/public CI, preserve existing authenticated GitHub workflow identity & source/stage/digest/run/attempt correlation. For private apps, qualification evidence comes from Mac/Dell, not a newly required GitHub CI path.

An origin candidate and final signed artifact need not have equal hashes. Their relationship must be traceable & verifiable. Qualification of an earlier candidate does not qualify a later sealed artifact. A receipt stored only in the tree it attests is invalid because recording it changes tree identity.
