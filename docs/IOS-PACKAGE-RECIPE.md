# iOS package recipe

Tracking: bogusyogi/rightkit#349 (one shared right-release recipe for every iOS app; follow-up of #345). Settled decisions that
apply: #771 D4 (no credential sits in a file) and D3 (no branches, worktrees or PRs).

One declarative `targets.ios.iosPackage` replaces the per-app iOS scripts (HeardRight `appstore-archive.sh`,
`testflight-distribute.py`, `device-smoke.sh`, ScrapeRight `run-e2e.sh`, CodeRight `xcodebuild-managed.sh`). The shape follows
macPackage (strict keys, receipts, fail closed, delete the artifact on failure) and the Android lane (a separate `upload`
command, dry run by default).

| Step | Command | Config |
| --- | --- | --- |
| Build | `right-release build --platform ios` | `targets.ios` (below) |
| Upload | `right-release upload --platform ios --release <sealed-id> [--apply]` | `targets.ios.distribution`, else top-level `distribution` (below) |
| One-time credentials | `right-release ios-credentials store --key-id <KEYID> --issuer <uuid>` (key on stdin) | none |
| Dev install | `right-release dev --platform ios [--serial <device id>]` | `development.targets.ios` (below) |

`build` never uploads; `upload` never builds. There is no App Store submission in v1: the upload reaches TestFlight only.

## Required `.gitignore`

The recipe writes receipts, the build-number counter and markers under `.right-release/`, and the clean-tree check of the next build fails if they show up as untracked files. Every iOS app repository must ignore:

```gitignore
.right-release/
ios/*.xcodeproj/        # generated by xcodegen when projectSpec is used (adjust to your project path)
build/ios/              # the archive and export directories named by iosPackage.archive and iosPackage.ipa
```

## Host rules

- Archive, export, upload, the Keychain commands and the dev install are macOS only (Xcode, the login Keychain, `devicectl`).
  On Windows and Linux only config validation and `--dry-run` run; anything else fails before it touches a file.
- Archive, export and a device build run in the GUI (Aqua) signing session: automatic signing needs the unlocked login keychain.
  An SSH or other non-Aqua session is refused with `IOS_GUI_SESSION_REQUIRED` (the signing agent protocol has no xcodebuild
  request, so there is nothing to route to; run from the logged-in desktop session).
- DerivedData and the result bundle come from `rightkit storage xcode-args --run-root $RIGHTKIT_RUN_ROOT` (run the command under
  `rightkit storage run --app <app> --`). Without a managed run the fallback is `.right-release/ios/DerivedData`, never an
  in-repo build folder.

## `targets.ios`

```js
targets: {
  ios: {

    signingContract: "ios-xcodebuild-archive-automatic-v1",   // optional; this is the only value
    iosPackage: {
      project: "ios/Pulse.xcodeproj",            // required
      projectSpec: "ios/project.yml",            // optional, same directory as project. When named, xcodegen is REQUIRED
      scheme: "Pulse",                           // required
      configuration: "Release",                  // default; a Debug configuration is refused
      teamId: "6KLGD3LLKF",                      // required, no built-in default
      bundleId: "dev.orthic.pulse.ios",          // required; a .dev/.qa/.test/.debug id is refused
      exportMethod: "app-store-connect",         // the only value
      signing: "automatic",                      // the only value; -allowProvisioningUpdates
      buildNumber: "date",                       // the only value: YYYYMMDDNN. The marketing version stays as the app sets it
      extraBuildSettings: { MY_ENDPOINT: "https://example.test" },   // non-secret; secret-looking names/values and signing settings refused
      prepare: [{ cmd: "scripts/build-core.sh", args: [], cwd: "ios" }],   // argv, no shell
      packageResolved: "Package.resolved",       // optional, only with a trust list: a COMMITTED Package.resolved outside the xcodeproj (see Trusted Swift macros and plugins)
      trustedSwiftMacros: [{ package: "swift-composable-architecture", revision: "<40-hex commit>" }],   // optional, reviewed allowlist
      trustedSwiftPlugins: [],                   // optional, same shape and rules, for build-tool plugins
      cleanup: { derivedData: true },
      checks: {
        forbidStrings: ["QA_CONTROL"],           // fail if any string is in the archived or shipped app
        plist: { ITSAppUsesNonExemptEncryption: false },   // expected Info.plist values
        // versionIdentity is always on and cannot be switched off
      },
      archive: "build/ios/Pulse.xcarchive",      // required
      ipa: "build/ios/export/Pulse.ipa",         // required
      timeoutMs: 3600000,
    },
    artifacts: ["build/ios/export/Pulse.ipa"],   // must list iosPackage.ipa (seals the IPA)
  },
},
// An app that also ships desktop puts this under targets.ios.distribution instead (it wins over the top level).
distribution: {
  provider: "app-store-connect",
  appId: "1234567890",                           // optional: omit it and --apply looks it up from bundleId (exactly one exact match)
  bundleId: "dev.orthic.pulse.ios",              // must equal iosPackage.bundleId
  track: "testflight",                           // the only track
  groups: "all",                                 // REQUIRED, no default: "all" or ["Internal Dogfood"] (the recipe has no policy of its own)
  submitExternalBetaReview: true,                // optional, default false; HeardRight sets true explicitly (see Upload)
  waitTimeoutSeconds: 1800, pollIntervalSeconds: 20,
  credentials: { keyService: "rightkit-asc-api-key", keyIdService: "rightkit-asc-key-id", issuerService: "rightkit-asc-issuer-id" },   // optional: Keychain service NAMES
},
```

Unknown keys are errors at every level. A hand-written `prePackage`, `package`, `sign`, `notarize` or `gradle` on `targets.ios`
is refused. HeardRight's model and worker variables, its ASC app id and the stale `tauri-app-next` PATH stay app side: pass
non-secret values through `extraBuildSettings` or `prepare`.

## Trusted Swift macros and plugins

Xcode refuses a Swift macro (or build-tool plugin) a user has not enabled: `Macro "X" from package "Y" must be enabled before it can be used`. Macros run arbitrary code at build time, so the recipe never passes a blanket `-skipMacroValidation`. An app that needs it lists the reviewed packages instead:

- `trustedSwiftMacros` / `trustedSwiftPlugins`: arrays of `{ package, revision }`. `package` is the lowercase SwiftPM identity (`swift-composable-architecture`); `revision` is the exact 40 character lowercase hex git commit (no tag, branch or short hash). No duplicates and no other keys. Both are optional and default to empty; with neither, nothing below applies and the archive command is unchanged.
- The pins come from `Package.resolved` (format version 2 or 3; others are refused). Default: `<project>.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, which must be tracked. When `projectSpec` is set the xcodeproj is regenerated and that file is untracked, so `packageResolved` is REQUIRED: an app-relative path to a committed `Package.resolved` outside the xcodeproj. `packageResolved` without a list is refused.
- The file is a required, hashed release input (`buildInputs.required`, on both the native iOS and the src-tauri iOS paths), so an untracked or modified copy blocks the release as dirty. The recipe also checks `git ls-files` and `git diff HEAD` on it before anything else runs.
- Before `xcodegen` the recipe checks that every listed package is pinned to exactly its listed revision. A missing package, a revision-less pin, or another revision is `IOS_PACKAGE_TRUST_MISMATCH` naming each package and both revisions. A missing, untracked, modified, unparseable or unsupported-version file is `IOS_PACKAGE_TRUST_FAILED`.
- After `generate` and `prepare`, an external `packageResolved` is copied into the xcodeproj's swiftpm location. A different file already there is refused, never overwritten. The file Xcode will read is re-hashed before the archive and again after it; any difference fails the run.
- Only then does the archive add `-skipMacroValidation` (macro list), `-skipPackagePluginValidation` (plugin list, same rules, never added from the macro list), plus `-disableAutomaticPackageResolution` and `-onlyUsePackageVersionsFromResolvedFile` so Xcode cannot move a pin after the check. The export step needs none of them (it compiles nothing).
- The receipt gains `swiftTrust: { packageResolved: { path, sha256 }, macros: [{ package, revision, location }], plugins: [...] }`; it is absent when no list is set.

Limit to know when approving a list: the Xcode skip flags are build-wide, not per package. The check proves the listed packages are at their reviewed revisions; any other package in `Package.resolved` is covered only by that file being committed, hashed and unchanged since review, so review every `Package.resolved` change in the commit that makes it. To update a package, re-review it, then change its revision here in the same commit as `Package.resolved`.

Flag sources (no Apple man page text was reachable from the Windows host; confirm with `xcodebuild -help` on the Mac): `-skipMacroValidation` and `-skipPackagePluginValidation` per the Swift Forums thread "Is there a way to programmatically allow (trust) the compiler plugin to run from the command line?" and Bitrise's "SwiftLintPlugin must be enabled before it can be used" article; `-disableAutomaticPackageResolution` and `-onlyUsePackageVersionsFromResolvedFile` per Apple Developer Forums thread 718178 (the flags used together on a CI `xcodebuild`).

## Build steps

1. **preflight**: macOS, GUI signing session, `xcodebuild -version`; `xcodegen --version` when `projectSpec` is set. Nothing is written before this passes.
2. **generate**: `xcodegen generate --spec <projectSpec> --project <dir>` when `projectSpec` is set. A missing xcodegen is `IOS_PACKAGE_TOOL_MISSING`; a committed xcodeproj is never used instead.
3. **prepare**: the app's own argv commands. With a trust list the Package.resolved check runs before step 2, and the pins file is installed after this step (see Trusted Swift macros and plugins).
4. **archive**: `xcodebuild -project ... -scheme ... -configuration Release -destination generic/platform=iOS -archivePath ... -derivedDataPath ... DEVELOPMENT_TEAM=<teamId> CURRENT_PROJECT_VERSION=<YYYYMMDDNN> -allowProvisioningUpdates [trust flags] archive`. No App Store Connect key is passed: signing uses the Xcode account of the GUI session. The build number counter (UTC day, then 01 to 99) is one file per bundle id in the vault state root (`$RIGHT_RELEASE_VAULT_STATE_ROOT/ios-build-numbers/`, set by `right-release build`), not in the app root, and it fails closed: only a missing file is the first build; an unreadable, corrupt, malformed or future-dated counter, or one past 99, stops the build (`IOS_PACKAGE_BUILD_NUMBER`) instead of restarting at 01. It is written to a temporary file in the same directory and renamed over the counter, so a crash never leaves a half-written counter. The `.right-release/` directory still holds receipts and markers and must be git-ignored.
5. **verify-archive**: one `CFBundleShortVersionString` and `CFBundleVersion` across the app, `PlugIns/*.appex`, `Watch/*.app` and the Watch appex plists (no `$(...)`, and the build equals the recipe's, so a literal in an Info.plist is caught), the app bundle id, `checks.plist`, the QA-control and release-switch scan (the same `assertNoQaControlBinaries` the other lanes use), `checks.forbidStrings`, and an unchanged repository HEAD.
6. **export**: writes `ios-export-options.plist` (`method app-store-connect`, `destination export`, `signingStyle automatic`, `teamID`, `stripSwiftSymbols`, `uploadSymbols`, `manageAppVersionAndBuildNumber false` so Xcode keeps the recipe's build number) and runs `xcodebuild -exportArchive ... -allowProvisioningUpdates` into a dedicated subdirectory (`<ipa name>.export` beside the IPA); the single exported `.ipa` is moved to the configured path and the subdirectory is removed, so neither the export nor its cleanup ever touches other files in the IPA's directory.
7. **verify-ipa**: the IPA is unzipped; the version identity is checked again on the shipped bytes; every bundle must pass `codesign --verify --strict`, have no `get-task-allow` and `aps-environment` of `production` when present; every app, `PlugIns/*.appex` and `Watch/*.app` bundle must carry its own `embedded.mobileprovision`, naming the configured team and that bundle's own `<team>.<CFBundleIdentifier>`, with no device list (the receipt records the main app's profile); the scans run again.
8. **receipt**: `.right-release/receipts/ios-archive.json` (or `$RIGHT_RELEASE_STATE_ROOT/ios-archive.json`): schema 1, contract, team, bundle id, marketing version, build number, `file: { name, sha256, sizeBytes }` over the FINAL IPA bytes, ExportOptions and entitlement digests, the profile summary, xcodebuild version and source commit. `iosSealEntry` seals the IPA with role `ipa`; the seal pins the team and bundle id and refuses a receipt for any other IPA.

Any failure after the work starts deletes the archive, the IPA and the receipt, and throws a typed `IosPackageError` (`IOS_PACKAGE_*`).

## Credentials (D4: Keychain only)

The App Store Connect API key (`.p8`), key id and issuer id are read at run time from the macOS login Keychain with
`security find-generic-password -s <service> -a <account> -w`. Defaults: services `rightkit-asc-api-key`, `rightkit-asc-key-id`,
`rightkit-asc-issuer-id`, account `$USER`; `distribution.credentials` renames them.

```sh
# once per Mac, in the logged-in desktop session; the key is read from stdin and never written to disk by right-release
cat AuthKey_ABC123DEFG.p8 | right-release ios-credentials store --key-id ABC123DEFG --issuer 69a6de80-0b1c-47e3-e053-5b8c7c11a4d1
right-release ios-credentials check      # prints the key id, issuer and service names, never the key
```

The key is stored as the single-line base64 of its PKCS#8 DER and sent to `security -i` on stdin (never an argument); the three
items are read back and compared. A key typed at a terminal is refused (it would echo). Delete the downloaded `.p8` afterwards.

Refused: a key path, key id, issuer, inline key or env variable name anywhere in `distribution` or `distribution.credentials`
(`IOS_ASC_CREDENTIAL_SOURCE_REFUSED`); key material in any environment variable on every host (`IOS_ASC_ENV_SECRET_REFUSED`);
the usual ASC variables (`APPLE_API_KEY`, `APPLE_API_KEY_PATH`, `APPLE_API_ISSUER`, `ASC_*`, `HR_IOS_ASC_*`) on managed hosts
(`MANAGED_HOST_ENV_SECRET_REFUSED`), as macOS notarization does. Key material never reaches a log or an error message: command output in errors masks PEM blocks, bearer tokens, bare JWTs and long base64 or hex runs.

Residual risk: the Keychain item is readable by any process running as the same user in the unlocked GUI session (a Keychain access prompt or ACL on the item narrows this; right-release cannot). The key is read only in memory, only in the Aqua session (`upload --apply` checks the session before the read and refuses SSH), and the JWT lifetime is 18 minutes (Apple's limit is 20), renewed one minute before it expires.

## Ownership scan scope

The release-preflight ownership scan of an iOS target covers only the files the app is built from, not the whole repository. The scope is a sorted, de-duplicated list of repository-relative roots:

- the directory holding `iosPackage.projectSpec` (or `iosPackage.project`);
- every local SwiftPM package referenced by `path:` in that XcodeGen `project.yml` `packages:` section, resolved from the spec's directory (remote `url:` packages add nothing);
- `.rightkit`, so the repository exceptions file is still read;
- plus `targets.ios.ownershipScope: string[]`, an optional list of repository-relative directories for prebuilt native inputs the project does not name (for example a Rust FFI crate that is linked as a static library). Absolute paths, `..` escapes, the repository root, and missing directories are refused.

Findings, coverage gaps, and lockfile resolution outside the scope are not inventoried; exceptions whose path is outside it show as stale warnings, never failures. The scan still reads the committed tree of a clean checkout and keeps the commit/tree binding, trust and key-log checks, and catalog/scanner digests. The sealed ownership evidence records `ownershipScope`; `upload --platform ios` re-derives the scope from the current config and fails if it differs from the sealed one before it re-scans with that same scope. Desktop targets and `right-release ownership` keep scanning the whole repository.

## Upload

`right-release upload --platform ios --release <sealed-id>` verifies the sealed release (commit, ownership, signed and hardened
checkpoints, the IPA receipt for the pinned team and bundle id, IPA bytes) and prints the plan. That dry run reads no Keychain
item and sends nothing. `--apply`:

1. **In-process upload, no key file.** The sealed IPA goes through the App Store Connect build-upload resources (ASC API 4.1), signed with the in-memory JWT. First `GET /v1/apps/{id}/buildUploads` is read and filtered to this version and build: a `COMPLETE` upload is finished without sending anything, `PROCESSING` is waited for, `AWAITING_UPLOAD` is resumed (its reservation is re-read; the parts are sent again), `FAILED` is refused with a clear message (choose a new build number), and more than one live upload is ambiguous and refused. Otherwise `POST /v1/buildUploads` (`cfBundleShortVersionString`, `cfBundleVersion`, `platform: IOS`, relationship `app`), `POST /v1/buildUploadFiles` (`assetType: ASSET`, `fileName`, `fileSize`, `uti: com.apple.ipa`, relationship `buildUpload`; the response lists `uploadOperations` with `method`, `url`, `offset`, `length`, `expiration`, `requestHeaders`), one `PUT` of the exact byte range to each pre-signed URL, `PATCH /v1/buildUploadFiles/{id}` (`uploaded: true`, `sourceFileChecksums.file` with `SHA_256`), then `GET /v1/buildUploads/{id}` until `state.state` is `COMPLETE` (`FAILED` stops with Apple's reason). No altool, no Transporter, and no file or temp file ever holds the key (D4).
   - **Retries.** GET, PATCH and the part PUTs are idempotent and are retried (network error, 429, 5xx) up to 5 attempts with exponential backoff capped at 30 s, honouring `Retry-After` (capped at 2 minutes). The two create POSTs are never retried: a lost response is resolved by the next run finding the upload in the list above.
   - **Expiry.** Each operation's `expiration` and the URL's `Expires` timestamp are checked (60 s margin) before every PUT; an expired reservation stops with `IOS_BUILD_UPLOAD_EXPIRED` before a byte is sent and, per Apple, the upload is then started over with a new build number.
   - **Pre-signed URLs and headers.** Only `https` URLs without credentials on `blobstore.apple.com` or a subdomain of it are accepted (`UPLOAD_HOST_SUFFIXES`); the only sample in Apple's upload guide is `store-030.blobstore.apple.com`, and the guide names no complete host list, so a different Apple host fails closed. A `requestHeaders` entry named `Authorization`, `Cookie` or `Proxy-Authorization` (any case), or a value with CR, LF or NUL, is refused. The bearer token is never sent to those URLs, the operations must tile the IPA exactly, and all of this is checked before the first byte.
   - **Only our own record is adopted.** Right after each create POST the build upload id, build upload file id, app id, version, build and the IPA sha256 are journalled (atomic write) in `$RIGHT_RELEASE_VAULT_STATE_ROOT/ios-build-uploads/ios-build-uploads.<appId>.json` (without a vault root: `.right-release/state/ios-build-uploads/`). A record is resumed, waited for or finished ONLY if its id is in that journal for the same IPA sha256 (and, when the API reports `sourceFileChecksums`, a SHA_256 equal to ours). Any other record for that version and build, whether COMPLETE, PROCESSING or AWAITING_UPLOAD, is another binary's (a second Mac, a fresh vault, a manual upload): it is refused with `IOS_BUILD_UPLOAD_FOREIGN`, naming it, and nothing is pushed into it; build again with a new build number. A corrupt journal is an error (`IOS_UPLOAD_JOURNAL_INVALID`), never an empty one.
   - **Streaming.** The IPA is hashed in a stream and each part is read as a byte range (with a size and mtime identity check), never the whole file in memory.
   - Apple's reference, as checked on 2026-10-18: <https://developer.apple.com/documentation/appstoreconnectapi/post-v1-builduploads>, <https://developer.apple.com/documentation/appstoreconnectapi/post-v1-builduploadfiles>, <https://developer.apple.com/documentation/appstoreconnectapi/patch-v1-builduploadfiles-_id_>, <https://developer.apple.com/documentation/appstoreconnectapi/builduploadstate>, uploading overview <https://developer.apple.com/documentation/appstoreconnectapi/uploading-builds-to-app-store-connect> (page not fetchable when checked), and the pre-signed URL rules (`Expires`, resending a failed part, starting over after expiry, the sample host) <https://developer.apple.com/documentation/appstoreconnectapi/uploading-assets-to-app-store-connect>.
2. The TestFlight steps use the in-memory key (ES256 JWT signed in process, reusing `signAppleApiJwtWithKey` from `apple-profile-renew.mjs`): wait until the exact marketing version and build number is `VALID`, assign that build to the selected beta groups (re-read until converged), and, only when an external group is selected and `submitExternalBetaReview` is explicitly `true`, create the TestFlight beta app review submission (HeardRight sets it to `true`; the default is `false`, and `groups` has no default at all). There is no App Store submission.
3. Evidence: `.right-release/receipts/ios-testflight.json`; markers `verified-ios-upload.json` (after the build upload is COMPLETE) and `verified-ios-testflight.json` (after the groups) under `.right-release/state/<release>/ios/`. A rerun after a TestFlight failure does not upload again, but a marker is trusted only when its `ipaSha256`, `appId`, `bundleId`, `marketingVersion` and `buildNumber` equal the current sealed values (`IOS_UPLOAD_MARKER_MISMATCH`; an unreadable marker is `IOS_UPLOAD_MARKER_INVALID`). `--apply` holds a per-release lock (`.right-release/locks/ios-upload-<release>.lock.json`, a pid lock; a stale lock is renamed to a unique tombstone, which only one process can win, before the exclusive create is retried, and a just-created empty lock counts as held for a 5 s grace period), so two applies of one release cannot interleave (`IOS_UPLOAD_LOCKED`), and the Keychain is read only after the GUI-session check. The seal also requires the receipt's `sourceCommit` to equal the release commit.

## `development.targets.ios`

```js
development: { targets: { ios: {
  project: "ios/Pulse.xcodeproj", projectSpec: "ios/project.yml", scheme: "Pulse",
  configuration: "Debug", teamId: "6KLGD3LLKF",                 // teamId required for a device build
  install: { kind: "simulator", device: "iPhone 17 Pro", bundleId: "dev.orthic.pulse.ios", launch: true },   // UDID or exact unique name
  // or
  // install: { kind: "device", device: "<devicectl identifier>", bundleId: "dev.orthic.pulse.ios", launchArgs: ["--onboarding-step", "2"] },
} } }
```

The build commands are generated (a hand-written `build` is refused). A simulator build boots the simulator if needed
(`simctl boot`), `simctl install`, and `simctl launch --terminate-running-process`. A device build adds
`-allowProvisioningUpdates -allowProvisioningDeviceRegistration`, checks the device is ready (HeardRight's readiness rule), then
`devicectl device install app` and `devicectl device process launch --terminate-existing --no-activate`. App arguments (`launchArgs`) are passed after a `--` terminator so an argument such as `--device` can never be read as a `simctl` or `devicectl` option; `extraBuildSettings` values get the same secret-value check as the release lane. The device is named by id
(`install.device`, `--serial` or `RIGHTKIT_IOS_DEVICE`); the only attached device is never assumed. `--dry-run` prints the plan on
any host. A dev build archives and uploads nothing and reads no App Store Connect credential.

## What a live Mac run must prove

Everything above is covered by unit tests with injected dependencies. These need a real Mac with Xcode, the signing account, a
paired device and the ASC key: the exact `xcodebuild` and `xcodegen` flags against real projects, `manageAppVersionAndBuildNumber`,
`security -i` storing the key and `security find-generic-password -w` reading it back, the build-upload sequence against the real service (whether the `sourceFileChecksums.file.hash` is accepted as lowercase hex SHA_256, and the shape of `state.errors` entries; Apple's reference does not spell either out), the App Store Connect responses, `simctl` and `devicectl` output, and the Aqua session check, and that `simctl launch` and `devicectl device process launch` accept the `--` terminator before the app arguments. Fallback if either rejects it: drop the `--` and reject any `launchArgs` entry that starts with `-`.
