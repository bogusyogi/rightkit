# Changelog

## 0.5.3 (unpublished)

rightkit#1180: `relocation_reuses_only_same_configured_key_store_arc` failed once on the hosted `windows-2025` runner (`NotRelocated` or `RelocatedCleanupPending`; the assertion did not print the report), and a second hosted failure with the message `backup operation timeout expired` hit three `tests/restore.rs` tests. The root cause of the relocation failure is not proven: the failing job showed a runner-wide stall (the test binary took 62 s against 29 s in two passing runs), and no log line names a Windows error code. The changes below close the paths listed below that fail, or leave a blocking journal, because of a delay or a transient Windows refusal. Requires rightkit-fs 0.4.8.

- Fix: the whole copy of every online backup this crate makes for its own callers is bounded by a budget of its own, not by `DbOptions::busy_timeout`. `online_backup_to` uses `busy_timeout` (five seconds by default) as the deadline for the entire copy, so a copy that took longer than that to create the staging file, derive the SQLCipher key, copy, sync and verify failed with `backup operation timeout expired` on every OS. Now `replace_database` and `replace_database_locked` (so `restore_database*` and `EncryptedStore::restore`), `EncryptedStore::backup_to`, the pre-migration backup of `migrate` and `open_writer_migrated*`, and `EncryptedStore::relocate` / `RelocationSession::copy` all bound the copy by one shared budget: 120 s plus one second per 4 MiB of the source database and its `-wal`, capped at six hours, and never less than `busy_timeout` (raise it to allow longer). `busy_timeout` keeps one job, how long a busy or locked source is waited for: an uninterrupted spell of busy or locked steps longer than `busy_timeout` fails with `backup busy timeout expired after .. (busy wait ..)`, and the spell starts again after every step that makes progress. A copy that is stuck still fails: a busy source after `busy_timeout`, anything else after the budget, and the message names the elapsed time and the budget (`backup operation timeout expired after 120s (budget 120s)`). The budget is a separate parameter of the internal copy, never stored in `busy_timeout`.
- Unchanged: the public `online_backup_to` keeps its contract (`options.busy_timeout` is the deadline of the whole copy, with or without a progress callback); only its expiry message changed to name the elapsed time and the budget.
- Fix: `restore_from` (and `DbOptions::restore_from`) waited for a busy or locked destination for `busy_timeout` counted from the start of the whole copy, so a busy spell that began a few seconds into a long restore failed at once. The wait now counts from the start of the busy spell and starts again after every step that makes progress, like the backup copy (`busy_wait_left` is the one owner of that rule); a destination that stays busy still fails after `busy_timeout`, and the message now says so (`restore busy timeout expired after .. (busy wait ..)`).
- Hardened: the busy arm of the backup copy no longer returns `check_deadline()` straight out of the copy. If that ever yielded `Ok`, the copy would have skipped the checkpoint, `quick_check` and the publish and reported a backup that was never made. It now returns the deadline error, or an explicit one.
- Fix: a Windows rename-over, delete, open or sharing refusal that clears by itself (`ERROR_ACCESS_DENIED` 5, `ERROR_SHARING_VIOLATION` 32, `ERROR_LOCK_VIOLATION` 33; an indexer or scanner holding a file without delete sharing) is retried at most 20 times, 100 ms apart, through `rightkit_fs::transient` (rightkit-fs 0.4.8, the one owner of that classification and bound; this crate keeps no copy of it), in: every transition journal write and removal (relocation, rotation, restore and recovery); the `FileTransaction` publish steps of a relocation and of its recovery (`TransactionOptions::access_denied_retry`); the cleanup of the candidate file and its workspace after a committed relocation (identity is proven again before each retry); the fsync, the identity read of the staging and the rename that publish an online backup (staging identity is re-checked before each retry); and the opens that compare the relocation's published copy with its candidate. After the bound the original error is returned, so a true permission failure still fails. Off Windows nothing is retried.
- Fix: a root's identity that cannot be read is no longer taken for a changed one, and is never recorded as "no identity". `RootIdentity::capture` retries a transient open failure before it gives up, but it stays infallible, so a root it cannot open still reads as no identity, exactly like a root that is not there; its documentation now says that a journal which a later check compares against must not record it. Every identity a relocation records now comes from `try_capture` (an unreadable root is the error, an absent one is `file: None`) or, for a root that must be there when it is recorded, `capture_present` (absent is an error too): the database, the transaction root, the candidate after the copy was written, and the published copy. Before, such a record could persist `file: None` after one refusal that outlasted the retry bound, and the relocation could never finish: the journal reader refuses a relocation journal whose transaction root or published copy has no file identity, and every identity check read the stored `None` as a changed root (`published destination identity changed`, `recorded committed copy changed`, `old root identity changed before abort`). If the published copy cannot be read right after the FS transaction committed, the publication is not recorded as committed: the phase becomes `fs-recovery-required` and the error is returned, which abort settlement and explicit recovery already resolve (recovery proves the file against the candidate and records its identity then). A workspace directory whose identity cannot be recorded is removed again, because no journal names it yet. The identity checks of relocation (`copy`, `reopen`, `settle`, recovery, `establish_relocation`) separate three results: the same file, a different or missing one (the existing `RecoveryRequired` refusals), and one that cannot be read, which is the underlying `LifecycleError::Fs`. In the cleanup after a committed relocation, an identity that cannot be read keeps the path and says why; nothing is deleted on it. The rotation and restore journals still record `RootIdentity::capture`: nothing reads those identities back.
- Fix: `RelocationSession::copy` records the `publishing` phase in memory only after the journal write succeeded. Before, a failed write left the in-memory phase at `publishing`, so the abort kept the candidate workspace and both journals as an unresolved FS publication although no publication had started, and the next `relocate` refused with `an existing transition requires explicit recovery`.
- Added: a relocation says why it kept a path, without changing any published type. `EncryptedStore::relocation_cleanup_errors()` returns, for the paths the store's most recent `relocate`, session `settle` or relocation recovery left behind, in the order of `cleanup_retained`, the last error that stopped each removal (the OS error text, for example `Access is denied. (os error 5)`) or the check that refused it; `RelocationSession::cleanup_errors()` returns the same for that session. `RelocationReport` and `RelocationSettlementReport` keep exactly the shapes of 0.5.2 (a field added to the struct-like variant or to the all-`pub` struct would break code that destructures them, and that is a minor bump with every dependent of this crate following); `recover_completed_relocation` returns no store, so it has no accessor. The failing assertion of `relocation_reuses_only_same_configured_key_store_arc` prints the accessor's result.
- Not changed: a journal-write failure inside `reopen` after the destination was selected still leaves the store blocked (the write is retried like every other journal write, but a failure after the bound is not undone).
- Tests: `deadline_tests` (the existing ones unchanged, plus a slow copy bounded by its budget with the budget named, a zero busy wait not bounding a copy that is never busy, a busy source failing after the busy wait, progress restarting the busy wait, the budget capping a longer busy wait) and `budget_tests` (budget arithmetic, the size counted, a copy that outlasts the busy wait completing, a source locked by another connection failing after the busy wait, `busy_wait_left` limiting a busy spell and starting again after progress, a `restore_from` into a destination that stays locked) in `src/backup.rs`; a zero `busy_timeout` no longer fails `restore_database` (`a_restore_is_not_bounded_by_the_sqlite_busy_timeout`), `replace_database`, `EncryptedStore::backup_to` (`backup_to_is_not_bounded_by_the_sqlite_busy_timeout`) and the pre-migration backup (each fails on every OS before the fix; `EncryptedStore::restore` has no copy of its own: it calls `restore_database_locked`, so it is the restore case); `core_tests` in `src/encrypted_lifecycle/relocate.rs`, which drive a `RelocationCore` without a store so that a zero `busy_timeout` reaches the copy alone: `the_relocation_copy_is_not_bounded_by_the_sqlite_busy_timeout` (relocation's one copy call, `copy_to`; reverting it to `online_backup_to` fails with `backup operation timeout expired .. (budget 0ns)`), `the_journal_a_relocation_opens_with_is_one_the_reader_accepts`, `a_root_that_is_missing_or_unreadable_is_the_error_and_nothing_is_recorded`, `a_published_copy_that_cannot_be_read_is_not_recorded_as_committed` and `capture_present_reports_what_try_capture_calls_absent` (each of the three identity tests fails when the record site goes back to the infallible `capture`); `a_failed_publishing_record_aborts_cleanly_and_a_retry_can_relocate`; `identity_tests` (changed, missing, unrecorded and unreadable roots; a workspace that cannot be removed is kept with its error); `retained_cleanup_carries_the_error_that_kept_it`; and three Windows-only cases (`tests/relocation_interruption.rs`: a journal and the candidate held open without delete sharing, a root held against reading) that have not run off Windows. The failing assertion keeps its meaning and prints the report, the reasons for any retained path and the elapsed time. The test of `a_passing_backup_check_lets_the_migration_run` no longer widens `busy_timeout` to 60 s: the copy has its own budget.

## 0.5.2 — 2026-10-23

- Fix (rightkit#932, ViewRight): a failed open no longer checkpoints and deletes the `-wal`/`-shm` before quarantine runs. When `open_at` failed (a key check reading page 1, or `check_on_open`), the `?` dropped the connection, and SQLite's close checkpoints and then deletes the `-wal` and `-shm`. Quarantine then found no `-wal`, and a valid-but-corrupt main file had already been rewritten, which broke the "nothing is deleted" promise of `open_writer_recovering`, `open_writer_recovering_unreadable` and `open_writer_migrated_or_degrade`. `open_at` now sets `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE` right after the handle opens (before keying) and clears it only once the check and sidecar hardening have succeeded, so a successful connection closes exactly as before. Every writer path goes through `open_at`. Damage that first surfaces during migration (`open_writer_migrated`, after `open_at` succeeded) sets the flag again before the connection is dropped, so `open_writer_migrated_or_degrade` also quarantines the original bytes.
- Tests: `tests/failed_open_keeps_wal.rs` (garbage main plus `-wal` through `open_writer_migrated_or_degrade` and `open_writer_recovering_unreadable`; a valid WAL store whose last write exists only in the `-wal`, with a corrupt interior page, under `IntegrityCheck::Quick` through `open_writer_recovering`; a WAL-only last write with a corrupt page first seen by a migration (`corruption_first_seen_during_migration_keeps_the_wal_and_the_main_bytes`); and a healthy-store close regression). Not published when written.

## 0.5.1 — 2026-10-20

Additive, behind the new optional feature `encrypted-lifecycle` (PK03-3..6). Nothing here changes the published 0.5.0 API, & rightkit-db still has no edge to rightkit-credentials or rightkit-daemon. Requires rightkit-fs 0.4.6 with `fs`, `lock` & `transaction`; publish fs 0.4.6 before this crate.

- New feature `encrypted-lifecycle`. It must be combined with `sqlcipher` or `sqlcipher-system`; alone it is a `compile_error!` instead of a build where `PRAGMA key` would be a silent no-op. The code is `rightkit_db::encrypted_lifecycle`.
- `ProtectedKeyStore`: the contract db defines for protected key storage, implemented later by an adapter in rightkit-credentials (db never depends on credentials). Methods: `read_primary`, `read_pending` (key plus an opaque `PendingRevision`), `write_pending`, `promote_pending(revision)`, `discard_pending(revision)`, `read_legacy_staging(alias)` / `delete_legacy_staging(alias)` (HeardRight's `SQLCipher/DBKey.staging` is configured as an explicit alias), `read_recovery` / `write_recovery` / `clear_recovery` (the slot that retains the previous key while a rotation is unproven), and `lock_rotation(timeout)` (the store's own rotation lock; default takes none). A read returns `Ok(None)` for an empty slot and `Err` for an unreadable one, so an unreadable slot is never mistaken for an empty one, and there is no plaintext fallback.
- `StoreTransition`: the one cross-process guard for open-time reconciliation, rotation, recovery, restore and relocation, built on the existing store-wide lock (`<db>.store-lock`, `StoreLock`). Cooperating openers hold the shared lock while they have connections open (`EncryptedStore` does); a transition holds the exclusive lock, so it starts only when no cooperating process uses the store. Acquisition is bounded (`TransitionOptions::acquire_timeout`); a busy store is `LifecycleError::Busy` before any file or key changes. The guard is held until the effects settle (every operation is synchronous, so an in-flight backend call is never abandoned); a process death releases the OS lock and leaves the journal. Lock order: guard, then the key store's rotation lock, then the database operation. A relocation takes the guard of both roots (in path order, each bounded).
- The transition journal `<db>.transition-journal` uses v2 for relocation (v1 remains for rotation/restore), recording explicit FS transaction root/id, candidate/publication identities, selection & cleanup authority. It is written atomically and privately beside each guarded root, holds no key material, and records the transition kind, phase, the staged pending revision and the old and new root identities (path plus filesystem file and directory identity). It is never deleted while unreadable. The reserved-name list for `MigrateOptions::backup_name` now also refuses `<db>.transition-journal`.
- `EncryptedStore::open(EncryptedStoreConfig)`: key selection over primary, pending, mapped legacy staging and the recovery slot. A clean store (no journal, the primary key opens the file, no pending key) opens under the shared guard; anything else is reconciled first under the exclusive guard (see `recover_rotation`). Failures are classified in `LifecycleError`: `StoreMissing`, `NotEncrypted`, `KeyMissing`, `KeyStore { slot, source }` (denied, unavailable, corrupt), `NoKeyOpens` (wrong key and damaged file are indistinguishable in SQLCipher), `DatabaseUnavailable { cause }`, `RecoveryRequired`, `Busy`. A missing file is never created unless `create_if_missing` is set and a primary key is stored; a file that no key opens is never created over, quarantined or replaced. The store owns its writer (`with_writer`) and managed read pools (`read_pool` returns `ManagedPool`) so a transition can drain and reopen them.
- `EncryptedStore::rotate_key(RotationRequest) -> RotationReport { Committed | CommittedCleanupPending | NotCommitted | Indeterminate }` over the existing `rekey`. Phases, each journaled before the next effect: guard, old key verified against the file and the stored primary key, old key written to the recovery slot and read back, new key staged as pending and read back, intent journaled, `rekey`, database read back with both keys, caller validation, exact-revision promotion, primary slot read back, final consistency proof from what storage returns, then cleanup. The outcome comes from readback, never from an error value: a `rekey` that returned an error but took effect is committed; a promotion that returned an error but wrote the primary key is committed; a promotion that did not write is a verified noncommit and the database is rolled back to the old key and read back; anything unreadable is `Indeterminate`, which keeps both keys, blocks ordinary writes and is resolved by `recover_rotation`. A cleanup-only failure (pending key, recovery slot, journal) never rolls back a committed rotation. `RotationRequest::retain_previous` keeps the previous key in the recovery slot afterwards, for backups made under it.
- `EncryptedStore::recover_rotation() -> RecoveryReport` and the free `recover_rotation(&EncryptedStoreConfig)` (for a store that cannot be opened). It decides from the real state: it tries every stored key against the file; the key that opens it is made canonical (a pending key is promoted, a legacy staging or recovery key is staged and promoted), leftovers are cleaned up, and nothing is deleted while it is the only key that opens the file. A legacy staging item is deleted only after canonical storage and a reopen readback prove recovery stays possible (`delete_legacy_after_migration`, default on). If no key opens the file or a slot cannot be read, recovery changes nothing and reports why (`RecoveryOutcome::Blocked`). It also finishes an interrupted restore through `recover_interrupted_restore_locked`. A relocation journal is refused with `RecoveryRequired`: only explicit authoritative relocation recovery may settle it.
- `EncryptedStore::backup_to` delegates online backup through its owned writer after checking stored key consistency. `restore` drains owned connections, takes exclusive transition authority, refuses any retained transition journal before mutation, validates replacement with store key & caller validation, then reopens; validation failure rolls restore back.
- `EncryptedStore::prepare_relocation(RelocationPlan) -> Result<RelocationSession, LifecycleError>` exposes `quiesce`, `copy`, `reopen` & `settle(RelocationSettlement::{Committed, Aborted})`. `RelocationPlan::transaction_root` / `with_transaction_root` supplies explicit caller-authorized FS recovery scope. Copy publishes verified encrypted DB through `rightkit-fs::FileTransaction`; caller durably selects destination before reopen & retains session through coordinator Completed before committed settlement. Old DB remains intact; existing destination & wrong destination key are refused. Committed publication with retained cleanup returns `RelocationReport::RelocatedCleanupPending` rather than rolling back. `EncryptedStore::relocate` remains standalone convenience; app wraps phased session as opaque daemon participant with no db/daemon dependency edge.
- `recover_relocation_session(config, plan)` resumes durably selected destination while retaining journals & recovery authority until explicit committed settlement; abort is forbidden after destination selection. `recover_relocation(config, plan, settlement)` is terminal standalone recovery under caller's authoritative root decision. `recover_completed_relocation(config, plan)` retries committed cleanup after durable coordinator Completed; it checks both journals under transition locks, returns `None` only when both are absent, & preserves unknown/mismatched authority on error.
- `ManagedPool::close()` permanently revokes every clone. `close_and_wait(Duration) -> Result<(), LifecycleError>` also drains current/retired generations within one timeout budget; timeout retains outstanding reader leases & shared exclusion. Checked-out readers retain exact generation until backend return, including dropped public handles or store owner; lifecycle resume cannot reopen revoked pools. Obtain new pool through `EncryptedStore::read_pool`.
- Source regressions in `tests/relocation_interruption.rs` cover phased interruption/replay, retained journals, completed cleanup retry, restore refusal, permanent pool revocation & reader exclusion through timeout/owner drop. `tests/encrypted_lifecycle.rs` (needs `--features sqlcipher,encrypted-lifecycle` or `sqlcipher-system,encrypted-lifecycle`, in-memory `ProtectedKeyStore`): open selection and every classified failure, primary unavailable, staging unreadable, legacy staging and the recovery slot as the sole viable key, rekey failure, rekey applied with an error, promotion with cleanup failure, promotion without a write and rollback, rollback failure, indeterminate readback, failed validation, interruption (simulated process death) after each of the nine rotation phases followed by a reopen, the guard, another opener holding the store, a pool with active readers, a refusing host, backup and restore, wrong destination key, relocation and collision. `tests/journal_fallback.rs` gains the PK03-2 regression: after a runtime WAL refusal the requested main file and its `-wal`/`-shm`/`-journal` siblings are retained byte for byte and the writer lands on the per-host sibling. No cleanup code was added for that, the retention is deliberate (see 0.5.0).
- The `sqlcipher` and `sqlcipher-system` gate rows for this crate (PK17-4, with `encrypted-lifecycle`) are in `ci/gate.config.json`.
- Tests: the backup total deadline is covered by six deterministic scripted-clock unit cases in `src/backup.rs` (`deadline_tests`); the native e2e backup test uses a 1 KiB fixture. The production deadline (`busy_timeout`, default 5 s) and its checks are unchanged.

## 0.4.3

- Additive: `replace_database(&DbOptions, replacement, &rightkit_fs::LockOptions)` and `replace_database_locked`, an atomic replace of the live database with a validated copy (Orthic-Labs/rightkit#311, PostRight ledger 196). The replacement is opened read-only with the options' key and must pass every `PRAGMA integrity_check` row; it is copied through the backup API (WAL included) into a staging file beside the live database, checked and synced; the live `-wal`, `-shm` and `-journal` are removed so a stale log is never replayed; the staging file is renamed onto the path. A failure before the sidecars are removed leaves the live database untouched.
- Additive: a store-wide advisory lock, `StoreLock::shared` / `StoreLock::exclusive` over `<db>.store-lock` (`store_lock_path`). A daemon and a shell hold a shared guard while they have connections open; `replace_database` takes the exclusive guard, so it runs only when no cooperating process is using the store and waits or fails (`DbError::Fs`, locked or timed out) per `LockOptions`. Cooperative: a process that never takes the shared guard is not excluded. Callers must still close their own connections first (required on Windows).
- The `rightkit-fs` dependency now enables its `lock` feature (libc on unix; no new crate). Not compiled when written.

## 0.4.0 — 2026-10-11

- **Breaking: default features are now empty (`default = []`).** 0.3.x built `bundled` and `statement-cache` by default. Name `features = ["bundled"]` for the bundled SQLite (without it `libsqlite3-sys` links the system library) and `"statement-cache"` for `prepare_cached`. SQLCipher consumers already set `default-features = false` and are unchanged. `rightkit-jobs` (store) now names `bundled` and `statement-cache`.

- Additive: opt-in recovery for a database that cannot be *read*. `DbOptions::open_writer_recovering_unreadable(policy, UnreadablePolicy)` and, with the open step supplied by the caller (the test seam), `open_writer_recovering_via`. `UnreadablePolicy::Fail` (default) returns the new `DbError::Unreadable { path, cause, consecutive_failures, quarantine_after, source }` and never touches the file. `UnreadablePolicy::QuarantineAfter { attempts }` renames the file (with its sidecars, never deleted, never overwritten) and creates a fresh database only after the read failed `attempts` consecutive opens; the count is kept in `<db>.unreadable-opens` and any successful open removes it. Only `UnreadableCause::PermissionDenied` and `UnreadableCause::IoReadFailure` count. `UnreadableCause::StorageUnavailable(StorageProblem)` (disk full, read-only filesystem, device or share not ready, sharing/lock violation, busy or locked, file missing, other) never counts and never quarantines, so a full disk, a dropped mount or a lock cannot replace a healthy database with an empty one. `SQLITE_CANTOPEN` is split by probing the file with a read open (SQLite reports `EACCES` as `CANTOPEN`). New `classify_open_failure`, `unreadable_counter_path`, `RecoveryAction`, `UnreadableRecovery`. The corruption path (`RecoveryPolicy`, `open_writer_recovering`) is unchanged. `DbError::Unreadable` is a new variant of a `#[non_exhaustive]` enum. Tests in `tests/unreadable_recovery.rs`. Not compiled when written.

- Additive: `QuarantineStamp::Seconds` no longer fails when the plain `.corrupt-<secs>` name is taken. The quarantine takes `-1`, `-2`, ... (up to 99 retries) and claims each name with create-new semantics (`rename_exclusive`, or `link` for `MoveMode::HardLinkThenRemove`), so an earlier quarantine is never overwritten. `Millis` and `Custom` still refuse an existing name. Under `SidecarPolicy::RenameSidecars` a name counts as taken when a sidecar name is taken too, and a sidecar that is taken now errors instead of being overwritten. Tests in `tests/quarantine_options.rs`. Not compiled when written.
- `DbOptions::optimize_on_open: bool` (default `true`, so behaviour is unchanged) and `DbOptions::without_optimize_on_open()`. When `false`, writer connections skip `PRAGMA optimize` at open; readers never ran it. The new public field is a breaking change for struct literals written without `..`; use `DbOptions::new(path)` or `..Default::default()`. Not compiled when written.

Breaking:
- `DbError` is `#[non_exhaustive]`. Exhaustive matches need a wildcard arm. Variants added later are not breaking.
- `DbOptions` gained `pub integrity: IntegrityCheck`. Struct literals without `..` no longer compile; use `DbOptions::new(path)` or `..Default::default()`.
- `MigrateOptions` gained `pub legacy_versions: Option<LegacyVersionTable>`. Struct literals without `..` no longer compile.
- `RecoveryPolicy` gained `pub quarantine_stamp: QuarantineStamp` and `pub sidecars: SidecarPolicy`. Struct literals without `..` no longer compile.
- `VersionStorage` gained the `VersionTable { table, version_column, applied_at_column }` variant. Exhaustive matches need a new arm.
- `DbError` gained `InvalidQuarantineSuffix(String)`. Exhaustive matches need a new arm.
- Recovery treats `DbError::Integrity` as unreadable. A caller that sets `integrity_check_on_open` with a recovery policy now quarantines and recreates instead of receiving an error.

Added:
- `VersionStorage::VersionTable { table, version_column, applied_at_column }` stores one row per applied version, in ViewRight's `_migrations(version, applied_at)` shape. The applied version is the highest stored `version_column`, and a rollback deletes the top row. `VersionStorage::version_table(table)` uses the `version` and `applied_at` column names. The existing `VersionStorage::Table { table, key }` is unchanged. The new variant is not named `Table` because a changed `Table` would drop its `key` field.
- `LegacyVersionTable` and `MigrateOptions::import_legacy_versions`. Once, from version 0, the configured storage adopts the highest version in an app's existing version table, so migrations up to it are not re-run. The legacy table is only read. A legacy version above the newest migration is refused with `NewerDatabase`, and nothing is written.
- `IntegrityCheck { Off, Quick, Full }` and `DbOptions::integrity`, default `Off`. `Quick` runs `PRAGMA quick_check`. `Full` runs `integrity_check`, or `cipher_integrity_check` when keyed. `integrity_check_on_open` alone still means `Full`, and `integrity` takes precedence when it is not `Off`.
- `QuarantineStamp` (`Millis` default, `Seconds`, `Custom(fn(SystemTime) -> String)`) and `SidecarPolicy` (`RenameSidecars` default, `DeleteSidecars`). `RecoveryPolicy` gained `quarantine_stamp` and `sidecars`. `quarantine_database_with` takes both.
- `DbError::InvalidQuarantineSuffix`, for an empty custom suffix or one containing a path separator or NUL.
- `ReadPoolOptions` with `new()`, `with_read_only(on)` and `with_reader_cache_kib(kib)`, and `DbOptions::open_read_pool_with(cap, options)`. `open_read_pool(cap)` is unchanged and uses `ReadPoolOptions::new()`.
- `with_read_only(true)`: pooled readers open with `SQLITE_OPEN_READ_ONLY`, so writes fail even if `query_only` is turned off. The database must already exist. The pool never creates it, changes its journal mode, narrows its permissions, or runs `optimize` or `init`. Default off.
- `with_reader_cache_kib(kib)`: each pooled reader gets `PRAGMA cache_size = -kib` (KiB, 1 to 2147483647, checked when the pool opens). It overrides `CacheProfile::LargeWorkingSet` on readers only; writers and `open_reader()` keep the profile size.
- `ReadPool::close()` stops checkout and drops idle readers. A checked-out reader closes when it is returned. A second call does nothing.
- `ReadPool::close_and_wait(timeout)` closes the pool, then waits until every reader is returned, so the database files are released. It returns `DbError::ReadPoolCloseTimeout { outstanding, timeout }` if any are still out.
- `DbError` gained `InvalidReaderCacheSize(u32)`, `ReadPoolClosed`, `ReadPoolCloseTimeout { outstanding, timeout }` and `ReadOnlyNotEffective(String)`.

Changed:
- `DbError::Integrity` is recoverable. `open_writer_recovering` quarantines and recreates for a failed `Quick` or `Full` check, under the same keyed/plain policy as a corrupt file. Callers that set `integrity_check_on_open` with a recovery policy now get quarantine instead of an error.
- Quarantine refuses to overwrite an existing destination. Sidecar move or delete failures are returned instead of ignored, so a stale `-wal` cannot be replayed into the replacement database.
- Every reader verifies `PRAGMA query_only` after setting it and fails to open if it did not stay on. This includes readers from `open_reader()`. Default readers still open read-write at the file level.
- Readers no longer run `PRAGMA optimize`. It can write statistics, and the writer runs it when it opens (`optimize_boundary` remains for apps). `query_only` is set after every other reader setup statement.
- `get()` on a closed pool returns `DbError::ReadPoolClosed`, including a `get` that was waiting for capacity when the pool closed.

- `statement-cache` feature (default on): enables rusqlite's `cache`, so `prepare_cached` works through the re-export. Without it `prepare_cached` did not compile.
- `QuarantineOptions { name, sidecars, move_mode, marker }` and `quarantine_database_opts`. `marker` writes an owner-only JSON recovery marker (`{"schema","original","quarantined","unixMs"}`) before any file moves, and the marker stays after success. `move_mode: MoveMode::{Rename, HardLinkThenRemove}` selects the move; `HardLinkThenRemove` links the destination before removing the original. `quarantine_database` and `quarantine_database_with` are unchanged and use the defaults.
- `DbOptions::secure_delete: Option<bool>` (default `None`) applies `PRAGMA secure_delete` at open. `owner_only = false` is documented as the intended switch when sibling processes read the file.
- Breaking for struct literals of `DbOptions` without `..`: the new `secure_delete` field. Use `DbOptions::new(path)` or `..`.

The new options default to the previous behaviour.
