# Changelog

## 0.4.5 — unpublished staging

- **Fixed: lease guard creation race** (Mac qualification of 5a5892a9). A new lease guard was visible empty before its creator took the OS lock; a contender that locked first left a headerless guard every later take refused as unknown legacy. The guard is now published complete (v2 header) by a strict no-replace publish before the stable inode is locked; the unknown-legacy refusal is kept and no placeholder fallback exists. Deterministic paused-publication contender test in `src/lease.rs`.
- **Added: strict directory publication policies** (CutRight #464 gap 7). `publish_dir_with(src, dest, DirPublishPolicy)` with `DirPublishPolicy { Replace, AbsentOnly, AbsentOrEmpty }` (`#[non_exhaustive]`, default `Replace`). The strict policies never delete or displace anything at `dest`: they publish only through a native atomic no-replace rename (Linux `renameat2(RENAME_NOREPLACE)`, Apple `renamex_np(RENAME_EXCL)`, Windows `MoveFileExW` without replace) and return `FsError::Unavailable` where none exists, with no check-then-rename fallback. `AbsentOnly` refuses any occupied `dest` with `AlreadyExists`; `AbsentOrEmpty` removes an empty real directory with `remove_dir` only, then renames, and refuses a non-empty `dest` with `AlreadyExists`. New `DirPublishMethod::EmptyRemovedThenExclusiveRename`. `publish_dir` is unchanged (`Replace`). Tests: `tests/publish_dir_policy.rs`.
- **Added: opt-in bounded retry of Windows ERROR_ACCESS_DENIED (5) on publish** (ScrapeRight G5, plan D14). Default unchanged (32/33 only). Additive API, no existing struct changed: `AccessDeniedRetry::new(RetryPolicy)` plus `atomic_write_with_access_denied_retry`, `publish_file_with_access_denied_retry` and `AtomicWriter::create_with_access_denied_retry`. Only those entry points honour it; the bound is the wrapped `RetryPolicy` (replacing `retry_sharing_violation` for that call, so 5/32/33 share one budget), the original error 5 is returned unchanged after the bound, and no ACL, attribute or open mode is touched. Windows only (inert elsewhere). `publish_file_first_free`, verified-copy, clone, lease, state and `publish_dir` keep the default. Tests: `access_denied_retry_tests` in `src/atomic.rs` (not compiled or run when written).

## 0.4.4 (2026-10-18)

- Fixed (#778): Windows private-directory creation retries transient parent sharing violations while another creator verifies its new directory. Retained parent handles still deny deletion, reparse points still refuse, and persistent sharing violations return unchanged without creating a child. Lease creation/takeover now share one stable OS lock; live or unknown legacy owners refuse migration. Test-mode roots use one validated, containment-checked owner.
- Additive (feature `fs`): `lease` module (Orthic-Labs/rightkit#478): `Lease::try_acquire(path, &LeaseOptions) -> Acquire { Acquired(Lease), Held(LeaseInfo) }`, `Lease::renew`, `Lease::release` (also on drop), `Lease::peek`, `LeaseInfo::staleness() -> Staleness { Fresh, HolderDead, Expired }`. A pid + heartbeat-TTL lease record in a plain file, created exclusively (`ReplaceMode::NoReplace`) and heartbeated by atomic replace. Stale means the holder pid is confirmed dead (the crate's tri-state probe: `kill(pid, 0)` on Unix, `OpenProcess`/`GetExitCodeProcess` plus a complete process snapshot on Windows; an unknown probe is never dead) or the last heartbeat is older than the holder's TTL (or more than a TTL in the future). A stale record is renamed aside, checked, and replaced; a renewing holder whose record was taken learns it from `FsError::Locked`. Not `FileLock`: it is a record, not an OS lock, and it never sleeps or polls. Local machine only. Not compiled or run when written.
- Additive (feature `fs`): `migrate_dir(from, to) -> Migrated { method: MigrateMethod, source_removed }` and `AppDirs::migrate_dir(from, to)` (Orthic-Labs/rightkit#487). Same volume: one `rename`. Different volumes: `copy_tree` to a hidden sibling `.<name>.rkmigrate-<pid>-<n>`, one rename to `to`, then `from` is removed, so `to` is never visible half-copied; stale siblings of dead processes are swept. `to` must be absent or an empty directory (a populated one is `FsError::AlreadyExists`, nothing written); `from` must be a real directory (symlinks refused); `to` inside `from` refused. Not compiled or run when written.
- Additive (feature `blake3`, new optional dependency `blake3` 1.8): `digest::{Blake3Hasher, blake3_bytes, blake3_reader, blake3_file, blake3_file_with_len, blake3_file_with_progress}` (Orthic-Labs/rightkit#464). Lowercase hex, 64 KiB streaming, `Interrupted` retried; `blake3_file_with_progress` calls `(bytes_hashed, initial_length)` at zero and after each chunk. The `digest` module and `verified` now compile with `digest` or `blake3` (the SHA-256 items stay behind `digest`). `copy_verified_with_digest(src, dest, options, DigestAlgorithm::{Sha256, Blake3}, expected, progress) -> VerifiedDigestCopy { algorithm, digest, bytes }`, and `copy_verified_with_progress` (the SHA-256 `copy_verified` with byte progress; `copy_verified` and `VerifiedCopy` unchanged). A source whose length changed during the copy is refused (`FsError::Corrupt`) even without an expected digest. Tests: `tests/blake3_verified.rs`, `sha256_progress_wrapper_keeps_existing_result_shape` in `tests/owner_verified.rs`. Not compiled or run when written.
- Additive (Orthic-Labs/rightkit#467): `zip::write_zip(dest, &[(name, source_path)])`, `zip::read_zip(path)`, `zip::crc_table()` and `zip::crc32_update(&table, crc, bytes)`, the file-backed deterministic STORED writer (byte-for-byte CutRight's former `cutright-qa/src/zip.rs`: UTF-8 flag, DOS epoch, Unix creator 3.0, mode 0644, no extras or comments or data descriptors; caller order and names kept verbatim) and its format-bound verifier (record bounds, sizes and every CRC checked; truncated or hostile input is `InvalidData`, never a panic). No ZIP64: 65535 or more entries, a name over 65535 bytes, or a size or offset over 4 GiB is `InvalidInput`, checked before the destination is truncated. Feature `zip` is an empty alias: the `zip` module has no feature gate (it already holds `StoredZipWriter` and `crc32`, which are unchanged; `StoredZipWriter` keeps its "made by" 2.0). Tests: `tests/stored_zip.rs`, unit tests in `src/zip.rs`. Not compiled or run when written.
- Fix (Windows): `contain_lenient` and `is_within` now refuse a path through a file used as a directory (Windows reports it as not found), and `is_within` refuses a `..` that follows a not-yet-existing component (Windows collapsed it before the existence check). `create_unique_file` skips a name held by an existing directory (Windows answers `create_new` with access denied, not already exists). The Windows trash record no longer carries an unused `$I` path (`restore` already removes it by name).

## 0.4.2

- **Exclusive publish on a volume without hard links (Orthic-Labs/rightkit#242 item 1).** `rename_exclusive` and `ReplaceMode::NoReplace` fell back to `link` then `unlink` when the exclusive rename was unavailable, and `link` fails on FAT, exFAT and some network shares (`EPERM`, `ENOTSUP`, `EMLINK`, `EINVAL`, `ENOSYS`). That failure now takes a third step on Unix: the destination is claimed with an `O_EXCL` (`create_new`) placeholder and the finished file is renamed over it. Guarantee, stated per platform in the `atomic` module table (new row U5b), `ReplaceMode::NoReplace` and the README: exclusive against every other exclusive publisher, but not atomic for readers (the name holds an empty file between the claim and the rename, a crash there leaves that empty file, and a non-exclusive replace can overwrite the placeholder); a failed rename removes the placeholder and publishes nothing. Linux and Apple keep the atomic exclusive rename; Windows keeps `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` and needs no fallback. New: `rename_exclusive_reporting` and `ExclusiveMethod` (`ExclusiveRename`, `MoveFile`, `LinkThenUnlink`, `PlaceholderThenRename`) say which mechanism ran. New: `publish_file_first_free(from, &candidates, options)` publishes one finished file under the first free name of a candidate list without rewriting it (each name is tried exclusively, a taken name is skipped, the source is synced once, the published path is returned; all taken is `AlreadyExists` for the last, an empty list is `InvalidInput`, any other error stops the search). Seam: `atomic::testing::force_no_hard_links()`. Tests: `tests/atomic_exclusive_nolink.rs` (Unix, feature `testing`), `tests/publish_first_free.rs`. Not run against a FAT or exFAT volume; the volume is simulated. CI-only, not compiled locally.

- **Release-safe test seams (Orthic-Labs/rightkit#242 item 2).** New feature `test-seams` (implied by `testing`, which still refuses to compile in release): `atomic::seams::fail_write_after(bytes, kind)` fails this thread's `AtomicWriter::write_all` and `AtomicWriter::writer()` writes after `bytes` bytes in total (the bytes up to the limit are written first, as a full disk does; the budget is cumulative across writers; a write through `file_mut()` or an `atomic_write_with*` closure's `File` is not seen), and `sync_counts` / `take_sync_counts` / `reset_sync_counts` return `SyncCounts { file_syncs, dir_syncs }`, the file flushes (`durable_sync_with`, the `sync_all` of a checked commit) and directory syncs (Unix directory `fsync`; on Windows the flush of a directory made by `create_parents`) this thread attempted. All per thread, inert until installed, a thread-local read per write and per sync otherwise. New: `AtomicWriter::writer()` and `TempWriter`, the temp file as an `io::Write` that goes through the seam. Tests: `tests/atomic_seams.rs` (needs only `test-seams`, so it runs in a release-profile test run). CI-only, not compiled locally.

- **`AppDirs::config` and legacy app names (Orthic-Labs/rightkit#242 item 3).** `AppDirs` gains `config`: Linux `$XDG_CONFIG_HOME` (else `~/.config`, else next to `data` when neither it nor `HOME` is set, so no new failure); the same folder as `data` on Windows, macOS and Android (they have no separate base); `<root>/config` under a test root or QA override. `data`, `local`, `cache` and `home` are unchanged. `AppId::with_legacy_names(&["LightCraft"])` and `AppDirs::resolve_with_legacy(app, opts, env, exists)`: for each of `data`, `local` and `config` separately, the current name's folder if it exists, else the first legacy name's folder that exists, else the current name (cache never moves; a dev build looks for `<legacy>Dev`; nothing is moved or created; test roots, QA overrides and injected folders ignore legacy names). `AppDirs::resolve` applies it with `Path::is_dir`; `resolve_with` stays pure and ignores legacy names. `AppId` and `AppDirs` are `#[non_exhaustive]`, so the new fields are additive. `create_all` also creates `config`. Tests: unit tests in `src/app_dirs.rs`. CI-only, not compiled locally.

- **`AppDirs::resolve` asks Windows for its base folders (Orthic-Labs/rightkit#197).** The Roaming AppData, Local AppData and Profile bases now come from `SHGetKnownFolderPath` (`FOLDERID_RoamingAppData`, `FOLDERID_LocalAppData`, `FOLDERID_Profile`, `KF_FLAG_DEFAULT`), so a process whose `%APPDATA%`, `%LOCALAPPDATA%` or `%USERPROFILE%` was redirected no longer moves the real folders (the `dirs` crate behaves the same way). The variable is read only when the call fails. The returned buffer is always freed with `CoTaskMemFree`. The calls are hand-declared in `app_dirs.rs` like the crate's other Windows calls; no dependency was added. `AppDirs::resolve_with` is unchanged and still reads only the environment it is given, so tests and `for_test` are unaffected. With feature `test-mode`, the real-folder check of a QA override now compares against the real known folders, not a redirected variable. No public item changed. Test: `windows_bases_come_from_known_folders` in `src/app_dirs.rs`. Not compiled locally; CI is the verification.

- **Windows: directories made by a durable `create_parents` write are flushed (Orthic-Labs/rightkit#217).** Each directory the call creates, and then its parent (which holds its link), is opened with `GENERIC_WRITE` and `FILE_FLAG_BACKUP_SEMANTICS` and flushed with `FlushFileBuffers` before the next component, so a crash after the call cannot lose the parent chain the file sits in. Only directories this call creates are flushed (the Unix rule); a failed flush is `FsError::DirSyncFailed` and the directory stays; a parent this call did not create that refuses the write handle with access denied is skipped. `atomic::testing::Step::DirSynced` and `fail_dir_sync` now also cover these flushes on Windows. The calls are hand-declared in `atomic.rs` like the crate's other Windows calls. README, `atomic` module docs (section 3) and `docs/PLATFORM-MATRIX.md` say what is proven (the calls and their order, `tests/atomic_publish.rs` module `windows`) and what is not (that the flush reaches the medium; no power-loss test). CI-only, not compiled locally.

- **`open_replaced`, `read_replaced`, `read_to_string_replaced` (feature `fs`; Orthic-Labs/rightkit#218).** Readers for a file another process replaces. On Windows an open refused with `ERROR_ACCESS_DENIED` (5) or `ERROR_SHARING_VIOLATION` (32) is retried, up to 64 opens with a 1 ms pause growing to 20 ms between them, then the last error is returned unchanged; every other error is returned at once. Pure unit tests cover the classification, the bounded backoff and the loop (`replaced.rs`); `tests/e2e.rs::concurrent_processes_never_expose_a_mixed_file` reads through `read_replaced`. CI-only, not compiled locally.

## 0.4.0

- **Breaking: default features are now empty (`default = []`).** 0.3.x built `fs`, `lock`, `json` and `digest` by default. Name what you use: `fs` (atomic writes, private files, `StateDir`, clone, `FsError`), `lock` (cross-process locks; implies `fs`), `json` (owner records, identity ledger, clonefile binary; implies `lock`), `digest` (SHA-256). `default-features = false` consumers are unaffected; a bare `rightkit-fs = "0.4"` now exposes no modules.

- **Windows owner repair accepts only the token user or an enabled owner-capable group (security fix).** `owner_is_trusted` accepted any enabled, non-deny-only token group as owner, so Everyone, Authenticated Users, BUILTIN\\Users, INTERACTIVE or LOCAL passed; an owner holds implicit WRITE_DAC, so repair left a non-private file and `is_owner_only` could report a false owner-only. Now only the token user, or a group with `SE_GROUP_OWNER` and `SE_GROUP_ENABLED` and not deny-only (in practice Administrators in an elevated token), is accepted, and those five well-known SIDs are refused even if flagged. Unit tests cover each. CI-only, not compiled locally.

Published version number: this release changes or removes public items, so it is a breaking release under Cargo's rules for 0.x versions. It was developed as 0.3.4, which was never published; everything under the 0.3.4 heading below ships in 0.4.0. `FsError` is non-exhaustive and `ReplaceMode::ReplaceFile`, `REPLACEFILE_WRITE_THROUGH` and `FsError::ReplaceInterrupted` are gone, so a 0.3.x number would have broken published crates that depend on `^0.3`.

- **Windows owner repair opens with `READ_CONTROL | WRITE_DAC` and `FILE_SHARE_READ|WRITE|DELETE` (regression fix).** The repair handle used `MAXIMUM_ALLOWED` without delete-share, so `restrict_owner_only` on a file SQLite held open failed with os error 32 (`rightkit-db`, `rightkit-embed` on Windows). The owner-trust rule is unchanged. Test: `restrict_owner_only_succeeds_while_another_handle_holds_the_file_without_delete_share`. CI-only, not compiled locally.

- **`AppendOptions::durable(bool)` builder.** `AppendOptions` is `#[non_exhaustive]`, so code outside the crate (including `tests/owner_append.rs`) cannot use a struct expression (E0639); it sets the flag with this builder. The three Windows `NtCreateFile` declarations (`private.rs`, `state/windows.rs`, `windows_temp_sweep.rs`) now share one signature and `IoStatusBlock` layout, which clears `clashing_extern_declarations` under `-D warnings`. CI-only, not compiled locally.

- **Additive M8 owner-gap primitives (no existing signature changed; `FsError` gains the non-exhaustive variant `DigestMismatch`).** `append_record` / `AppendOptions` (single-write durable append that returns the `SyncLevel`; torn-tail repair stays in the app); `copy_verified` / `VerifiedCopy` (digest feature: copy, hash, compare, re-hash the temp, publish; nothing published on mismatch); `write_private_executable` (0700 on Unix, owner-only DACL on Windows); `AtomicWriter::commit_reporting`, `atomic_write_reporting` and `WriteReport` (achieved flush level and publication durability); `sweep_stale_temps_report` / `SweepReport` (dead, live, unknown and other temps counted apart; Windows counts only removals). Each has a negative test (`tests/owner_*.rs`). Never compiled locally: CI is the verification. Open decisions are in `docs/plans/M8-fs-owner-gap-design.md`.

- **Temp recovery removes only temps of a writer confirmed dead; Windows private storage verifies owner and DACL (completes an abandoned session's uncommitted work; preimage: `private-audits/inventory/owner-fixes/fs-uncommitted-preimage.patch`).**
  - `sweep_stale_temps` and `StateDir::sweep_temps` no longer delete by age. `max_age` is kept for source compatibility and ignored: a temp is removed only when its name is a complete generated temp name, the entry is a regular file (never a symlink), the writer PID is confirmed dead, and the liveness and file identity are rechecked immediately before removal. A live, current, or unqueryable PID survives however old the file is, so PID reuse can retain residue. An old record whose name has the exact generated shape (0.3.4 note below) is now kept unless its PID is dead. Unix cannot make compare-and-`unlinkat` atomic against an arbitrary concurrent path mutator (stated in the docs); the descriptor-opened identity is compared to the name just before removal.
  - `process_alive` now reports `false` only for a confirmed-dead process. Windows: `OpenProcess` failure other than ERROR_INVALID_PARAMETER is unknown, and ERROR_INVALID_PARAMETER is dead only after a complete bounded process snapshot omits the PID; other platforms report unknown (true). Dependents that use it (`rightkit-cache` temp sweep) treat unknown as alive.
  - Windows: both sweeps enumerate with extended directory information (`FILE_ID_EXTD_DIR_INFO`), require a usable full 128-bit file ID (all-zero and all-ones are rejected), reopen the name without reparse traversal and without delete sharing, compare volume and full ID, recheck liveness, and dispose through that same handle. Unsupported identity retains the temp.
  - Windows private files and directories get TokenUser ownership and one protected user-only full-control ACE (SDDL now carries `O:`); creation verifies owner and DACL through the created handle and deletes an unverified new object through that handle; `private::is_owner_only` reads the real owner and DACL (it was an unconditional `true`); repair uses a no-reparse handle opened with `MAXIMUM_ALLOWED` so inherited ACEs are not rewritten into children; a filesystem without `FILE_PERSISTENT_ACLS` is refused. `StateDir` creation verifies the created entry; opening an existing `StateDir` still performs no owner/DACL check. `ensure_private_dir` stops treating an unreadable ancestor as missing.
  - Tests: a zero-age sweep keeps current-process and PID-0 temps and a symlink named like a dead writer's temp (Unix); a killed writer's temp is reclaimed only after the child is reaped; `windows_temp_sweep` replacement-after-enumeration is preserved; Windows `is_owner_only` reads a broad DACL as false.

- **A path taken for a directory is opened only if it is one (second comparative review, 2026-10-12).** The macOS ACL check of a parent directory (`acl::guard_parent_path`, before every private creation), the check of a directory just created, and `sync_dir` opened their argument with a plain open. Given a path that is a regular file (`create_private_new(p.join("child"))` where `p` is a file), they opened and closed that file, which releases every POSIX record lock the process holds on it, before the creation failed. All three now open with `O_DIRECTORY`, so a regular file is refused by the kernel without being opened; the parent check then lets the creation report the failure. 0.3.3 opened no parent for an ACL check; `sync_dir` had the same plain open.
- **Known limit, stated:** any function that READS an existing file opens and closes it (`StateDir::read`, `read_opt`, the digest functions, `FileKey::of_path`, `Fingerprint::of_path`, the clone ladder's source). Do not call one on a file this process holds a POSIX record lock on through another descriptor (a locked database, a `FileLock` path): the close releases that lock. This is how POSIX record locks work and is unchanged from 0.3.3. Also unchanged: a `FileLock` acquisition that fails its ACL check after another process linked an already-held inode to the missing name drops the descriptor before it is parked.

- **An existing file is never opened to read its ACL (regression in the unpublished tree, found by GenRight, 2026-10-12).** On macOS `restrict_owner_only` and `private::is_owner_only` opened the entry, read its ACL through the descriptor and closed it. Closing any descriptor a process holds on a file releases every POSIX record lock that process holds on it. rightkit-db calls `restrict_owner_only` on a database and on its `-wal` and `-shm` files at every open, so SQLite's own locks were dropped while the connection was live: with two processes on one database the WAL index could be rebuilt under a mapping and the engine died with a bus error (`walIndexAppend`), and the database file's own locks were dropped the same way. The same call on a lock file of this crate released the lock. Both functions now read the ACL by path with `acl_get_link_np` (a link at the path is not followed) and open nothing. 0.3.3 opened nothing either (it had no ACL step). Test: `tests/private_keeps_locks.rs` (a second process still finds the lock held). One more hand-declared read-only call: `acl_get_link_np`.

- **A refused lock file is never unlinked (comparative review, 2026-10-12).** `open_lock_file` looked for the name, then opened it with a non-exclusive create, and on macOS removed the file when it carried an ACL `allow` entry. Between the look and the open another process can create and lock that name; unlinking it let a third process lock a new file at the same name while the first still held the old one, so two holders ran at once. The file is now refused (`UnsafeAcl`) and left in place. 0.3.3 never removed a lock file; this restores that.

- **Windows: a reader can be refused for a moment while another process replaces the file. Documented; test fixed.**
  `tests/e2e.rs::concurrent_processes_never_expose_a_mixed_file` failed on the windows-2025 CI leg: the parent's
  `std::fs::read` of the shared file returned access denied (error 5) while three child processes replaced it in a
  loop. The writers use the default mode, which is `std::fs::rename` (`plan_replace_on`, `replace_step`), the same call
  0.3.3 made in `AtomicWriter::commit`, so this is not new with the reduction below. The test asserted more than the
  contract: it now retries a refused open (errors 5 and 32, Windows only, at most 200 tries, no sleep), still asserts
  that no read is truncated or mixed, and prints how many opens were refused. Its first CI run on Windows printed
  0 refused opens in 8,816 and 5,194 reads: it shows that readers are not broken by the writers on that runner, and
  it does not exercise the retry. README and PLATFORM-MATRIX state the
  reader behaviour. No product change: this crate's reads do not retry.

- Tests: no helper process of `tests/e2e.rs` outlives its test. The writer helpers of
  `concurrent_processes_never_expose_a_mixed_file` looped until a stop file appeared, and a test that failed never
  created it; the orphaned helpers kept the test binary's output pipes open and a CI step waiting on those pipes
  hung for 71 minutes on the Windows runner. The helpers are now held by a guard that creates the stop file and kills
  and reaps any that still run when it is dropped, including during a failed assertion, and every helper role ends
  on its own after 60 seconds (the two that sleep until killed slept 120).

**Reduction before the 0.3.4 publication (2026-10-12, `docs/audits/2026-10-11-astra-publication-path-consult.md`).** Five review rounds did not converge: each added platform mechanisms that had never compiled, and the next read found new defects inside them. This release removes those mechanisms and keeps the proven fixes. Nothing removed here was ever published (0.3.3 has none of it), and no new mechanism or platform call was added. Nothing was compiled or run locally; verification is the CI run. This entry supersedes every entry below that describes a removed item.

- **`ReplaceFileW` is gone.** Removed: `ReplaceMode::ReplaceFile`, `ReplaceApi::ReplaceFile`, `atomic::REPLACEFILE_WRITE_THROUGH`, `FsError::ReplaceInterrupted`, `PostPublishStep::OwnerOnlyAcl`, `HardenStage::{DestinationBeforeReplace, DestinationAfterReplace}` (both already inert), `atomic::testing::fail_recovery_move`, the `ReplaceFileW` call, the `.<name>.rktbak-` backup file, the `.<name>.rktnew-` recovery rename and their tests. Why: `ReplaceFileW` can fail after it has removed the destination (error 1176), and moving the new bytes to a protected name *afterwards* cannot cover a crash before that move, so a restart sweep could delete the only copy. Windows publication is `std::fs::rename` (`Rename`), or `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING` (`MoveWriteThrough`, write-through) and without it (`NoReplace`): the calls the crate already made, unchanged. `publication_durability(options, destination_exists)` keeps its signature; no mode's answer depends on `destination_exists` now.
- **No record of synced directories; only what a call creates is synced.** Removed `atomic::published` (the in-process set keyed by device, inode and birth time). A directory inode being durable says nothing about the link a later move created, and the record forgot the sync strength reached. The rule now, in `create_dir_all_durable`, the durable `create_parents` write, `StateDir::create` and `StateDir::child`: a directory's parent link is synced only when this call created it (the create returned `Ok`, not `AlreadyExists`). Directories that already exist are not looked at, so a call whose directories all exist makes no ancestor sync (0.3.3 made none either), and `rightkit-settings` calling `create_dir_all_durable(parent, false)` on every lock acquire and write costs nothing in steady state. **Residual:** a directory created by an earlier call that died before its parent sync, or whose sync failed (`DirSyncFailed`, the directory stays), is not synced by later calls, however it got there (another process, moved into place), and a symlinked component is left alone. This is still strictly more than 0.3.3, which synced no ancestor, but a successful retry after `DirSyncFailed` is not proof of a durable link.
- **ACLs are rejected, never repaired.** Removed `acl::scrub_created`, `scrub_created_path` and `strip` and the ACL-removal path, with the extern declarations `acl_set_fd_np` and `acl_init`. Six read-only externs remain (`acl_get_fd_np`, `acl_free`, `acl_get_entry`, `acl_get_tag_type`, `acl_get_flagset_np`, `acl_get_flag_np`). Removing an ACL from an inode cannot revoke a descriptor already open, so a repair reported success while the exposure stood. One predicate now decides every ACL check: an ACL is unsafe iff it has an `allow` entry (a `deny` entry cannot widen access; an entry whose type cannot be read, or that is not `deny`, counts as `allow`). A parent with an inheritable `allow` entry refuses the creation before it (`UnsafeAcl`); a new entry that carries an `allow` entry anyway is removed while still empty (no byte is written before the check) and refused; `restrict_owner_only` narrows the mode and then refuses an entry with an `allow` entry (it used to strip any ACL); `private::is_owner_only` is false only for an `allow` entry. Deny-only ACLs pass everywhere, as in 0.3.3, including a parent with an inheritable `deny` entry.
- **No native macOS clone of an owner-only source.** `clone_or_link_or_copy_nofollow` no longer calls `clonefile` for a source with no group or other permission bit: a clone takes the source's mode and the destination directory's inheritable ACL, so owner-only cannot be established. It goes on to the hard link, then to the copy, which creates its destination `0600` first. Other sources are cloned as before; `clone_file_nofollow` is unchanged.
- **Windows reserved names: leading spaces.** `reject_reserved_name` also refuses a name that Windows would store as a generated temp name after dropping leading ASCII spaces (` .record.rktmp-123-1-0`), alone or with the trailing-space, trailing-period and `:stream` forms. The leading-space rule is taken from the fifth read's citation of Microsoft's documentation and has not been observed on Windows from this tree.
- Tests removed: `partial_replace_tests::*` and the `plan_tests` ReplaceFile cases, `atomic_publish.rs` recovery and sweep tests and the private `ReplaceFile` Windows test, `atomic_dacl_windows.rs::replace_file_mode_leaves_private_writes_owner_only`, `published_tests::*`, the `ReplaceInterrupted` case in `error.rs`. Rewritten for the created-only rule: the `parents` tests in `atomic_publish.rs`, `state_ancestors.rs`, the child case in `state_durability.rs`, `acl_macos.rs`. Added: a second identical call syncs no ancestor, pre-existing and moved-in directories are not synced, a `Strict` request fails only for a link the call creates, an inheritable `deny` parent is accepted and an inheritable `allow` parent refused (file-only, directory-only and both), `restrict_owner_only` refusing an `allow` entry and accepting a deny-only ACL, the macOS private-source clone case, leading-space name cases.

**Fourth-read fixes (2026-10-11, `docs/audits/2026-10-11-astra-fs-fourth-read.md`).** Nothing here was compiled or run locally; verification is the CI run. Windows code and the macOS ACL calls are marked in the sources as unchecked against the platform headers.

- **Recovery content is never swept (P1 13, and the open half of 1).** An interrupted `ReplaceFileW` (1176/1177) now moves the temp file, which may hold the only copy of the new content, to `.<name>.rktnew-<pid>-<n>-<nanos>` before returning `ReplaceInterrupted`; `new_content` names that file. No sweep (`sweep_stale_temps`, `StateDir::sweep_temps`) matches `.rktnew-`, so neither a living writer's age threshold nor a restart reaches it; the old content stays at the `.rktbak-` backup (or the destination). If the move fails the temp stays and the error message says a sweep may delete it. New seam `atomic::testing::fail_recovery_move`. Tests: `atomic_publish.rs` (sweep at zero age in this process and in a re-executed process).
- **Directory links are published whoever created the directory (P1 3, 4).** The in-process record of *unpublished* directories is gone: it assumed that a directory it had not seen created was already published, so a directory made by another process, a crashed run, or a thread between its `mkdir` and its bookkeeping skipped the sync. It is replaced by a *positive* record (directories whose link this process synced, keyed by `(dev, ino, birth time)`, bounded). `StateDir::create`/`child` and the durable `create_parents` path sync the parent of every directory they walk that the effective user owns and this process has not published, found or made; a failed sync records nothing. Directories owned by others (`/`, `/Users`) are skipped. Cost: one directory sync per owned directory on a path, once per process. New `atomic::create_dir_all_durable(dir, owner_only)`.
- **Settings creates parents durably (P1 4).** `rightkit-settings` no longer calls `create_dir_all` before the write; it sets `create_parents: true`. Its lock file (`backend.rs`) and `atomic_write_with` use `create_dir_all_durable`.
- **Reserved names after Windows normalisation (P2 9).** `reject_reserved_name`, which every name check in the crate funnels through, also tests the name Win32 stores (trailing spaces and periods dropped, `:stream` removed): `create_private_new(".record.rktmp-123-1-0 ")` and the other creation APIs are refused. (`StateDir` already rejected trailing spaces and periods.)
- **macOS ACLs defeat `0600`/`0700` (P1 11).** New `FsError::UnsafeAcl`. Before creating a private file or directory the parent's ACL is read and an inheritable `allow` entry refuses the creation; an ACL the new entry got anyway is removed and read back; `restrict_owner_only` removes ACLs and `is_owner_only` sees them. Sites: atomic temps and `create_parents` directories, `create_private_new`, `ensure_private_dir`, `StateDir` temps, children and ancestors, lock files. `tests/acl_macos.rs`.
- **Copy uses the permissions of the file it read (P1 12).** The byte copy took the source's mode from path metadata captured before the clone and link steps ran, so a source replaced in between was published with the old file's mode. It now reads the mode from the opened handle (and no longer carries the earlier metadata). Test: `clone_fallback.rs::a_source_replaced_between_the_check_and_the_copy_is_copied_with_its_own_permissions`, using the clone-step seam to do the replacement.
- **Lock registry.** New seam `lock::testing::after_identity_check` (between the `lstat` and the `open`) and the deterministic swap test `lock_alias.rs::swap::...` the third read said was missing (finding 2 was closed; its interleaving is now covered).
- **Docs.** `atomic` module docs: a table of every publish path (platform x mode x durable x destination, with the temp-creation table per privacy), the recovery files, and the directory table; `state` module docs: the directory-creation table; `lock` module docs: the registry table. Each row names its test or the seam that stands in for the OS.
- New: `FsError::UnsafeAcl`, `atomic::create_dir_all_durable`, `atomic::testing::fail_recovery_move`, `lock::testing`.
- Behavior changes: `child("kid")` and `StateDir::create` sync the link of an existing owned directory the first time this process sees it (previously never, unless this process had made it); `ReplaceInterrupted::new_content` is now the recovery name, not the temp name; private creation under a macOS parent with an inheritable `allow` ACL entry is `UnsafeAcl`.

- Fix (ViewRight gap): `AtomicWriter::commit_checked` now flushes and file-syncs the temp file before the check runs in EVERY mode, including `durable: false` (previously a non-durable write ran the check on unsynced bytes). The file only is synced (`File::sync_all`; the Apple ladder / `FlushFileBuffers` when `durable`); the directory is still synced only when `durable`. Plain `commit` and `commit_with_digest` are unchanged (a non-durable write still does no sync). Order documented on the method. In the `testing` seam a non-durable checked write now logs `Step::TempFlushed` before the check and never `Step::DirSynced`. Tests in `tests/atomic_checked_sync.rs`. Not compiled when written.

- Additive: `AtomicWriter::commit_checked(check)`. `check(&temp_path)` runs after the temp file's content is written (flushed and synced first when `durable`) and before the replace; an `Err` aborts the write (`FsError::Io` naming the temp path), leaves the destination untouched and removes the temp file. `commit` and `commit_with_digest` are unchanged. Tests in `tests/atomic_checked.rs`. Not compiled when written.

**Third-read fixes (2026-10-11, `docs/audits/2026-10-11-astra-fs-third-read.md`).** Nothing here was compiled or run locally; verification is the CI run.

- **Windows `ReplaceFileW` no longer risks both versions (P1 1).** It is given a unique backup file (`.<name>.rktbak-<pid>-<n>`, not swept). A failure with 1176 or 1177 that leaves the destination missing or a backup beside it is the new `FsError::ReplaceInterrupted { path, new_content, previous_content, source }`; the temp and backup are left for recovery and `target_replaced()` is false. `rightkit-settings` maps unknown variants to `Error::Io` (the `FsError` stays inside it); a typed mapping there is a follow-up.
- **No cross-inode lock alias cache (P1 2).** The registry maps only `(dev, ino)` to held entries; the `lstat identity -> opened identity` map is gone, so a name that was swapped between `lstat` and `open` can no longer make a later request on an unrelated, unchanged inode borrow the other file's guard.
- **Creation retries cannot skip a failed durability barrier (P1 3).** A directory a `StateDir::create` / `child` made is recorded as unpublished until the sync of its parent succeeds; a retry, or a concurrent creator in the same process, that finds it runs that sync (and fails with `DirSyncFailed` if it still fails) before descending or accepting it. In-process only. Behavior change: `child("kid")` retried after a failed sync now syncs again instead of returning.
- **Atomic writes publish the parents they create (P1 4).** With `create_parents` and `durable`, missing ancestors are made top down and the parent of each is synced (`DirSyncFailed` on failure, with the same retry rule). Non-durable writes are unchanged.
- **Private Windows `ReplaceFile` writes use a move (P1 5).** Over an existing destination a `Privacy::OwnerOnly` / `private: true` write plans `MoveFileExW` (`MOVEFILE_REPLACE_EXISTING`, plus write-through when `durable`) instead of `ReplaceFileW`, so the temp file's owner-only DACL is what the published file has; the destination is no longer narrowed or re-checked. `HardenStage::DestinationBeforeReplace/DestinationAfterReplace` and `PostPublishStep::OwnerOnlyAcl` remain but are never produced. `publication_durability` reports `WriteThroughMove` for that case. Cost: like `MoveWriteThrough`, a reader holding the old file open without share-delete can make it fail.
- **No `icacls` fallback (P1 6).** `restrict_owner_only` on Windows fails when the native DACL replacement fails. The fallback only replaced the current user's grant and left other explicit ACEs.
- **`create_private_new` is owner-only from creation on Windows (P1 7)** (`CreateFileW` with the owner-only descriptor), and refuses generated temp names.
- **Unix copy fallback no longer exposes private bytes (P1 8).** The copy step creates its temp `0600` and applies the source's mode before publication (a fresh-metadata copy still uses the default mode). The Linux `FICLONE` step does the same, and its result now carries the source's mode (it previously got the default mode).
- **Reserved names across creation APIs (P2 9).** `create_private_new`, `clone_or_link_or_copy_nofollow[_with]`, macOS `clone_file_nofollow` (`CloneError::InvalidPath`) and lock files refuse a complete generated temp name (`FsError::BadName`).
- New: `FsError::ReplaceInterrupted`.
- Finding 10 (`rightkit-settings/tests/writer.rs`) is in another crate and was not touched.

- Additive: `impl From<FsError> for std::io::Error`. The `io::ErrorKind` is mapped per variant
  (`AlreadyExists` stays `AlreadyExists`, `NotFound` for `UnknownId`, `PermissionDenied` for
  `NotOwned` and `TooPermissive`, `Io`-carrying variants keep their source's kind, and so on), so callers
  need not re-map "already exists" by text. The original `FsError` is the `io::Error`'s inner error
  (`get_ref()` / `into_inner()`), and its `source()` chain is kept. Unit tests in `src/error.rs` cover each
  variant. Not compiled when written.

## 0.3.4

**Review fixes (2026-10-11, `docs/audits/2026-10-11-astra-rightkit-fs-first-read.md`).** The ten findings of the first independent read, and what changed. Nothing here was compiled or run locally; verification is the CI run.

- **BREAKING: `FsError` is `#[non_exhaustive]`.** Match it with a wildcard arm. 0.3.4 already added variants to what 0.3.3 shipped as an exhaustive enum; making it non-exhaustive now means later additions are not breaking. Against the published 0.3.3 this is a breaking change for exhaustive matches (a patch release cannot carry it; this needs the next breaking version when published). New: `FsError::ReplacedButPostStepFailed { path, step: PostPublishStep, source }`, `PostPublishStep::{TempCleanup, OwnerOnlyAcl}` (non-exhaustive), `target_replaced()` is true for it.
- **Linux compiles with `lock`.** `libc::F_WRLCK`/`F_RDLCK` are `c_int` on Linux and `c_short` on Apple; the record-lock type is cast to `c_short` at one place (`lock_type`), with a unit test of the values.
- **POSIX lock exclusion is by file identity.** The registry is keyed by `(dev, ino)` of the opened file. A hard link or case alias of a held lock file no longer gets a second, independent lock (which downgraded the holder's process-wide lock and released both on close). An alias descriptor that cannot be avoided is parked in the entry and closed only at the final release; a pre-open `lstat` answers aliases without opening, so polling an alias parks nothing. `tests/lock_alias.rs`.
- **`StateDir::create` publishes every directory it makes.** Unix syncs the parent of each newly created directory before descending and stops with `FsError::DirSyncFailed` if the sync fails; Windows opens each created directory write-through (no directory flush exists there). `state::testing::take_dir_events()` / `DirEvent` expose the order. `tests/state_ancestors.rs`.
- **Windows `ReplaceFile` no longer passes `REPLACEFILE_WRITE_THROUGH`.** Windows documents the flag as unsupported. `ReplaceFileW` always gets flag word 0 (`REPLACEFILE_WRITE_THROUGH` stays exported and is never used). Over an existing destination a durable `ReplaceFile` write is `FileFlushedOnly`; first creation, `MoveWriteThrough` and `NoReplace` use `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`. New `publication_durability(&options, destination_exists) -> PublicationDurability` (`None`, `FileFlushedOnly`, `DirectoryFlushed`, `WriteThroughMove`, non-exhaustive) says what a call gets. `rightkit-settings` mirrors `ReplaceMode`; its Windows test `configured_replace_mode_and_flags_reach_the_replace_call` expected the old `(ReplaceFile, REPLACEFILE_WRITE_THROUGH)` row and its docs claim write-through for `ReplaceFile`.
- **Windows private writes have no exposure window and fail closed.** The temp file is created with an owner-only security descriptor passed to `CreateFileW` (it was created, then restricted). A private `ReplaceFile` write now fails (nothing published, temp removed) if the destination cannot be narrowed before `ReplaceFileW`, which keeps the destination's ACL; it was best effort. Unix creates the temp `0600`, unchanged. `atomic::testing::on_harden` / `HardenStage` / `HardenCall` inject failures at each step. `tests/atomic_publish.rs`.
- **Published content is never reported as unchanged.** Publication is tracked apart from cleanup and hardening. A hard-link-fallback `unlink` failure, or a failed post-`ReplaceFileW` ACL check, now completes the directory sync and returns `ReplacedButPostStepFailed` (`target_replaced()` true), not a plain `Io`. `rename_exclusive` returns the same for a leftover source name. `atomic::testing::{take_steps, Step, fail_dir_sync, force_link_fallback}` observe and force these.
- **The temp namespace is reserved.** Public writes (`atomic_write*`, `AtomicWriter::create_with`, `rename_exclusive`, `StateDir::write`/`write_new`, `state::validate_name`) refuse a target that is a complete generated temp name (`.<name>.rktmp-<pid>-<n>-<attempt>` or the atomic-write form with a hex nanosecond field), and `sweep_stale_temps` / `StateDir::sweep_temps` delete only complete generated names. A committed record such as `invoice.rktmp-1-final` is no longer deleted by a zero-age sweep. An old record whose name already has the exact generated shape cannot be told from an orphan and is still swept.
- **Concurrent Unix listings are complete.** Each listing opens its own directory description (`openat(dirfd, ".")`); duplicated descriptors shared one offset. Two-thread test in `tests/state_durability.rs`.
- **`StateDir::read(name, u64::MAX)`** returns the content; `max_bytes + 1` overflowed (a panic in debug, an empty read in release).
- **Every integration test names its features** (`required-features` in `Cargo.toml`), so default, `--no-default-features` and each single feature compile; the owner-record assertion in `tests/lock_cross_process.rs` needs `json`.
- **`atomic_dacl_windows.rs`** compares ACLs without the `AI` inheritance-bookkeeping flag (`D:PAI(...)` and `D:P(...)` are the same list).
- **New: `clone_or_link_or_copy_nofollow(src, dst) -> Result<CloneOutcome>`** (`Cloned`, `HardLinked`, `Copied`) and `_with(src, dst, &CloneOptions { allow_hard_link, durable })`. Clone is macOS `clonefile` or Linux `FICLONE`; then a hard link; then a durable `NoReplace` atomic write. Never follows a link at either end, never overwrites (`FsError::Symlink`, `FsError::AlreadyExists`). A hard link shares content with the source; disable it with `allow_hard_link: false` when the copy will be modified. `clone::testing::{override_clone, override_link}` is the step seam. `tests/clone_fallback.rs`.
- **New: `CloneOptions::fresh_metadata(bool)`** (default `false`, unchanged behaviour). `true` makes the destination a fresh file: the clone and hard-link steps are skipped (a clone copies the source's mode and xattrs, a hard link is the source's inode), the byte copy keeps no source permission bits and gets the platform's default mode for a new file (honouring the umask), and the outcome is always `CloneOutcome::Copied`. A read-only source no longer yields a read-only export with this option. Field `CloneOptions::fresh_metadata` is also public; struct literals of `CloneOptions` need `..CloneOptions::default()`. `tests/clone_fallback.rs`.

- **Incremental SHA-256 (feature `digest`).** `digest::Sha256Hasher` (`update`, `finalize` as lowercase hex, `finalize_bytes`, also `io::Write`) on this crate's own `sha2`, equal to `sha256_bytes` of the concatenated input. `AtomicWriter::commit_with_digest` and `atomic_write_with_digest` return the digest of the published bytes, taken from the temp file after the last write and `fsync` (one extra sequential read), so it is correct however the bytes were written.
- **No-replace publish.** `ReplaceMode::NoReplace` and `rename_exclusive(from, to)` fail with `FsError::AlreadyExists` if the target exists, atomically, and remove the loser's temp: Linux `renameat2(RENAME_NOREPLACE)`, Apple `renamex_np(RENAME_EXCL)`, `link` then `unlink` where neither exists (still exclusive; both names exist for an instant), Windows `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING`. The Linux and link-fallback paths are not compiled in this tree's verification (Mac and Windows only).
- **`Privacy` split.** `AtomicWriteOptions::privacy` (`Inherit`, `OwnerOnly`, `OwnerOnlyUnixInheritWindows`); `private: true` still means `OwnerOnly` and wins. Windows ACLs for each are documented on `Privacy` next to the DACL measurements.
- **Write-through and a fault seam.** New `ReplaceMode::MoveWriteThrough` (Windows `MoveFileExW` with `MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH`, existing or missing destination). `ReplaceMode::Rename` stays `std::fs::rename`: a trial that routed it through `MoveFileExW` made writers fail with `ERROR_ACCESS_DENIED` against concurrent readers (`tests/e2e.rs`), because `MoveFileExW` lacks the POSIX replace semantics `std` uses. `ReplaceFile`'s first creation is a write-through `MoveFileExW` when `durable`; over an existing file it is `ReplaceFileW` with no write-through (see the review fixes above: `REPLACEFILE_WRITE_THROUGH` is unsupported and not passed). Per-mode guarantees are in the `ReplaceMode` docs. New feature `testing` (off by default; fails to compile without `debug_assertions`): `atomic::testing::on_replace` installs a per-thread hook that sees each replace call (`ReplaceCall`: API, flag word, temp, target) and may return an error in place of the OS call.
- **`ReplaceMode::ReplaceFile` keeps private writes owner-only on Windows.** Measured on Windows build 10.0.26300.9550 (`tests/atomic_dacl_windows.rs`, DACL read back with `GetNamedSecurityInfoW`): `ReplaceFileW` keeps the destination's DACL, so a private write over a broader destination stayed broad (`D:AI(A;;FR;;;WD)(A;ID;FA;;;<user>)`). A private `ReplaceFile` write now narrows the destination to owner-only before the replace (an error, nothing published, if that fails) and checks it again after (a typed post-publication error if that fails). `ReplaceMode::Rename` already ended owner-only in every case (`D:PAI(A;;FA;;;<user>)`) and is unchanged.
- **Lock owner records carry an RFC 3339 `started` field.** Owner files now write both `started_unix_ms` and `started` (UTC, whole seconds, the form CutRight reads). Reads accept either field, so records from 0.3.3 and earlier still parse, and a record without `label` reads as an empty label. `LockOwner` keeps its fields; the new `LockOwner::started()` returns a `SystemTime`.
- **`LockKind` (`Fcntl` default, `Flock`).** `FileLock::acquire_kind`, `FileLock::acquire_shared_kind` and `FileLock::try_lock_with(path, kind, timeout)` pick the Unix primitive per lock. Default behaviour and `LockOptions` are unchanged. `Flock` uses `flock(2)`, the primitive `std::fs::File::try_lock` uses. Windows takes `LockFileEx` for both kinds, so the kind has no effect there.
- **`probe_owner(path)`.** Reads the owner record without taking the lock. `FileLock::current_owner` now delegates to it.
- **Semantics, documented.** `Fcntl` locks belong to the process and drop when it closes any descriptor for the file. `Flock` locks belong to the open file description, which a forked child inherits until it execs; `Flock` drop unlocks explicitly, so an inherited descriptor cannot keep a released lock busy. Two `Flock` holders in one process exclude each other.
- **Atomic write options.** New `AtomicWriteOptions` (`private`, `create_parents`, `durable`, `replace: ReplaceMode`, `retry_sharing_violation: Option<RetryPolicy>`), used by `atomic_write_with_options` and `AtomicWriter::create_with`. The default is `ReplaceMode::Rename`, which is what every existing call does. `ReplaceMode::ReplaceFile` calls `ReplaceFileW` (flag word 0) on Windows when the destination exists, and renames elsewhere. `RetryPolicy` retries Windows sharing and lock violations (32, 33); it is inert elsewhere. `AtomicOptions` is unchanged, and converts with `From`.
- **Directory sync failures are no longer swallowed.** When the directory `fsync` fails after the replace, `AtomicWriter::commit` and `atomic_write*` return the new `FsError::ReplacedButDirSyncFailed { path, source }`, and `FsError::target_replaced()` is true. Before, the error was discarded and `Ok(())` returned. Callers that matched on `Ok` for a durable write now see this error in that case. `sync_dir` stays best-effort for other callers.
- **Cross-kind exclusion is not guaranteed.** A probe on macOS (Darwin 27) found that a `flock` in one process refused an `fcntl` record lock in another, and the reverse. Callers should still give each lock file one kind for all users.
- **`StateDir` reports directory-sync failures.** Unix `write`, `write_new` and `remove` flushed the directory and discarded the result. A failed directory flush is now `FsError::ReplacedButDirSyncFailed` (writes) or the new `FsError::DirSyncFailed` (removal, and a `child` that creates), and the change is in place when it is returned. `remove` and a creating `child` now flush the directory too (before: neither did). Windows has no directory flush: the old `sync_all` on the list-access handle always failed with `ERROR_ACCESS_DENIED` and was ignored; it is removed, and creation (including missing ancestors), the publishing rename and the delete now run on `FILE_WRITE_THROUGH` handles (no power-loss test). See the `state` module docs.
- **`StateOptions`** (`StateDir::open_with`, `create_with`, `create_in_resolved_parent_with`; defaults unchanged): `allow_rename_while_open` (Windows `FILE_SHARE_DELETE` on directory handles; default off, which keeps `path()` true), `privacy: Privacy` (Windows ACL; `OwnerOnlyUnixInheritWindows` or `Inherit` skips the owner-only DACL so a fresh data root is not protected and propagated), `max_name_len` (write cap, default 200 bytes on unix / 255 units on Windows, up to 255), and `sync: SyncPolicy`.
- **Names.** `read`, `read_opt`, `stat`, `exists` and `remove` accept any name up to the platform limit, so one on-disk record over the 200-byte write cap no longer breaks a read-by-listing loop on unix. Temp names carry at most 64 bytes of the real name, which is what lets a 255-byte name be written. `validate_name` is unchanged (default write cap).
- **`list_entries` and `DirEntry`.** Names with `EntryKind` from `d_type` (unix) or the directory record's attributes (Windows), with no stat per entry; `DT_UNKNOWN` costs one `fstatat`. Windows `list` no longer fails the whole listing on an unpaired-surrogate name (returned lossily).
- **`SyncLevel`, `SyncPolicy`, `durable_sync_with`.** `durable_sync` keeps its signature and its Apple fallback (`F_FULLFSYNC`, `F_BARRIERFSYNC`, `fsync`). `durable_sync_with` returns the level reached; `SyncPolicy::Strict` returns the `F_FULLFSYNC` error instead of falling back. `StateDir::write_reporting` and `write_new_reporting` return the weakest level reached.
- **Lock file links.** `FileLock` refuses a link at the lock file's name as `FsError::Symlink`: unix maps the existing `O_NOFOLLOW` failure (`ELOOP`), Windows opens with `FILE_FLAG_OPEN_REPARSE_POINT` and checks the reparse attribute (before: it followed reparse points). README documents `LockKind::Flock` and the fcntl/flock caveat, and the migration path from a create-new marker lock.
- **`state::testing`** (feature `testing`): `fail_dir_sync`, `without_full_sync`, `dir_sync_count`, `fallback_stat_count`, `take_dir_events`.

## 0.3.3

- **Atomic path swap.** New `swap` module: `swap_paths(a, b)` exchanges two existing paths with macOS `renamex_np(RENAME_SWAP)` in one kernel step, so neither name is ever absent, even under SIGKILL. `is_swap_unsupported` recognises `ENOTSUP`, `EINVAL`, `ENOSYS` and `ErrorKind::Unsupported` (non-APFS volume, other OS) so callers can fall back. Other platforms return `ErrorKind::Unsupported`.
- **`rightkit-swap A B` binary** (feature `fs`). Exit 0 swapped, 1 I/O, 2 usage, 3 unsupported. Used by `right-release install-app`.

## 0.3.2

- **Durable writes fall back like libuv on Apple.** `atomic_write*`, `StateDir` publishes and directory syncs now call the new `durable_sync`: `F_FULLFSYNC`, then `F_BARRIERFSYNC`, then `fsync`. Previously `File::sync_all` (bare `F_FULLFSYNC`) failed hard with `EIO` on some external volumes under parallel writes where Node's `fsync` succeeded. Other platforms still use `sync_all`.

## 0.3.1

- **`lock` no longer depends on `nix`.** Unix record locks call `libc::fcntl(F_SETLK)` directly (same whole-file POSIX record lock, non-blocking, shared or exclusive), retrying on `EINTR`. Lock semantics are unchanged. `lock` now costs only `fs`.

## 0.3.0

- **Cargo features.** `digest` (sha2), `fs` (libc, thiserror: atomic, private, state, netfs, clone, error), `lock` (nix, on top of `fs`), and `json` (serde, on top of `lock`: identity ledger, owner records, clonefile binary). All are on by default. `rightkit-db` uses `features = ["fs"]`. Digest-only callers use `features = ["digest"]`; fs adds neither libc nor nix to their trees.
- **`digest` module (new).** `sha256_bytes`, `sha256_reader`, `sha256_file`, `sha256_file_with_len` (bytes hashed, for indexers), and `hex`. File digests stream in 64 KiB chunks. Output is lowercase hex, identical to the copies it replaces.
- **Documented primitives.** `atomic_write` and the two lock primitives, `FileLock::acquire` (exclusive) and `FileLock::acquire_shared`, are unchanged in behaviour and now documented as the shared entry points.
- Without `json`, locks behave the same but write no owner record, so `recovered_stale` is `None` and `current_owner` returns `None`.

## 0.2.0 — unpublished

- **File locks no longer look busy after a fork (Unix).** `FileLock` used `flock` through
  `File::try_lock`, which belongs to the open file description. A child forked by another
  thread (for example a `rightkit-process` spawn with `pre_exec`) inherits a lock descriptor
  until it execs. A failed `acquire` after the lock was taken (for example when the owner
  record cannot be written) dropped that descriptor without unlocking it, so the lock stayed
  held while the child lived and the next `try_acquire` reported `Locked`. Normal release was
  not affected: `Drop` calls an explicit unlock. Unix locks are now POSIX record locks
  (`fcntl F_SETLK`, through `nix`), which belong to the process and are not inherited. A
  process-wide registry keeps in-process exclusion (shared holders share one descriptor,
  exclusive is refused while anything is held), and every acquire and release runs under it,
  so one process never holds two descriptors on one lock file. Windows keeps `LockFileEx`
  through `File::try_lock` unchanged.
- Adds a `unix` dependency on `nix` (pinned `=0.30.1`, `fs` feature, already in the workspace).
- **Clone helper.** New `clone` module: macOS `clonefile(2)` with `CLONE_NOFOLLOW`. It never
  falls back to a byte copy. Ships the `rightkit-clonefile` binary.
- Crate version moves from 0.1.1 to 0.2.0.
