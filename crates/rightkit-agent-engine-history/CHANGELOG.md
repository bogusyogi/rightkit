# Changelog

## 0.1.4 (2026-11-16)

Fixes a data-loss bug in the slot key and ports the store's safety fixes. These are the store's own behaviour, not host options; no public item is added, renamed or removed. A patch in this 0.x crate, as 0.1.3 was: dependents on `0.1` take it without a requirement change.

- **Injective slot key (the data-loss fix).** A file's history slot was named by a flat key (`/ \ : * ? " < > |` all became `_`), so `a/b_c` and `a_b/c` shared one slot, which remembered only the first of them, and a rewind could write one file's old bytes over the other. A slot is now named by an injective escaping: those characters, `%`, control characters, bytes that are not UTF-8 and a trailing `.` or space become `%XX` per byte, everything else stays; a name over 200 bytes becomes a readable prefix, `%~` and a 128-bit hash, and a hashed name that collides is stepped over by the slot's `PATH` (`name%+1`, `name%+2`, ...). Every new slot also holds an empty `SLOT` file. The session directory is named by the same escaping (equal to the old name for ids made of letters, digits, `-`, `_` and `.`).
- **On disk, before and after.** Before: `<workspace>/<state_dir>/history/<session>/<flat key>/` with `PATH`, `<ts>.snap`, `<ts>.new`, `<ts>.after`, and `redo/<flat key>/`. After: the same layout and files, with the slot directory named by the injective key and holding `SLOT`, plus `PRUNED` (below) and, in a fork's copy of an old slot, `LEGACY`. The `.snap`, `.new`, `.after`, `PATH` and `redo` files are unchanged byte for byte.
- **Upgrade (existing history keeps working).** A slot written by 0.1.3 or earlier (no `SLOT`) is found by its flat name and continues to be used for the path its `PATH` names: reading, rewinding, redoing and recording more edits all work in place, and a `redo` stash written by an older version is redone. A path with no slot of its own gets an injective slot. An old slot cannot say which file wrote an entry when two paths shared it, so it is rewound only when the entries to undo read as one file's unbroken history (each post-edit record equals the next entry's pre-edit state, and the link holds content: a link that is "absent" or an empty file is not accepted, since two files can both be absent or empty); otherwise the path is reported in `failed` as `this history predates per-file keys and may mix the edits of more than one file; left as it is` and nothing is written. `peek_latest` and `restore_latest` of such a slot return the newest entry only when its post-edit record equals the file now. Residual: two files that hold identical non-empty content at the switch point between their entries pass the chain; if the first entry to undo belongs to the other file, it is written. A path whose own slot does not exist and whose flat name is held by another path's old slot that still has restore points (or a pending redo) cannot be told apart from it: `can_record` is `false` and a write fails (`history_unavailable` through `snapshot_targets`) until that slot is empty or the session is deleted. `can_record` is `true` for the previously colliding case once neither is an old slot, and `false` for a path that is not valid UTF-8 (a slot stores its path as text; such a path used to be written to its lossy spelling). A session whose id holds a character the key now escapes (`/ \ : * ? " < > |`, `%`, a control character, a trailing `.` or space, the name `redo`, or over 200 bytes) is looked up under its new directory name, so its older history is not found (it is left untouched on disk).
- **Downgrade.** 0.1.3 reads a session written by this version without corrupting it: it lists slots by directory and reads `PATH`, `.snap`, `.new`, `.after` and `redo`, so a rewind and a redo of the injective slots work and ignore `SLOT`, `PRUNED` and `LEGACY`. It does not look a path's history up by the injective name (`peek_latest` of such a path is `None`), and it writes the path's next edit to a flat slot beside the injective one; this version then refuses to rewind that path (`the history of this file is split over more than one slot`) instead of guessing an order. 0.1.3's `fork_from` drops `PRUNED` and `LEGACY`, so a fork it makes loses the retention marker and the old-slot check.
- **Retention.** At most 200 restore points and 512 MiB of snapshots per file; the oldest are pruned first, the newest is kept however large (so a single huge snapshot cannot make the prune loop), entries held in a redo stash are never touched, and the newest pruned timestamp is written to `PRUNED` before anything is deleted. A rewind that reaches a pruned restore point is refused for that file (`the restore point is older than the history kept for this file (the newest 200 edits and 512 MiB per file); left as it is`) instead of restoring a later state. An old slot over the limits is pruned on its next write.
- **Atomic restore.** A rewind and a redo replace the file crash-atomically through `rightkit-fs` (new dependency, feature `fs`) and keep its permissions, instead of truncating and writing in place. A restore needs to create a temporary file in the file's directory.
- **Fail-closed rewind.** A file whose newest entry has no post-edit record is left alone and reported as unverified (it used to be restored over whatever was there).
- **Redo stash.** A rewind drops the previous redo stash only once it is about to restore a file, so a rewind that matches nothing or is refused everywhere keeps the redo.
- **No-op edits.** `record_after`, `record_after_bytes` and `record_after_file` drop an entry whose edit changed nothing, so retries of a failed edit do not push real restore points out of retention.
- **Forks and deletion.** `fork_from` moves a path inside the parent's root to the same place under the child's root (also in its canonical spelling), so a rewind in the fork never writes into the parent's files; it returns `NotFound` when `child_root` differs from `parent_root` and does not exist yet (create the worktree first). `delete_session` refuses a session directory that is not one plain child of the history root (an id of `..` or an empty id used to resolve to the state directory itself).

## 0.1.3 (2026-11-16)

Byte-exact snapshots, additively: no existing function, file name or on-disk file changes for a text caller.

- New `HistoryStore::snapshot_bytes`, `record_after_bytes`, `record_after_file`, `peek_latest_bytes` / `consume_snapshot_bytes` (with `HistorySnapshotBytes`), `restore_latest_bytes` and `can_record`. A byte snapshot is the same `<ts>.snap` file `snapshot` writes (the bytes as they are), under the same slot, with the same `PATH`, `.after` and `redo` files, so a text snapshot reads back identically through the byte readers and a byte snapshot of valid UTF-8 is indistinguishable from a text one. `record_after_bytes` stores the same FNV-1a fingerprint as `record_after`, now computed over raw bytes (equal for text); `record_after_file` computes it from the file on disk in 64 KiB chunks, for a file too large to hold. `peek_latest_bytes` returns `Ok(None)` for a slot whose newest entry is a created-file marker with no snapshot under it, and an error when one lies under it (an older snapshot would be written over the created file); `peek_latest` is unchanged. `can_record` is `false` when the slot of a path is already owned by a different path (the flat slot key joins `a/b_c` and `a_b/c`), so a caller that records for a file it cannot name beforehand can fail closed instead of mixing two files' history.
- `restore_since` and `redo_since` now read and compare raw bytes, so a byte snapshot is restored exactly and a non-UTF-8 file on disk is judged by its content (it used to compare as absent); for UTF-8 content they behave as before. They also refuse, and report, a target that is a symlink or whose parent directory is a symlink leaving the workspace, instead of writing through it.
- Unchanged and not ported from the host fork: the injective slot key (it renames every slot), per-slot retention, the redo stash kept until a rewind restores something, fail-closed rewind when the post-edit record is missing, and the atomic write.
