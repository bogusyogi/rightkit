# Changelog

## Unreleased

Additive. No existing public item changes; no exhaustive enum gains a variant. Requests: Orthic-Labs/rightkit#423 (Pulse, BOM part), #531 (Pulse, capped read part), #191 (Pulse, documented behaviour). Not compiled when written; verification is the CI run.

- **New: `StoreOptions::utf8_bom(bool)`, `ReadOptions::utf8_bom(bool)` and `FileBackend::utf8_bom(bool)`** (default `false`). With `true`, a leading UTF-8 byte order mark is removed on read (the main file and `<path>.bak`) and every write puts one back. With the default, a BOM file is damaged JSON and goes through `OnCorrupt` as before. Tests: `tests/bom_and_cap.rs`.
- **New: `ReadOptions::max_bytes(limit)`** (#531). The free `read_with_options` / `read_with_defaults` refuse a file (main, or `.bak` when used) longer than `limit` with `Error::Invalid`, checked before the file is read. The file is not quarantined or written. Default: no limit. Earlier entries that say the free read is not limited are superseded by this one.
- **Documented, no code change (#191):** a newer schema version, an oversized file and undeclared keys are already covered: `OnRefused::ReadOnlyDefaults` (defaults, file untouched, `writable()` false), `StoreOptions::max_bytes` under it, and `allow_unknown_keys` with `KeyOrder::Preserve`. A damaged file is not covered by `OnRefused`; `OnCorrupt::Refuse` returns `Error::Corrupt` from `open`, and the free read returns defaults without touching it.
- **Already present (#251):** the connection-scoped SQL backend, feature `sql`, is in 0.2.3 (`SqlSettings`).

## 0.2.3

Additive, behind the new cargo feature `sql` (off by default). With it off the crate builds and behaves exactly as 0.2.2. Request: Orthic-Labs/rightkit#251 (MailRight, bogusyogi/mailright#69). Not compiled when written; verification is the CI run (`Cargo.lock` is regenerated there).

- **`SqlSettings` and `SqlError` (feature `sql`).** A connection-scoped settings backend for a SQL `settings(key, value)` table: `get`, `set`, `remove`, `patch` (several edits, all or none), `list(prefix)` for dynamic keys such as `signature:<acct>`, `ensure_table`, `refusal`, `writable`, `migrate`. Every call takes the caller's `&rusqlite::Connection`; a `&Transaction` derefs to it, so calls run inside the app's own migrations and transactions and join them. It owns no connection or pool and never commits or rolls back the caller's transaction (`patch` and `migrate` use a savepoint, which nests). It does not open or key a database, so SQLCipher works when the app builds `rightkit-db` with a `sqlcipher*` feature.
- **No reset on missing or newer data.** A missing table reads as defaults. With `version_key` set, a stored version above the schema's makes `get` return only the configured defaults and every write and `migrate` fail with `Error::NewerSchema`, writing nothing (the `OnRefused::ReadOnlyDefaults` behaviour). Table and column names are configurable, so MailRight's table and key strings stay unchanged; no version row is written unless `version_key` is named.
- **Reuses `Schema` and its migrations.** `migrate` runs pending migrations over the table's string values and writes back only the difference plus the version stamp, in one savepoint. `Schema::validate` is now `pub(crate)`.
- New optional dependency `rightkit-db` 0.4 (for its `rusqlite` re-export; dev-dependency with `bundled` for the tests). Tests: `tests/sql.rs`. The value column is read as text; a NULL value reads as absent.

## 0.2.2

Additive; defaults unchanged. Nothing compiled locally; verification is the CI run. Request: rightkit#191 (Pulse).

- **New: `StoreOptions::on_refused(OnRefused::{Fail, ReadOnlyDefaults})`.** A file whose schema version is newer than the code's, or that is over `max_bytes`, can open as read-only defaults instead of failing. `get` returns the defaults; `update`, `patch` and `remove_keys` fail with the error `Fail` opens with (`Error::NewerSchema`, `Error::Invalid`) before the backend takes its lock, so the file is left byte for byte as it was and no `.lock`, `.bak` or quarantine file appears. Default `Fail` is today's behaviour.
- **New: `Store::writable()` and `Store::refusal() -> Option<Refusal>`** (`Refusal::{NewerSchema { found, supported }, Oversized { len, limit }}`, `non_exhaustive`), checked against the file on each call, so a store recovers when the file is replaced or deleted. `poll_external` reports no change while a file is oversized under `ReadOnlyDefaults`.
- **New: `StoreOptions::flat_version_key(key)`.** A flat file has no envelope version; this names the top-level value that holds it, so a newer flat file is refused (open fails, or read-only defaults) and a write to one is never made. Without it nothing changes for flat files.
- **New: `SettingsBackend::size_refusal()`** (default `Ok(None)`; `FileBackend` implements it from `max_bytes`). Existing backends compile unchanged. `Error::Invalid` for an oversized file now reads "settings file is N bytes, over the L byte limit" (it named the path before) and still contains "byte limit".
- **Confirmed and documented: keys the type does not declare survive a save.** Flat files always; envelope files with `allow_unknown_keys` (every key already in the file is kept, the validator gates only new keys in a patch), in the file's own order under `KeyOrder::Preserve`. Not changed, only now tested.
- Not covered by `OnRefused`: a damaged (unparseable) file stays under `OnCorrupt` (`Refuse` touches nothing); a newer envelope whose `values` is not an object reads as damaged.
- Tests: `tests/refused.rs`. Docs: README "Refused files".

## 0.2.1

Renamed from rightkit-settings; 0.1.1 remains published under the old name.

Additive; defaults unchanged. Nothing compiled locally; verification is the CI run.

- **Docs (Android compile pass, rightkit#152):** no code change. The crate has no `target_os` branch and discovers no directory (no `HOME`, `XDG_*` or user-database lookup), so an Android build takes its root from the caller; the README now says to pass `Context.getFilesDir()` as an absolute path. The only platform split is `file_stamp` (`cfg(unix)` uses `MetadataExt`, available on Android) and the `rightkit-fs` atomic write and lock it calls (rightkit-fs is not changed here; its exclusive rename uses `renameat2` only on `target_os = "linux"`, so on Android it takes the `link` plus `unlink` fallback, which is unverified under Android's SELinux policy). Not built or run for an Android target.

- **New: `Document` and `DocumentState`, frontend-owned settings documents** (rightkit#113). For apps whose settings schema and `migrate()` live in the frontend (ViewRight, ScrapeRight): an opaque JSON object stored in the same versioned envelope, with the same atomic write, `.bak`, corruption recovery and cross-process lock as `Store`, and no typed struct. The crate never interprets or migrates it; the frontend states the version it writes. `Document::open_path(path, namespace)`, `open_path_with(path, &StoreOptions)` (envelope only; the schema supplies the namespace), `with_backend`; `get() -> Option<DocumentState { version, value, revision }>`; `put(version, value, expected_revision)` replaces; `patch(version, &patch, expected_revision)` merges top-level keys (`null` removes; nested objects are replaced whole); `import_if_missing(version, build)` runs a one-time legacy import inside the write lock, only when nothing is stored. A `version` below the stored one is refused with `Error::NewerSchema`, a stale `expected_revision` with `Error::Conflict`, a different stored namespace with `Error::Invalid`. A legacy flat file reads as version 0. Tests: `tests/document.rs`. Not done: the `@rightkit/tauri` / `@rightkit/settings-ui` get/patch helper and the change-event subscription for documents.
- **New: `Store::poll_external() -> Result<Change, Error>`** (M10-O3). Cross-process change had no signal beyond re-reading in `get`. This compares the backend stamp, re-reads when it differs, refreshes the cache and delivers one `Change` to this store's subscribers. The caller decides when to call it (timer or file watcher); the crate starts no thread. A read failure is an `Err` and leaves the cache as it was. Own writes are not re-reported. Tests: `tests/poll_external.rs`.
- **New: `StoreOptions::max_bytes(limit)` and `FileBackend::max_bytes`** (M10-O5). A settings file longer than `limit` bytes is refused before it is read (`Error::Invalid`); the file is not quarantined or overwritten, `get` keeps the last value, writes fail. Default: no limit. The free `read_with_*` functions are not limited. Tests: `tests/max_bytes.rs`.
- Not implemented, design decisions: layered/TOML loader (O2), SQLite backend (O4), Swift store (O1), Windows ACL profile (O6); see the M10 design note.

## 0.2.0

Durability claims corrected: on Windows only `ReplaceMode::MoveWriteThrough` is write-through; `Rename` is not. Nothing here was compiled or run locally; verification is the CI run.

Data loss and key order (two findings from HeardRight, read against 0.2.0 and verified against the source first):

- **Fix (data loss): a damaged settings file that cannot be moved aside is no longer written over.** `quarantine` discarded the `fs::rename` error (`let _ =`), so under `OnCorrupt::Quarantine` a damaged file that could not be renamed (permissions, a directory or locked file at the target, a full disk) was replaced by the write that followed, destroying the original the user could have recovered. The operation now fails with the new `Error::PreserveFailed { step: PreserveStep::Quarantine, path, kept_as, source }`, which names the file, where it was to go and the I/O cause, and the damaged file stays at `path` byte for byte (`backend.rs`: `quarantine`, `preserve`, called from `commit`). Nothing is written, the in-memory value is unchanged and no change event fires. `Store::open` fails the same way when the open-time repair needs the quarantine. A retry repeats the step. **Breaking for exhaustive matches on `Error`** (it is not `non_exhaustive`), like `Error::Replaced` in this section; `PreserveStep` is `non_exhaustive`.
- **Fix (same class): a `<path>.bak` that cannot be refreshed stops the write.** The refresh was `let _ = fs::copy(..)` ("best-effort"), so a write went ahead and replaced the file whose content the backup was meant to keep, leaving an older generation in `.bak` to be restored from later. It is now `PreserveStep::Backup`. **Behaviour change:** a write that used to succeed with a stale or missing `.bak` now fails; on Windows a transient sharing violation on `.bak` (a scanner holding it) is such a failure, and the caller retries. `sidecars(false)` has no `.bak` and is unaffected.
- **Fix (same class): the `keep_corrupt_copy` copy** already aborted the write, but as an untyped `Error::Io` that named no file; it is now `PreserveStep::CorruptCopy`. **Behaviour change** for callers matching `Error::Io` on that failure.
- **Sweep of the crate for ignored errors before a destructive step** (`let _ =`, `.ok()`, `unwrap_or`, `if let Err`): `quarantine` and the `.bak` copy were the only sites that dropped the error of a preserving step. Every other site is a read whose failure only forces a re-read or loses a hint (`get`/`peek`/`stamp`, `KeyLayout::of`, `Shape::parse`, the flat reference parse), the cleanup of this crate's own temp file after a failure that is already being returned (`atomic_write_with`), or the lock `unlock` in `Drop`, which cannot propagate and is released when the handle closes right after. The flat writer's second read of the file (`fs::read(..).ok()`, the source of its style) is gone: the bytes are read once, with any error other than `NotFound` propagated. No site ignores a sync error; the directory sync lives in rightkit-fs and reaches callers as `Error::Replaced`. Not changed, and not an ignored error: the `.bak` copy is not flushed, and a `Timestamped` quarantine name has one-second resolution, so a second quarantine in the same second replaces the first.
- **New: `StoreOptions::key_order(KeyOrder::{Preserve, Sorted})`**, also `FileBackend::key_order`. The crate wrote every envelope sorted, because `serde_json::Map` is a sorted map without `preserve_order`. That feature is **not** enabled (cargo feature unification would change `Map` for every crate in every app that links this one). The order is taken from the stored text instead, with an order-preserving parse of this crate's own (`Shape`, a serde `Visitor` that keeps keys in document order) and from the order the settings type serialises its keys (`KeyLayout`). `Preserve` is the default: keys the file holds keep their relative order at every level (objects in arrays follow the element at the same index), new keys are appended in the settings type's field order, removed keys disappear. A new file is in field order, the envelope's own keys as `schemaVersion`, `namespace`, `values`, `revision`. `Sorted` is alphabetical at every level, sorted explicitly (so it does not depend on the map type), and reproduces the output of every earlier version byte for byte (one exception: a flat file written over a damaged one under `OnCorrupt::Overwrite` used to take its indent from the damaged bytes; it now gets the default two spaces). Numbers, escapes and whitespace are written by the same `serde_json` code in both modes. This supersedes the 0.2.0 note that no key-order option is offered. The exact rules, per format, are on `KeyOrder`.
- **Behaviour change for existing consumers (default `Preserve`):** (1) a file that does not exist yet is created in the settings type's field order instead of alphabetically, and an envelope in `schemaVersion, namespace, values, revision` order instead of `namespace, revision, schemaVersion, values`; set `key_order(KeyOrder::Sorted)` to keep the old bytes. (2) A file written sorted by an earlier version stays sorted, but a key it did not hold (a field the type gained, an open key) is appended after the sorted ones instead of being inserted in its sorted place. (3) A flat file already kept its key order and the bytes of unchanged values; now a *changed* nested object also keeps its key order, and new keys are appended in field order rather than alphabetically. (4) A legacy flat file adopted as an envelope keeps its key order inside `values`. (5) A document restored from `<path>.bak` is written in the backup's order (and, for a flat file, its style and unchanged-value bytes) instead of a fresh layout; under `Sorted` a restore is written as before. (6) `pretty_sorted_newline(true)` still always sorts.
- **New: `SettingsBackend::patch_ordered` and `KeyLayout`.** The store hands the backend the settings type's key order with each commit. `patch_ordered` has a default implementation that drops the layout and calls `patch`, so existing backends compile and behave as before; `FileBackend` overrides it. `Stored` and `Edit` are unchanged.
- Limits, documented on `KeyOrder`: a patch is a `serde_json::Value`, which cannot carry the order it was written in, so several new open keys in one patch are appended alphabetically (in patch order only where `preserve_order` is on in the build); separate patches append in call order. A `HashMap` field serialises in a different order each run, so several new keys inside one are appended in no stable order.
- Tests: `tests/key_order.rs` (byte-identical round trip, one-value patches, new keys in field order, nested objects and arrays, sorted files, legacy flat adoption, `Sorted` against literal expected files, open keys, formatting parity), `tests/preserve.rs` (real file-system failures: a directory where the quarantine name, the corrupt copy or `.bak` must go), and unit tests in `src/backend.rs` with an injected rename or copy failure through a new private, `cfg(test)` seam (`fault`): there was none for these calls; the rightkit-fs `on_replace` hook only reaches the replace step.
- Docs: README (damaged files, preserve failures, key order, custom backends), rustdoc on `KeyOrder`, `OnCorrupt::Quarantine`, `keep_corrupt_copy`, `trailing_newline`, `pretty_sorted_newline`, `SettingsBackend::patch_ordered`, `KeyLayout`, `Error::PreserveFailed`. `OnCorrupt::Quarantine` said `<ms>`; the name is in seconds.

- **Fix: `Store::<serde_json::Value>` opens again.** 0.2.0 refused it with "settings type must serialize to an object" because `Value::default()` is `null`. A `null` default now counts as an empty object (`store.rs`, `to_object`): a store with no file opens as `{}`, a file holding an object loads, and a value that is an array, string, number or bool is still refused. Restores 0.1.1 behaviour. Covered by `value_typed_store_opens_and_round_trips`.
- **New: `Error::Replaced { path, source }`.** Returned when the settings file was replaced and a later step failed (Unix and macOS directory flush). It was an `Error::Io` wrapping an opaque error; it now says the new file is in place, so callers do not retry the write. **Breaking for exhaustive matches on `Error`**, and `atomic_write` (public) now reports it as an `io::Error` whose message says so. Published 0.2.0 is affected: a version bump is needed on release.
- **New: `StoreOptions::achieved_durability(destination_exists) -> PublicationDurability`** (re-exported from rightkit-fs). States what a write with the options gets on this platform: `None`, `FileFlushedOnly`, `DirectoryFlushed`, or `WriteThroughMove`.
- `tests/writer.rs`: the replace-call table covers `Rename` and `MoveWriteThrough`; new tests for `achieved_durability` and for `Error::Replaced` (Unix, injected directory-sync failure).
- Docs (README, rustdoc on `ReplaceMode`, `durable`, `atomic_write`): the durability statements now give the per-platform, per-mode answer.

Existing callers keep today's behavior: `Store::open(root, schema)` still writes the namespaced envelope at `<root>/<namespace>/settings.json`. Changes:

- `Store::open_path(path, options)` opens an explicit file path. The path is not tied to the namespace; the schema is still validated.
- `StoreOptions` (`new(schema)` plus builders `format`, `defaults_provider`, `allow_unknown_keys`) carries the schema and the new options.
- `defaults_provider`: used while the file is missing. Opening or reading writes nothing and creates no directory or lock file; the first update or patch that changes a value writes the file.
- `Store::open_read_only(path, options)`: creates no lock, backup, or directory, never waits for a writer's lock, and refuses `update`, `update_at`, and `patch`.
- `FileFormat::Flat`: the file stays a flat JSON object with no envelope, so older readers keep working. Undeclared keys are retained. A rewrite changes only the values that changed and keeps every other value's bytes, the original key order, the indent unit, and the trailing newline. A flat file has no version, so migrations do not run in this mode. The one-way opt-in to the envelope: open the same path with the default `FileFormat::Envelope`. The flat object is adopted as version 0, migrations run, and the next write produces the envelope. Undeclared keys are dropped by that first envelope write, so mirror any still needed in a migration first. Flat readers then refuse the envelope with `Error::Invalid`.
- `SettingsBackend` trait (`load`, `patch`, `stamp`, with default `revision` and `save`) and `Stored` / `Edit`. `FileBackend` is the file default; `Store::with_backend` opens over any backend. The trait docs carry an illustrative SQLCipher signature. Nothing is implemented for SQLCipher here.
- `patch` with `allow_unknown_keys(validator)`: undeclared top-level keys accepted by the validator are stored and kept across later saves. `null` removes one (under `NullMeans::SetNull` it stores `null`; see below). Patches that pass an allow-list refuse open keys.
- `patch_dry_run(patch, allow)` returns `PatchPreview { value, change }`; nothing is written.
- Flat-file revisions are an FNV-1a fingerprint of the file bytes (flat files have no counter).
- `StoreOptions::null_means(NullMeans::{Reset, SetNull})`: what `null` means in a patch for declared keys. `Reset` (default) keeps today's behavior. Under `Reset`, `null` removes an open key the document holds. Under `SetNull`, `null` always stores `"key": null` for an open key, held or absent; applying it twice leaves the document unchanged and writes nothing. Under `SetNull`, deleting an open key is `remove_keys` only.
- `StoreOptions::validate_values(check)`: validation beyond type checks over the complete candidate values. It runs only for edits that change something, in `update`, `update_at`, `patch`, and `patch_dry_run`; a failure is `Error::Invalid` and nothing is written.
- `get()` is cached: it re-parses only when the backend `stamp` changes. Custom backends that do not implement `stamp` are re-read on every call, as before.
- `StoreOptions::persist_defaults_on_first_save(bool)`, default `false`. When `true`, the first committed save against a missing file writes it even if the edit changes nothing, so the defaults reach disk. Additive; default behaviour is unchanged.
- Envelope `values` keys are written in alphabetical order (serde_json's default map). No key-order option is offered: serde_json's `preserve_order` is a compile-time feature, so a runtime flag cannot provide it.
- `StoreOptions::on_corrupt(OnCorrupt::{Quarantine, Refuse})`, default `Quarantine` (unchanged). `Refuse` returns the new `Error::Corrupt(path)` on open, read or write, and touches nothing: no rename, no write, no `.bak` read. Breaking for exhaustive matches on `Error`.
- `StoreOptions::sidecars(bool)`, default `true` (unchanged). `false` writes no `<path>.bak` and no `<path>.lock`, and never reads `<path>.bak` either (a missing file with a stale `.bak` reads as empty/defaults, also under `OnCorrupt::Refuse`; `ReadOptions::sidecars(false)` does the same for `read_with_options`); writers in this process are serialised by an in-process lock, and other processes are not excluded in this mode. Intended for flat files that must stay one file on disk.
- `StoreOptions::pretty_sorted_newline(bool)`, default `false` (unchanged output). `true` writes pretty JSON with object keys sorted at every level and a trailing newline, so the bytes depend only on the values. Flat files are rewritten whole in this mode, which drops the byte-preservation of unchanged values.
- `NullMeans::SetNull` now stores `"key": null` for a null-valued key (declared or open) the file does not yet hold, even when the in-memory value already equals null. Before, such a patch changed nothing and wrote nothing.
- `PatchPreview` gained `document: Map<String, Value>`: the exact document a committed patch stores, including retained open keys. Breaking for struct literals of `PatchPreview`.
- Repair and reads share one resolver (`Store::open`, `get()`, `read_with_defaults`, `read_with_options` cannot disagree). It starts from the caller's complete defaults (the provider's object, or `T::default()` serialised when there is no provider) and overlays the file's keys one at a time in sorted order, so the result does not depend on key order. A file key is dropped only when the settings type no longer parses with it; its default stays. If a default-supplied key is a different spelling of the same field (a serde `alias`, a duplicate field), the default key is dropped and the file's value wins. A file holding two spellings of one field keeps the alphabetically first. `T::default()` is never substituted for a value: if the defaults and the file do not form a valid value, the result is `Error::Invalid`. The cost is at most `O(n^2)` parses for `n` keys. A missing or unparseable file (no usable `.bak`) yields the defaults whole. Unknown keys never block a read (a key that breaks a `deny_unknown_fields` type is dropped from the value).
- `StoreOptions::fill_optional(bool)` and `ReadOptions::fill_optional(bool)`, default `false`. A key is optional when the settings type parses without it (a `#[serde(default)]` field or an `Option`). By default a field the file merely omits keeps plain serde behaviour; with `true` it is filled from the defaults. A required field the file omits, or a field the file holds with an invalid value, always takes the defaults. This replaces the earlier rule that provider defaults beat a `#[serde(default)]` struct's own defaults for omitted fields.
- `read_with_defaults::<T>(path, format, &defaults) -> Result<T, Error>` and `read_with_options::<T>(path, &defaults, ReadOptions)` (new, exported; `ReadOptions` has `format`, `fill_optional`, `sidecars`): a read-only, sidecar-free read. It uses the main file, then `<path>.bak`, then `defaults` (a JSON object, computed by the caller). It creates no directory, lock or backup, and quarantines nothing. Migrations do not run, so it reads the current document format only.

- `Store::remove_keys(&[&str])` and `remove_keys_dry_run`: explicit remove, independent of `NullMeans`. A present open key is deleted; an absent key changes nothing, creates nothing and writes nothing. A declared key returns to the value the type yields when the key is absent (serde default or `None`) and is written back by the type's own serialisation; a declared key with no serde default, or a key outside the schema, is `Error::Invalid`. The dry run agrees with the commit. Through `SettingsBackend::patch` a remove is an `Edit::Commit` of the document without the key, or `Edit::Keep` when it is absent.
- `NullMeans` default is `Reset`. Under `Reset`, a `null` patch for a key the document does not hold creates nothing and writes nothing. Only an explicit `SetNull` creates the key. `SetNull` now writes only for keys the patch itself nulls (before, any null-valued key absent from the document could force a write).
- A null-valued file key that collides with another spelling of the same field is the one dropped: `"tdt_model_dir": null` beside `"model_dir": "/x"` reads `/x`; `"model_dir": null` beside a valued alias reads the alias value; both null reads as the default (or unset for an `Option`). Two valued spellings still keep the alphabetically first.

- Durability options (fit review): `StoreOptions::replace_mode(ReplaceMode::{Rename, MoveWriteThrough})`, `durable(bool)` (default `true`), and `retry_sharing_violation(attempts, delay)` (default none), also on `FileBackend` (`replace_mode`, `durable`, `retry_sharing_violation`, `on_corrupt`, `with_options`). They map onto `rightkit-fs` 0.3.4 (`AtomicWriteOptions`), so this release requires `rightkit-fs = "0.3.4"`; publish rightkit-fs 0.3.4 first. What each gives is a table on `ReplaceMode`. **Default decision: unchanged, `Rename`.** Evidence (rightkit-fs 0.3.4, `atomic.rs` `plan_replace`): `Rename` never uses `MoveFileExW`; on Windows it flushes the temp file but the rename is not write-through and there is no directory flush, so after a power loss the previous content can reappear (a stale but complete file, never a torn one). `MoveWriteThrough` is always write-through, and it loses POSIX replace semantics, so a process that holds the settings file open without share-delete can make the write fail with a sharing violation. Settings are read by other processes (read-only stores, `get()` re-reads) and 0.1.1 and 0.2.0 adopters already run `Rename`, so a default flip would trade a rare stale-after-power-loss for new write failures and would silently change behaviour on upgrade. Apps whose settings must survive power loss opt in: `replace_mode(ReplaceMode::MoveWriteThrough).retry_sharing_violation(5, Duration::from_millis(50))`. On Unix and macOS every mode is `rename(2)` with a flushed temp file and a directory `fsync` after it; the options change nothing there. Windows tests assert the call and flag word through the `rightkit-fs` `testing` hook.
- `OnCorrupt::Overwrite`: an unparseable file is never renamed or refused; it stays at the path until an atomic replace succeeds, so a failed write leaves the old bytes. Reads still fall back to `<path>.bak`, and a damaged file is never copied over a good `.bak` (the `.bak` refresh now happens only when the current file parses, for every policy). `StoreOptions::keep_corrupt_copy(true)` makes a copy (never a rename) at the quarantine name immediately before the replace; a failed copy aborts the write. Additive; existing `match` on `OnCorrupt` needs an arm.
- `StoreOptions::quarantine_name(QuarantineName::{Timestamped, Fixed(suffix)})`, default `Timestamped` (`.corrupt-<secs>`, unchanged). `Fixed(".corrupt")` quarantines to `<path>.corrupt` and overwrites the previous one. An empty suffix or one with a path separator is `Error::BadSchema` at open.
- `StoreOptions::trailing_newline(bool)`, default `false`: every write ends with `\n`, with no key sorting, flat rewrites keep unchanged values' bytes and key order, and an unchanged document is not written. Separate from `pretty_sorted_newline`.
- `StoreOptions::flat_migration(fn(Map) -> Result<(Map, bool), Error>)`: a migration for flat files (no version). It runs once on open, on the parsed object as stored, before defaults and before repair; a reported change is committed once during open. `Err` aborts the open and writes nothing. It never runs for `open_read_only`, a missing file, or envelope files. It must be idempotent.

Behavior changes:

- A file that exists but cannot be read (not `NotFound`, for example permission denied) is now an `Error::Io` on open and update. Previously it was treated as missing and could be overwritten with defaults. Nothing is quarantined or written in that case.
- Migrations are fallible: `Migration::apply` and `Schema::migration` take `fn(&mut Map<String, Value>) -> Result<(), Error>`. Existing 0.1.x migration closures must end with `Ok(())`. An error aborts the open.
- A clean open no longer creates `settings.json.lock`. The lock is taken only when a write is needed.
- `serde_json` gains the `raw_value` feature (needed for byte-preserving rewrites). Envelope key order and bytes are unchanged.
- Fixed the stale README claim of `ReplaceFileW`; the atomic write renames over the destination (as in 0.1.1).

Consumer note: `rightkit-secrets` pins `rightkit-settings = { version = "0.1.0" }`. That requirement does not match 0.2.0 and must be bumped with this release.

## 0.1.1

- `atomic_write` now delegates to `rightkit_fs::atomic_write` (unique temp file, `fsync`, rename, directory `fsync`). The hand-declared `ReplaceFileW` FFI and the Windows branch are removed; the crate has no `cfg(windows)` code. Adds the `rightkit-fs` dependency (`fs` feature only).
- `atomic_write_with` keeps its signature as the failure-injection hook; its default replace step is `fs::rename`, which replaces an existing file on every platform.
