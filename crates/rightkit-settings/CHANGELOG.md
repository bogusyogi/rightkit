# Changelog

## Unreleased

Durability claims corrected for the rightkit-fs change that stopped passing `REPLACEFILE_WRITE_THROUGH` on Windows. Nothing here was compiled or run locally; verification is the CI run.

- **Fix: `Store::<serde_json::Value>` opens again.** 0.2.0 refused it with "settings type must serialize to an object" because `Value::default()` is `null`. A `null` default now counts as an empty object (`store.rs`, `to_object`): a store with no file opens as `{}`, a file holding an object loads, and a value that is an array, string, number or bool is still refused. Restores 0.1.1 behaviour. Covered by `value_typed_store_opens_and_round_trips`.
- **Behaviour: Windows `ReplaceMode::ReplaceFile` over an existing file** calls `ReplaceFileW` with flag word 0 (it was `REPLACEFILE_WRITE_THROUGH`). That swap is not flushed; `MoveWriteThrough` is the write-through mode, and `ReplaceFile`'s first creation still is.
- **New: `Error::Replaced { path, source }`.** Returned when the settings file was replaced and a later step failed (Unix and macOS directory flush). It was an `Error::Io` wrapping an opaque error; it now says the new file is in place, so callers do not retry the write. **Breaking for exhaustive matches on `Error`**, and `atomic_write` (public) now reports it as an `io::Error` whose message says so. Published 0.2.0 is affected: a version bump is needed on release.
- **New: interrupted replace is typed.** When rightkit-fs reports `FsError::ReplaceInterrupted`, the settings file may be missing. It surfaces as `Error::Io` (and `atomic_write` as an `io::Error`) whose inner error is the new public `InterruptedReplace { path, new_content, previous_content, source }`. Recover it with `err.get_ref().and_then(|e| e.downcast_ref::<InterruptedReplace>())`. It was an opaque `Error::Io` before. No new `Error` variant was added: `Error::Replaced` would claim the new file is in place, and a new variant would break exhaustive matches. `Error` is not `non_exhaustive`, so a variant would be a breaking change.
- **New: `StoreOptions::achieved_durability(destination_exists) -> PublicationDurability`** (re-exported from rightkit-fs). States what a write with the options gets on this platform: `None`, `FileFlushedOnly`, `DirectoryFlushed`, or `WriteThroughMove`.
- `tests/writer.rs`: the Windows replace-call table expects `(ReplaceFile, 0)` over an existing file; new tests for `achieved_durability` and for `Error::Replaced` (Unix, injected directory-sync failure).
- Docs (README, rustdoc on `ReplaceMode`, `durable`, `atomic_write`): the durability statements now give the per-platform, per-mode answer.

## 0.2.0

Existing callers keep today's behavior: `Store::open(root, schema)` still writes the namespaced envelope at `<root>/<namespace>/settings.json`. Changes:

- `Store::open_path(path, options)` opens an explicit file path. The path is not tied to the namespace; the schema is still validated.
- `StoreOptions` (`new(schema)` plus builders `format`, `defaults_provider`, `allow_unknown_keys`) carries the schema and the new options.
- `defaults_provider`: used while the file is missing. Opening or reading writes nothing and creates no directory or lock file; the first update or patch that changes a value writes the file.
- `Store::open_read_only(path, options)`: creates no lock, backup, or directory, never waits for a writer's lock, and refuses `update`, `update_at`, and `patch`.
- `FileFormat::Flat`: the file stays a flat JSON object with no envelope, so older readers keep working. Undeclared keys are retained. A rewrite changes only the values that changed and keeps every other value's bytes, the original key order, the indent unit, and the trailing newline. A flat file has no version, so migrations do not run in this mode. The one-way opt-in to the envelope: open the same path with the default `FileFormat::Envelope`. The flat object is adopted as version 0, migrations run, and the next write produces the envelope. Undeclared keys are dropped by that first envelope write, so mirror any still needed in a migration first. Flat readers then refuse the envelope with `Error::Invalid`.
- `SettingsBackend` trait (`load`, `patch`, `stamp`, with default `revision` and `save`) and `Stored` / `Edit`. `FileBackend` is the file default; `Store::with_backend` opens over any backend. The trait docs carry an illustrative SQLCipher signature. Nothing is implemented for SQLCipher here.
- `patch` with `allow_unknown_keys(validator)`: undeclared top-level keys accepted by the validator are stored and kept across later saves. `null` removes one (under `NullMeans::SetNull` it stores `null`; see below). Patches that pass an allow-list refuse open keys.
- `patch_dry_run(patch, allow)` returns `PatchPreview { value, change }`; nothing is written.
- Flat-file revisions are an FNV-1a fingerprint of the file bytes (flat files have no counter).
- `StoreOptions::null_means(NullMeans::{Reset, SetNull})`: what `null` means in a patch for declared keys. `Reset` (default) keeps today's behavior. Under `Reset`, `null` removes an open key the document holds. Under `SetNull`, `null` always stores `"key": null` for an open key, held or absent; applying it twice leaves the document unchanged and writes nothing. Under `SetNull`, deleting an open key is `remove_keys` only.
- `StoreOptions::validate_values(check)`: validation beyond type checks over the complete candidate values. It runs only for edits that change something, in `update`, `update_at`, `patch`, and `patch_dry_run`; a failure is `Error::Invalid` and nothing is written.
- `get()` is cached: it re-parses only when the backend `stamp` changes. Custom backends that do not implement `stamp` are re-read on every call, as before.
- `StoreOptions::persist_defaults_on_first_save(bool)`, default `false`. When `true`, the first committed save against a missing file writes it even if the edit changes nothing, so the defaults reach disk. Additive; default behaviour is unchanged.
- Envelope `values` keys are written in alphabetical order (serde_json's default map). No key-order option is offered: serde_json's `preserve_order` is a compile-time feature, so a runtime flag cannot provide it.
- `StoreOptions::on_corrupt(OnCorrupt::{Quarantine, Refuse})`, default `Quarantine` (unchanged). `Refuse` returns the new `Error::Corrupt(path)` on open, read or write, and touches nothing: no rename, no write, no `.bak` read. Breaking for exhaustive matches on `Error`.
- `StoreOptions::sidecars(bool)`, default `true` (unchanged). `false` writes no `<path>.bak` and no `<path>.lock`, and never reads `<path>.bak` either (a missing file with a stale `.bak` reads as empty/defaults, also under `OnCorrupt::Refuse`; `ReadOptions::sidecars(false)` does the same for `read_with_options`); writers in this process are serialised by an in-process lock, and other processes are not excluded in this mode. Intended for flat files that must stay one file on disk.
- `StoreOptions::pretty_sorted_newline(bool)`, default `false` (unchanged output). `true` writes pretty JSON with object keys sorted at every level and a trailing newline, so the bytes depend only on the values. Flat files are rewritten whole in this mode, which drops the byte-preservation of unchanged values.
- `NullMeans::SetNull` now stores `"key": null` for a null-valued key (declared or open) the file does not yet hold, even when the in-memory value already equals null. Before, such a patch changed nothing and wrote nothing.
- `PatchPreview` gained `document: Map<String, Value>`: the exact document a committed patch stores, including retained open keys. Breaking for struct literals of `PatchPreview`.
- Repair and reads share one resolver (`Store::open`, `get()`, `read_with_defaults`, `read_with_options` cannot disagree). It starts from the caller's complete defaults (the provider's object, or `T::default()` serialised when there is no provider) and overlays the file's keys one at a time in sorted order, so the result does not depend on key order. A file key is dropped only when the settings type no longer parses with it; its default stays. If a default-supplied key is a different spelling of the same field (a serde `alias`, a duplicate field), the default key is dropped and the file's value wins. A file holding two spellings of one field keeps the alphabetically first. `T::default()` is never substituted for a value: if the defaults and the file do not form a valid value, the result is `Error::Invalid`. The cost is at most `O(n^2)` parses for `n` keys. A missing or unparseable file (no usable `.bak`) yields the defaults whole. Unknown keys never block a read (a key that breaks a `deny_unknown_fields` type is dropped from the value).
- `StoreOptions::fill_optional(bool)` and `ReadOptions::fill_optional(bool)`, default `false`. A key is optional when the settings type parses without it (a `#[serde(default)]` field or an `Option`). By default a field the file merely omits keeps plain serde behaviour; with `true` it is filled from the defaults. A required field the file omits, or a field the file holds with an invalid value, always takes the defaults. This replaces the earlier rule that provider defaults beat a `#[serde(default)]` struct's own defaults for omitted fields.
- `read_with_defaults::<T>(path, format, &defaults) -> Result<T, Error>` and `read_with_options::<T>(path, &defaults, ReadOptions)` (new, exported; `ReadOptions` has `format`, `fill_optional`, `sidecars`): a read-only, sidecar-free read. It uses the main file, then `<path>.bak`, then `defaults` (a JSON object, computed by the caller). It creates no directory, lock or backup, and quarantines nothing. Migrations do not run, so it reads the current document format only.

- `Store::remove_keys(&[&str])` and `remove_keys_dry_run`: explicit remove, independent of `NullMeans`. A present open key is deleted; an absent key changes nothing, creates nothing and writes nothing. A declared key returns to the value the type yields when the key is absent (serde default or `None`) and is written back by the type's own serialisation; a declared key with no serde default, or a key outside the schema, is `Error::Invalid`. The dry run agrees with the commit. Through `SettingsBackend::patch` a remove is an `Edit::Commit` of the document without the key, or `Edit::Keep` when it is absent.
- `NullMeans` default is `Reset`. Under `Reset`, a `null` patch for a key the document does not hold creates nothing and writes nothing. Only an explicit `SetNull` creates the key. `SetNull` now writes only for keys the patch itself nulls (before, any null-valued key absent from the document could force a write).
- A null-valued file key that collides with another spelling of the same field is the one dropped: `"tdt_model_dir": null` beside `"model_dir": "/x"` reads `/x`; `"model_dir": null` beside a valued alias reads the alias value; both null reads as the default (or unset for an `Option`). Two valued spellings still keep the alphabetically first.

- Durability options (fit review): `StoreOptions::replace_mode(ReplaceMode::{Rename, ReplaceFile, MoveWriteThrough})`, `durable(bool)` (default `true`), and `retry_sharing_violation(attempts, delay)` (default none), also on `FileBackend` (`replace_mode`, `durable`, `retry_sharing_violation`, `on_corrupt`, `with_options`). They map onto `rightkit-fs` 0.3.4 (`AtomicWriteOptions`), so this release requires `rightkit-fs = "0.3.4"`; publish rightkit-fs 0.3.4 first. What each gives is a table on `ReplaceMode`. **Default decision: unchanged, `Rename`.** Evidence (rightkit-fs 0.3.4, `atomic.rs` `plan_replace`): `Rename` never uses `MoveFileExW`; on Windows it flushes the temp file but the rename is not write-through and there is no directory flush, so after a power loss the previous content can reappear (a stale but complete file, never a torn one). `ReplaceFile` passes `REPLACEFILE_WRITE_THROUGH` only when `durable` and moves a first-created file with `MOVEFILE_WRITE_THROUGH`; `MoveWriteThrough` is always write-through. Both lose POSIX replace semantics, so a process that holds the settings file open without share-delete can make the write fail with a sharing violation. Settings are read by other processes (read-only stores, `get()` re-reads) and 0.1.1 and 0.2.0 adopters already run `Rename`, so a default flip would trade a rare stale-after-power-loss for new write failures and would silently change behaviour on upgrade. Apps whose settings must survive power loss opt in: `replace_mode(ReplaceMode::ReplaceFile).retry_sharing_violation(5, Duration::from_millis(50))` (the Windows behaviour 0.1.0 had through `ReplaceFileW`). On Unix and macOS every mode is `rename(2)` with a flushed temp file and a directory `fsync` after it; the options change nothing there. Windows tests assert the call and flag word through the `rightkit-fs` `testing` hook.
- `OnCorrupt::Overwrite`: an unparseable file is never renamed or refused; it stays at the path until an atomic replace succeeds, so a failed write leaves the old bytes. Reads still fall back to `<path>.bak`, and a damaged file is never copied over a good `.bak` (the `.bak` refresh now happens only when the current file parses, for every policy). `StoreOptions::keep_corrupt_copy(true)` makes a copy (never a rename) at the quarantine name immediately before the replace; a failed copy aborts the write. Additive; existing `match` on `OnCorrupt` needs an arm.
- `StoreOptions::quarantine_name(QuarantineName::{Timestamped, Fixed(suffix)})`, default `Timestamped` (`.corrupt-<secs>`, unchanged). `Fixed(".corrupt")` quarantines to `<path>.corrupt` and overwrites the previous one. An empty suffix or one with a path separator is `Error::BadSchema` at open.
- `StoreOptions::trailing_newline(bool)`, default `false`: every write ends with `\n`, with no key sorting, flat rewrites keep unchanged values' bytes and key order, and an unchanged document is not written. Separate from `pretty_sorted_newline`.
- `StoreOptions::flat_migration(fn(Map) -> Result<(Map, bool), Error>)`: a migration for flat files (no version). It runs once on open, on the parsed object as stored, before defaults and before repair; a reported change is committed once during open. `Err` aborts the open and writes nothing. It never runs for `open_read_only`, a missing file, or envelope files. It must be idempotent.

Behavior changes:

- A file that exists but cannot be read (not `NotFound`, for example permission denied) is now an `Error::Io` on open and update. Previously it was treated as missing and could be overwritten with defaults. Nothing is quarantined or written in that case.
- Migrations are fallible: `Migration::apply` and `Schema::migration` take `fn(&mut Map<String, Value>) -> Result<(), Error>`. Existing 0.1.x migration closures must end with `Ok(())`. An error aborts the open.
- A clean open no longer creates `settings.json.lock`. The lock is taken only when a write is needed.
- `serde_json` gains the `raw_value` feature (needed for byte-preserving rewrites). Envelope key order and bytes are unchanged.
- Fixed the stale README claim of `ReplaceFileW`; the atomic write renames over the destination (as in 0.1.1).

Consumer note: `rightkit-secrets` pins `rightkit-settings = { version = "0.1.0" }`. That requirement does not match 0.2.0 and must be bumped with this release.

## 0.1.1

- `atomic_write` now delegates to `rightkit_fs::atomic_write` (unique temp file, `fsync`, rename, directory `fsync`). The hand-declared `ReplaceFileW` FFI and the Windows branch are removed; the crate has no `cfg(windows)` code. Adds the `rightkit-fs` dependency (`fs` feature only).
- `atomic_write_with` keeps its signature as the failure-injection hook; its default replace step is `fs::rename`, which replaces an existing file on every platform.
