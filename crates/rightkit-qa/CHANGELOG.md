# Changelog

## Unreleased (after 0.2.16)

- QA runs never touch real user data. New `userdata` module: `Guard` runs inside `control::launch` (home must be a created QA root under a system temp root; working directory and every absolute environment path must resolve inside it) and in the engine launch paths (`data_dir` and data/home/profile/config environment paths must be in a temp root). Refused with a typed `UserDataViolation { path, rule, detail }`: Documents, Desktop, Downloads, Pictures, Music, Movies, iCloud Drive, OneDrive, Dropbox, Google Drive, the app's real application-support / AppData / config directory, `/Volumes/*`, UNC paths, and any symlink that resolves into them. No opt-out. Behaviour change: a `RIGHTKIT_QA_HOME_ROOT` or `RUNNER_TEMP` outside a temp root, or in one of these places, is now refused at launch. `userdata::seed_from` copies seed state through a caller transform and refuses the real data of the app under test unless the scenario declares the copy scrubbed and a verification callback returns true. `StopReport::permission_dialog()` reports dialog agents in the sampled foreground names; `Control::assert_no_permission_dialog()` is a documented no-op (no window-by-owner enumeration in `rightkit-control`).
- QA home hygiene. Each home records its owner in `.rightkit-home.json`. `workspace::dispose` deletes a home only when it is a runner-created home. At run start `workspace::create` removes homes whose owner process is dead and that are older than 2 h (`RIGHTKIT_QA_HOME_MAX_AGE_SECS`), then returns `RootOverCap` (naming the largest homes) when the root holds more than 4 GB (`RIGHTKIT_QA_ROOT_CAP_BYTES`, `0` disables). `Harness` drop removes its home on pass and fail unless `with_keep_failed_home(true)` / `RIGHTKIT_QA_KEEP_FAILED_HOME=1`, which keeps only the failed run's home and prints its path and size (`suite::run` does the same). New `storage::clean_homes`, `storage::clean` and `rightkit-qa clean [--dry-run]`. `sweep_homes` no longer removes a home whose recorded pid is alive. Nothing here was compiled or run.
- Sidecar buffers are bounded. `Sidecar::events` keeps the newest frames (default 2,048; trimmed in batches once it reaches twice the limit, so it holds 2,048 to 4,095), and engine stderr keeps its last 256 KiB, cut on a line boundary where possible, with a `[N bytes of earlier stderr dropped]` marker in `stderr_tail()`. `SidecarStatus` gains `events_dropped` and `stderr_dropped_bytes`; `Sidecar::set_event_limit` and `set_stderr_limit` change the limits. A request still sees its own id as the frame arrives, so a trimmed frame cannot turn a timeout into "did not answer".
- Retention lock (regression: parallel scenarios failed with "QA retention lock is held" since 0.2.13/0.2.14). The lock guards only the prune pass, but `storage::create` held it across the prune AND the run-directory creation and failed after 5 s, so a slow prune (large tree, several processes) failed an unrelated scenario. A starter now takes the lock without waiting: if another process is pruning, it skips its own pass and starts (run ids are claimed with an atomic `create_dir`). An explicit `prune*` waits up to 120 s, then fails with a message starting `storage::LOCK_HELD` (`storage::is_lock_held`). A lock whose owner process died, or that never got an owner file within 30 s, is recovered; the lock is released on drop, including a panic. Introduced in commit 3548fc7a.
- App-home sweep. Homes under `<tmp>/rightkit-qa/` were only reclaimed through their run record, so a home whose run root was deleted (a killed process, a test run inside another home's scratch) was never found again. `storage::sweep_homes` also removes homes with no run record older than 24 h and homes of finished runs older than 24 h, then the oldest finished homes while the total exceeds 4 GB (only when removing them can meet the bound). Live runs, young orphans and directories without a `.rightkit-app.json` binding are never removed. `workspace::create` runs it at most every 10 minutes (set `RIGHTKIT_QA_HOME_SWEEP=0` to skip). New `rightkit-qa homes [--apply]` reports what it would remove (dry run by default).
- `RIGHTKIT_QA_HOME_ROOT=<absolute dir>` moves homes to `<dir>/rightkit-qa/`. The default is unchanged: homes stay on internal storage because a launchd-started macOS app cannot open its live log on an external volume (`control::launch`) and the control socket path must fit `sockaddr_un`.
- `workspace::create` now creates every directory its exported environment points at (including `WEBVIEW2_USER_DATA_FOLDER` and the suite root) plus the per-user directories platform known-folder lookups resolve under the isolated profile: Windows `AppData\Local`, `AppData\Roaming`, `AppData\LocalLow` and the `Desktop`/`Documents`/`Downloads`/`Music`/`Pictures`/`Videos` folders; macOS `Library/Application Support`, `Caches`, `Preferences`, `Logs`; Linux `.local/share`, `.local/state`, `.config`, `.cache`. Windows expands the registry's `%USERPROFILE%\AppData\Local` against the overridden USERPROFILE, so with the directory missing `SHGetKnownFolderPath` failed (Tauri "unknown path", `dirs::cache_dir()` None). Gap ledger #92 (2). A platform-neutral test asserts each exported path under the home exists as a directory.
- The live app log now goes to `<home>/.rightkit-qa/` instead of directly into the app's HOME, so apps that list or watch HOME do not see their own log writes as directory changes.
- Launch timeout errors on Windows say when the harness process is in session 0 or on a non-visible window station (SSH, service) and that a hidden WebView2 app cannot get a ready window from there; the window-ready error also reports whether the process was alive. README Windows section documents it. Gap ledger #92 (1).

## 0.2.16 - 2026-10-11

- Sidecar frame shape follows the hello again. The 0.2.16 `sidecar_command` default (rightkit-jobs frames for every engine) broke GenRight's engine, which never answers that shape, so three scenarios that passed on 0.2.15 waited out their timeout. The shape is now read from the hello captured at spawn: a `contract_version` field means the rightkit-jobs contract, an `rpc_version` field (GenRight's `EngineFrame::Hello`) means the legacy GenRight frames, and a hello with neither keeps the jobs contract. The per-command `legacy_status_frames` option and `Sidecar::legacy_status_frames = true` still force the legacy frames; `Some(false)` forces the jobs contract. New `Sidecar::set_frame_shape(Option<bool>)` pins the shape for the whole sidecar in either direction and is what `sidecar_start` now uses, so an explicit `false` in a scenario overrides detection. When the hello names neither shape and a command gets no frame for its request id before the timeout, the error says the engine did not answer the frame shape that was sent, names it, and names `legacy_status_frames` as the switch. The timeout is unchanged.
- Windows background invariant. `StopReport::owned_never_frontmost` was always `false` for a hidden or background launch on Windows because nothing sampled the foreground owner. The focus monitor now reads the foreground window's owning pid (`GetForegroundWindow` + `GetWindowThreadProcessId`) every 20 ms and compares it with the started pid, registered the instant the process is spawned. The flag is `true` only when no sample found that pid in front and no foreground owner was unreadable; a moment with no foreground window counts as nothing owned in front. The check covers the started pid only, not helper processes. The macOS check is unchanged.
- The README no longer says this crate has no changelog, and states exactly what the Windows hidden launch checks.
- Windows pointer path: none of `control.rs` `move_to`/`pointer`/`click`/`screenshot_*`, `launch_env`, `QaWorkspace` creation or `process.rs` changed between 0.2.12 and 0.2.14, so this release makes no pointer change. Gap ledger #74 (Pulse hub journey, Windows: Folders radio shows no hover or pressed state under 0.2.14) is not attributed to a code path in this crate. Pulse's run with every other change kept and `=0.2.12` restored passed (CI run 38086940130), so the cause is still open; Pulse stays on `=0.2.12` until its Windows leg passes on this release.
- `sidecar_command` now speaks the rightkit-jobs contract by default (`{type:"request", id, method: name, params: input}` answered by `{type:"response", id, ok, result | error:{code,message}}`). GenRight's old frames (`method:{method:"command",...}`, `status: ok|err`) stay behind `legacy_status_frames = true`, set on `sidecar_start` for the whole sidecar or on a single `sidecar_command`. Behaviour change for scenarios that relied on the old default: add the option.
- Unit tests cover the foreground classification and the fail-closed rule on every platform.

## 0.2.15 - 2026-10-10

- `rightkit-control` is now a macOS-only target dependency with `default-features = false`; only `mac::frontmost_name` and `mac::frontmost_pid` were used, and Windows builds no longer compile it.
- Drop `libc`: orphan-sweep liveness (`storage::pid_live`) now uses `rightkit_process::AdoptedProcess::is_running` on every platform (replaces `libc::kill` on Unix and a `tasklist` spawn on Windows). A process whose state cannot be measured counts as live.
- Drop `uuid` and `time`: `util::new_id` builds the same hyphenated v4 identifier from `getrandom`, and `util::now_iso` formats RFC 3339 UTC by hand with the same shape as before. Both have tests.
- Windows foreground read (`control::frontmost`) uses `windows-sys` 0.61 (already in the lock via overlay, ort, crash, logs, hotkeys) instead of `windows` 0.62. Written and checked by inspection only: no Windows build was run for this change.
- No public API changes.

## 0.2.14 - 2026-10-09

- Digests come from `rightkit-fs` (`digest` feature only, `default-features = false`): `util::sha256_hex` calls `rightkit_fs::digest::sha256_bytes`; the direct `sha2` dependency is gone. Output is the same lowercase hex.
- Windows foreground read (`control::frontmost`) and the Windows `tasklist` liveness probe move from `windows` 0.61 to `windows` 0.62 (target dependency only), and `storage::pid_live` drops a redundant `return`.
- README documents features, platform support and examples.
- No change to `control.rs`, `workspace.rs`, `process.rs` or `scenario.rs`: launch environment, run directories and the hover, press, move and screenshot calls are byte-for-byte the 0.2.12 code. (Gap ledger #74, a Windows hub-journey failure first seen alongside this release, is not traceable to a code path in this crate; see 0.2.16.)

## 0.2.13 - 2026-10-08

- The ffprobe pin is resolved from Settings with three keys, first match wins: `RIGHTKIT_QA_FFPROBE`, then `<APP>_FFPROBE` (the app name upper-cased, every non-alphanumeric character becoming `_`, so `scrape-right` reads `SCRAPE_RIGHT_FFPROBE`), then GenRight's historical `GENRIGHT_FFPROBE`. A key that is set but names no file yields no pin and PATH discovery is not tried. Resolution runs in the shared `Harness` constructor, so `new` and `new_in_managed_root` behave the same.
- The short registered `TMPDIR` for runs, the same-volume Trash check and the `--trash-kind run` cleanup that shipped in this release live in the build-control npm packages (`storage.mjs`, `storage-cli.mjs`). They do not change how this crate creates run directories or launches apps (`QaWorkspace` and `control::launch` are unchanged).
