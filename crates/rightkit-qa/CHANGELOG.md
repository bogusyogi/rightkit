# Changelog

## 0.5.0

Breaking (0.x minor): runs are functional by default and take no screenshots. Not built or run locally; CI is the compiler.

- **Run kinds.** A run is `functional` (default: clicks, state and text, no screenshots, no screen recordings) or `visual` (the audit-visual run that captures screens). A scenario sets `kind = "functional"|"visual"`; the CLI sets `rightkit-qa run --kind functional|visual` (`SuiteOptions::kind`, `storage::RunKind`). `--kind` wins; otherwise the run is visual when a selected scenario declares `visual`. A capture step in a functional scenario is **refused** with a clear error, never skipped: `ui_screenshot`, `browser_screenshot`, and a `screenshot`, `record*`, `capture*` or `video*` method inside `ui_batch`. The automatic `failure.png` is taken only in visual scenarios. A scenario that declares `visual` inside an explicit functional run fails with an error. New: `scenario::{resolve_run_kind, scenario_kind, ensure_capture_allowed, is_capture_method}`, `Scenario::kind`, `Ctx::kind`, `Harness::{with_run_kind, run_kind}`. The kind is in the run header, `results.json` (`kind`), the evidence identity (`runKind`) and the run marker.
- **Run marker.** `.rightkit-run.json` gains `kind` and `outcome` (`passed|failed|skipped`), both optional so older markers still load. The suite records the outcome when it ends; the harness records it when the last clone is dropped (failed on a panic or any failed scenario, skipped when nothing ran). New: `storage::{RunKind, RunOutcome, set_run_kind, set_run_outcome}`, `QaWorkspace::{set_kind, set_outcome}`.
- **Evidence retention.** New `retention` module: `prune_runs(managed_root, app, dry_run)`, `prune_runs_after_job(managed_root, app)` and `managed_root_of_run`. It prunes only directories that carry a valid marker for their own app and run id, keeps every failed run, every unfinished or active run and the newest passing run per app and kind, and deletes the other passing runs (and runs that executed nothing). It never leaves `<managed root>/runs`, refuses a `runs` link, skips app and run directories that are links and never follows one. The suite and the harness run it right after each job (it cannot fail the job). New CLI subcommand `rightkit-qa prune-runs [--app KEY] [--root DIR] [--dry-run]` for a schedule.
- The count and byte-cap prune at run start (`storage::prune*`, `sweep`) now keeps failed runs by the count rule; only the byte cap can still evict one, oldest first.
- **Evidence stays out of app repos.** Suite and harness evidence were already under `<managed root>/runs/<app>/<run-id>/`. The unused `evidence_dir` config key and `QaConfig::evidence_root` (which named `<app>/.cache/rightkit-qa` inside the checkout) are removed; an old key is ignored. README documents the ignore lines apps need for the repo-side paths the crate still touches (`.cache/`, `target/`, `rightkit-qa.settings.env`).
- Examples: `ui-hidden.scenario.toml` and `bench/ui-bench-batch.scenario.toml` are `kind = "visual"` (they take screenshots). `bench/ui-bench.scenario.toml` takes screenshots too; run it with `--kind visual`.
- Migration: a scenario that takes screenshots needs `kind = "visual"` (or `--kind visual`). Consumers that gate on a screenshot count (Pulse's `scripts/gate.sh` wants at least eight) must run their visual scenarios as visual.

## 0.4.0

Depends on `rightkit-qa-driver` ^0.4. UI QA latency: a click step went from about 230 ms to about 1 ms, 200 typed characters from 2.3 s to about 0.12 s, a condition wait returns when the page is ready (no polling tax).

- `Control::wait_eval` and `wait_for_text` use the driver's new `wait` method: one round trip, the page reports the moment the predicate holds. An app on an older driver is polled every 25 ms (was 100 ms). The timeout error text is unchanged.
- New `Control::batch(&[(method, params)])` and scenario step `ui_batch` (`steps = [{method, params}]`): many steps in one round trip, stopped at the first failure.
- `Control::screenshot_png` asks for the image inline (base64 in the reply) instead of write-read-delete; an older driver's `path` reply is still read. The scenario `ui_screenshot` takes the size from the bytes it already has, and `evidence = false` keeps a working capture out of the evidence bundle (only bundled artifacts are hashed).
- A reused call thread replaces a thread per request; a timed-out call abandons it and the next call starts a new one.
- Input pacing: `Control::set_pace_ms` or `RIGHTKIT_QA_PACE_MS` sends `paceMs` with click, drag, key and type; default none.
- The scenario `until` retry interval defaults to 25 ms (was 500 ms); set `interval_ms` per step to change it.
- `control::launch` waits for the app's own page (not `about:blank`, which reports `complete`) before returning, and checks every 20 ms.
- **Background proof diagnostics.** `StopReport` gains `frontmost_pid_unavailable_samples` and `owned_never_frontmost_failure`, so "an owned app process was frontmost (pid [..])" is told apart from "the foreground owner's pid could not be read in N sample(s)" and from "the owned executable was never registered". `ui_stop` and scenario teardown print that reason. The guard itself is unchanged and still fails closed: an unreadable pid, an unregistered executable or an unmeasurable sample leaves `owned_never_frontmost` false. Works with the driver's fixed macOS frontmost reader (see rightkit-qa-driver 0.4.0), which is what Ember's CI needed.
- Benchmark scenarios `examples/control-test-app/bench/ui-bench.scenario.toml` and `ui-bench-batch.scenario.toml` (20 clicks, 200 typed characters, 10 screenshots, 5 waits).

## 0.2.16 - 2026-10-11

(os error 5)" after it had already deleted `.rightkit-app.json`; without that binding file no sweep can prove the home ours, so it stayed for good (176 CutRight homes, 1.86 GiB, on one machine in a day). Not compiled or run locally.
  - Homes are now removed by `storage::remove_home_tree` (crate-private). It takes the `rightkit-qa` root it may work under and refuses a path that is not a real directory strictly inside it once both are resolved. A link in the tree (symlink, or junction on Windows) is removed as itself, never listed and never followed, on every system. A read-only file is removed on Windows. The binding file goes last. The error names the entry that could not be removed.
  - Used by `workspace::dispose` (the home; the run root is unchanged), `clean_homes`, `sweep_homes` and the prune of a finished run's home.

  (temp file, flush, rename). They were plain `fs::write`, so a retention sweep in another process could read a
  partly written file and treat the home as unbound or malformed. The `rightkit-fs` dependency gains its `fs`
  feature. Not changed: the sweep stamp (`let _ = fs::write`), whose content is a best-effort time. Not built or
  run locally.
- Windows: a run no longer fails to start with "Access is denied" while another starter releases the retention lock.
  The lock is a directory; on Windows a directory that is being removed keeps its name until the last handle on it
  closes, and creating that name meanwhile is refused with access denied, not "already exists". `try_lock` passed that
  error on, so `create` failed for one of several parallel starters (seen in `parallel_starters_in_one_process_all_proceed`
  on the windows-2025 runner). The refusal now counts as "held": a starter skips its own prune pass and starts, and a
  caller that waits for the lock keeps waiting until its deadline. New Windows test makes that state on purpose.
  Present since the starters stopped waiting for the lock (c9774ac5); not caused by the per-product cap, the dispose
  change or the launch guard.
- BREAKING, safety: an engine launch that names no isolated data directory is refused before the process starts (`UserDataViolation { rule: Rule::NoIsolatedDataDir }`, naming the target). Before, `check_engine_dirs` judged only a directory it was given and environment values that were absolute paths, so `data_dir: None` with no variable naming the folder passed, and the engine then resolved its real per-user folder by its own default (on Windows from the Known Folder API, which ignores `HOME`, `USERPROFILE` and `APPDATA`). A GenRight scenario opened the real folder that way twice against an installed build. Applies to `EngineTarget::cli`, `run`, `start_sidecar` and the scenario `cli` / `sidecar_start` steps. A launch names a directory when `CliOptions::data_dir` reaches the engine through `EngineTarget::data_dir_env`, `data_dir_env` is set in the launch environment, or the new `EngineTarget::data_dir_arg` flag carries one in the arguments, and the guard accepts it; a `data_dir` on a target that declares neither is refused too, because the engine would never receive it. Nothing here was compiled or run (CI only).
  - Migration: pass an isolated directory with a target that declares `data_dir_env` (config `[engine] data_dir_env`, now effectively required for engine steps), or use the probe below. Scenario suites whose config has no `data_dir_env` now fail their engine steps until they add it. `EngineTarget` gained public fields (`data_dir_arg`, `forbidden_args`, `allow_no_data_dir_for_refusal_probe`), so struct literals need updating; `EngineTarget::new(binary)` with `with_data_dir_env`, `with_data_dir_arg`, `forbid_args` builds one.
  - `EngineTarget::forbid_args(&[..])` / config `[engine] forbidden_args`: a launch whose arguments carry a listed flag (`flag` or `flag=value`) is refused with `Rule::ForbiddenArgument`. Empty by default; no product flag is named in this crate.
  - `EngineTarget::allow_no_data_dir_for_refusal_probe()`: the one opt-out, for asserting an engine's own refusal to run without a folder. Refused outright on Windows (`Rule::ProbeUnavailable`: the Known Folder API ignores the environment). On Unix it needs the child environment to set `HOME` to a directory the guard accepts, and `XDG_DATA_HOME` / `XDG_CONFIG_HOME` too wherever set or inherited; otherwise `Rule::ProbeUnavailable`. The directory rules and the forbidden-argument list still apply.
  - `control::launch` refuses a launch environment without `RIGHTKIT_QA_DATA_DIR` inside the QA root (`NoIsolatedDataDir`); workspaces always set it.
  - Public API: `userdata::check_engine_launch`, `userdata::EngineLaunch`, `userdata::check_app_data_dir`, `Rule::{NoIsolatedDataDir, ForbiddenArgument, ProbeUnavailable}`, `EngineTarget::{new, with_data_dir_env, with_data_dir_arg, forbid_args, allow_no_data_dir_for_refusal_probe}`, `EngineConfig::{data_dir_arg, forbidden_args}`. `check_engine_dirs` is unchanged and still judges only what it is given. The `budget` bench now gives its synthetic engine a scratch data directory.
- Windows: `workspace::dispose` no longer fails with "Access is denied. (os error 5)" and leaves the home behind when it runs right after `Control::stop()` (ledger 174). WebView2 and GPU helpers of the stopped app were still exiting and held `EBWebView`, the shader caches and logs. Before removing the home, dispose now waits (up to 20 seconds) for every process that names the home on its command line or runs from it. Of those that remain it ends only the run's own: a process whose executable is inside the home, or a descendant of an app the run launched (`control::launch` records the pid; `workspace::record_launched` for an app started by hand). A process that merely names the home is never ended. A home that still cannot be removed is reported with the processes holding it (`...; held by msedgewebview2.exe (pid 412)`). New: `workspace::home_holders(home)`, `HomeHolder`, `workspace::record_launched`. A process whose working directory is inside the home but which does not name it is not detected (reading another process's working directory is not done). Homes left by earlier runs are taken by the existing sweep. Other systems are unchanged.
- QA root limits are per product (fixes the 0.2.16 whole-root cap, which refused unrelated products' runs: PostRight and ViewRight could not run while GenRight and CutRight leftovers filled the root). Nothing here was compiled or run.
  - `RIGHTKIT_QA_ROOT_CAP_BYTES` (default 4 GB, `0` disables) now bounds one product's homes. A run for app X is refused only when X's own homes exceed it. A home's product is the `app` in its `.rightkit-app.json` binding, else the label in its directory name (`<app cut to 16 characters>-<suffix>`). The refusal names the product, its total, its largest homes, and that `rightkit-qa clean` removes the homes of dead runs.
  - New root-wide ceiling `RIGHTKIT_QA_ROOT_CEILING_BYTES` (default 32 GB, `0` disables): every run is refused only when all homes together exceed it. The refusal names the largest homes with their product. Behaviour change: a root above 32 GB now refuses runs where the cap alone never would have.
  - Limits can be set in code, because the variables never reach a test run under `rightkit cargo`: `Harness::with_root_cap_bytes(u64)` and `Harness::with_root_ceiling_bytes(u64)` (`0` disables), `workspace::create_with_limits(.., storage::RootLimits)`. A value set in code wins over the variable; an unset limit falls back to the variable, then the default. Behaviour change: the harness now checks its limits at the first scenario that runs instead of in its constructor (so a setter chained after `new` applies); it still sweeps in the constructor. A refused scenario records a failed evidence bundle, removes its own home and panics with the refusal; a scenario skipped by tier or requirement does not check.
  - Public API: `storage::check_root_cap(parent, app, cap_bytes)` takes the app; new `storage::check_root_limits`, `RootLimits`, `ResolvedRootLimits`, `RootLimitKind`, `root_ceiling_bytes`, `ROOT_CEILING_ENV`, `DEFAULT_ROOT_CEILING_BYTES`. `RootOverCap` gains `kind`, `app` and `home_count`, renames `cap_bytes` to `limit_bytes`, and each `largest` entry is `(home, bytes, product)`.
- The start-of-run sweep removes dead homes that have no `.rightkit-home.json` owner marker (written before 0.2.16, or missing a file). `clean_homes` used to follow the run record's lease for them, so a cancelled run's home stayed alive and counted for 24 hours, and a home without a binding file was never touched. Such a home now goes when all of these hold: it is a plain directory directly inside `rightkit-qa` (no symlink followed, nothing outside the root); its name is `<label>-<16 lowercase hex>` or `<label>-<6 letters or digits>`; no pid its records name is alive (the run record's `ownerPid` through the binding's `runRoot`, and the pid in a home marker that has no binding); and nothing in the home, the directory included, was modified within `RIGHTKIT_QA_HOME_MAX_AGE_SECS` (default 2 h). Not checked: processes that have the home as working directory or an open file, and the run record's lease. A symlink entry is reported as retained ("symlink skipped"). Homes that have an owner marker keep their rule. Behaviour change: homes that were kept before are now removed, including those of runs cancelled within the last 24 hours.
- `rightkit-qa guard` follows the "QA control never ships" rule (`src/guard.rs`). The registration may sit under `#[cfg(feature = "qa-native")]` with or without `debug_assertions`, so release-derived dev builds (`--profile release-iterate`) can carry the server. The `compile_error!` for non-debug builds is no longer required, and the older debug-only gate is still accepted. Rejected: an unconditional registration, including a `not(feature = "qa-native")` gate; a non-optional `rightkit-control` that enables `qa-control`; `qa-native` in `default`, directly or through another feature; `qa-native` without `rightkit-control/qa-control` (or dependency-level `qa-control`); and any other feature that enables the dependency. A gate may sit on an enclosing function or block. `use` lines and comments no longer count as registrations. Each message names the file and the change to make.
- QA runs never touch real user data. New `userdata` module: `Guard` runs inside `control::launch` (home must be a created QA root under a system temp root; working directory and every absolute environment path must resolve inside it) and in the engine launch paths (`data_dir` and data/home/profile/config environment paths must be in a temp root). Refused with a typed `UserDataViolation { path, rule, detail }`: Documents, Desktop, Downloads, Pictures, Music, Movies, iCloud Drive, OneDrive, Dropbox, Google Drive, the app's real application-support / AppData / config directory, `/Volumes/*`, UNC paths, and any symlink that resolves into them. No opt-out. Behaviour change: a `RIGHTKIT_QA_HOME_ROOT` or `RUNNER_TEMP` outside a temp root, or in one of these places, is now refused at launch. `userdata::seed_from` copies seed state through a caller transform and refuses the real data of the app under test unless the scenario declares the copy scrubbed and a verification callback returns true. `StopReport::permission_dialog()` reports dialog agents in the sampled foreground names; `Control::assert_no_permission_dialog()` is a documented no-op (no window-by-owner enumeration in `rightkit-control`).
- QA home hygiene. Each home records its owner in `.rightkit-home.json`. `workspace::dispose` deletes a home only when it is a runner-created home. At run start `workspace::create` removes homes whose owner process is dead and that are older than 2 h (`RIGHTKIT_QA_HOME_MAX_AGE_SECS`), then returns `RootOverCap` (naming the largest homes) when the root holds more than 4 GB (`RIGHTKIT_QA_ROOT_CAP_BYTES`, `0` disables). `Harness` drop removes its home on pass and fail unless `with_keep_failed_home(true)` / `RIGHTKIT_QA_KEEP_FAILED_HOME=1`, which keeps only the failed run's home and prints its path and size (`suite::run` does the same). New `storage::clean_homes`, `storage::clean` and `rightkit-qa clean [--dry-run]`. `sweep_homes` no longer removes a home whose recorded pid is alive. Nothing here was compiled or run.
- Sidecar buffers are bounded. `Sidecar::events` keeps the newest frames (default 2,048; trimmed in batches once it reaches twice the limit, so it holds 2,048 to 4,095), and engine stderr keeps its last 256 KiB, cut on a line boundary where possible, with a `[N bytes of earlier stderr dropped]` marker in `stderr_tail()`. `SidecarStatus` gains `events_dropped` and `stderr_dropped_bytes`; `Sidecar::set_event_limit` and `set_stderr_limit` change the limits. A request still sees its own id as the frame arrives, so a trimmed frame cannot turn a timeout into "did not answer".
- Retention lock (regression: parallel scenarios failed with "QA retention lock is held" since 0.2.13/0.2.14). The lock guards only the prune pass, but `storage::create` held it across the prune AND the run-directory creation and failed after 5 s, so a slow prune (large tree, several processes) failed an unrelated scenario. A starter now takes the lock without waiting: if another process is pruning, it skips its own pass and starts (run ids are claimed with an atomic `create_dir`). An explicit `prune*` waits up to 120 s, then fails with a message starting `storage::LOCK_HELD` (`storage::is_lock_held`). A lock whose owner process died, or that never got an owner file within 30 s, is recovered; the lock is released on drop, including a panic. Introduced in commit 3548fc7a.
- App-home sweep. Homes under `<tmp>/rightkit-qa/` were only reclaimed through their run record, so a home whose run root was deleted (a killed process, a test run inside another home's scratch) was never found again. `storage::sweep_homes` also removes homes with no run record older than 24 h and homes of finished runs older than 24 h, then the oldest finished homes while the total exceeds 4 GB (only when removing them can meet the bound). Live runs, young orphans and directories without a `.rightkit-app.json` binding are never removed. `workspace::create` runs it at most every 10 minutes (set `RIGHTKIT_QA_HOME_SWEEP=0` to skip). New `rightkit-qa homes [--apply]` reports what it would remove (dry run by default).
- `RIGHTKIT_QA_HOME_ROOT=<absolute dir>` moves homes to `<dir>/rightkit-qa/`. The default is unchanged: homes stay on internal storage because a launchd-started macOS app cannot open its live log on an external volume (`control::launch`) and the control socket path must fit `sockaddr_un`.
- `workspace::create` now creates every directory its exported environment points at (including `WEBVIEW2_USER_DATA_FOLDER` and the suite root) plus the per-user directories platform known-folder lookups resolve under the isolated profile: Windows `AppData\Local`, `AppData\Roaming`, `AppData\LocalLow` and the `Desktop`/`Documents`/`Downloads`/`Music`/`Pictures`/`Videos` folders; macOS `Library/Application Support`, `Caches`, `Preferences`, `Logs`; Linux `.local/share`, `.local/state`, `.config`, `.cache`. Windows expands the registry's `%USERPROFILE%\AppData\Local` against the overridden USERPROFILE, so with the directory missing `SHGetKnownFolderPath` failed (Tauri "unknown path", `dirs::cache_dir()` None). Gap ledger #92 (2). A platform-neutral test asserts each exported path under the home exists as a directory.
- The live app log now goes to `<home>/.rightkit-qa/` instead of directly into the app's HOME, so apps that list or watch HOME do not see their own log writes as directory changes.
- Launch timeout errors on Windows say when the harness process is in session 0 or on a non-visible window station (SSH, service) and that a hidden WebView2 app cannot get a ready window from there; the window-ready error also reports whether the process was alive. README Windows section documents it. Gap ledger #92 (1).

- Sidecar frame shape follows the hello again. The 0.2.16 `sidecar_command` default (rightkit-jobs frames for every engine) broke GenRight's engine, which never answers that shape, so three scenarios that passed on 0.2.15 waited out their timeout. The shape is now read from the hello captured at spawn: a `contract_version` field means the rightkit-jobs contract, an `rpc_version` field (GenRight's `EngineFrame::Hello`) means the legacy GenRight frames, and a hello with neither keeps the jobs contract. The per-command `legacy_status_frames` option and `Sidecar::legacy_status_frames = true` still force the legacy frames; `Some(false)` forces the jobs contract. New `Sidecar::set_frame_shape(Option<bool>)` pins the shape for the whole sidecar in either direction and is what `sidecar_start` now uses, so an explicit `false` in a scenario overrides detection. When the hello names neither shape and a command gets no frame for its request id before the timeout, the error says the engine did not answer the frame shape that was sent, names it, and names `legacy_status_frames` as the switch. The timeout is unchanged.
- Windows background invariant. `StopReport::owned_never_frontmost` was always `false` for a hidden or background launch on Windows because nothing sampled the foreground owner. The focus monitor now reads the foreground window's owning pid (`GetForegroundWindow` + `GetWindowThreadProcessId`) every 20 ms and compares it with the started pid, registered the instant the process is spawned. The flag is `true` only when no sample found that pid in front and no foreground owner was unreadable; a moment with no foreground window counts as nothing owned in front. The check covers the started pid only, not helper processes. The macOS check is unchanged.
- The README no longer says this crate has no changelog, and states exactly what the Windows hidden launch checks.
- Windows pointer path: none of `control.rs` `move_to`/`pointer`/`click`/`screenshot_*`, `launch_env`, `QaWorkspace` creation or `process.rs` changed between 0.2.12 and 0.2.14, so this release makes no pointer change. Gap ledger #74 (Pulse hub journey, Windows: Folders radio shows no hover or pressed state under 0.2.14) is not attributed to a code path in this crate. Pulse's run with every other change kept and `=0.2.12` restored passed (CI run 38086940130), so the cause is still open; Pulse stays on `=0.2.12` until its Windows leg passes on this release.
- `sidecar_command` now speaks the rightkit-jobs contract by default (`{type:"request", id, method: name, params: input}` answered by `{type:"response", id, ok, result | error:{code,message}}`). GenRight's old frames (`method:{method:"command",...}`, `status: ok|err`) stay behind `legacy_status_frames = true`, set on `sidecar_start` for the whole sidecar or on a single `sidecar_command`. Behaviour change for scenarios that relied on the old default: add the option.
- Unit tests cover the foreground classification and the fail-closed rule on every platform.

## 0.2.15 - 2026-10-10

- `rightkit-control` is now a macOS-only target dependency with `default-features = false`; only `mac::frontmost_name` and `mac::frontmost_pid` were used, and Windows builds no longer compile it.
- Drop `libc`: orphan-sweep liveness (`storage::pid_live`) now uses `rightkit_process::AdoptedProcess::is_running` on every platform (replaces `libc::kill` on Unix and a `tasklist` spawn on Windows). A process whose state cannot be measured counts as live.
- Drop `uuid` and `time`: `util::new_id` builds the same hyphenated v4 identifier from `getrandom`, and `util::now_iso` formats RFC 3339 UTC by hand with the same shape as before. Both have tests.
- Windows foreground read (`control::frontmost`) uses `windows-sys` 0.61 (already in the lock via overlay, ort, crash, logs, hotkeys) instead of `windows` 0.62. Written and checked by inspection only: no Windows build was run for this change.
- No public API changes.

## 0.2.13 - 2026-10-08
