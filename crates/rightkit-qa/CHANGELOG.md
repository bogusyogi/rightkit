# Changelog

## 0.10.0 (unpublished)

`Scenario` and `Step` are all-pub structs and gain pub fields (`inputs`), so the next version is 0.10.0 (the registry records 0.9.0).

- Fixed (`embedded::Control`, window label): after the app's own `.window(..)` and the launcher's `[ui] window_label` (`RIGHTKIT_QA_WINDOW_LABEL`), the control plugin now binds the window the app declares in its Tauri config (`main` if declared, else the first window the config creates, `create` not `false`) before it falls back to `main`. A control build started without the runner, whose only window is not `main` (for example `hub`), used to answer every order with `window_not_found` and now works with a bare `Control::<tauri::Wry>::new()`. The runner always exports `[ui] window_label` (default `main`), so a runner launch of such an app still sets that key. A window built only in code is not in the config, so such an app calls `.window(..)` or sets `[ui] window_label`. The resolved label is the one the control service role (`control:<label>`) names.
- Added (`Scenario::inputs`, per-app QA inputs, gap C2-07): a scenario can set an app's QA-only input with an `[inputs]` table (or `inputs = { .. }`) before its first `[[step]]`, for an app that reads it with `rightkit_daemon::test_selector!(mode, "RIGHTKIT_<APP>_<NAME>")`. `Scenario::load` refuses the file with `<path>: inputs.<KEY>: <why>` unless the key is `RIGHTKIT_` plus upper-case words (`^RIGHTKIT_[A-Z0-9]+(_[A-Z0-9]+)*$`, at most 64 bytes), is not a name the harness or the daemon's mode decision sets or reads itself (`RESERVED_INPUT_KEYS`: the control token file, service and window label, the pool world, `RIGHTKIT_UNDER_TEST`, the test roots, what `workspace::create` sets, the runner's settings), and names no credential (the launch guard's `key_names_credential`), and the value is a string of at most 1024 bytes with no NUL, CR or LF; a number, boolean or array value is a load error. `ui_launch` applies the inputs in the order `[ui].env`, config `env`, data-dir variable, scenario `inputs`, the step's own `env`, so a step can still override one for a launch. `Step::inputs` carries the scenario's table onto each step, so no runner change is needed. See the README, "Per-app QA inputs".
- Fixed (`ui_launch` environment): each key is passed once, the highest layer winning. A key that appeared in two layers (`[ui].env` and the config `env`, or the config `env` and the step's `env`) used to be passed twice and refused at launch as an override of a harness-owned value; the step's `env` now overrides the config as documented.

## Unreleased

False-pass hardening (rk-qa-hardening; gaps C4-05 to C4-07, C4-09 to C4-12, QA-01 to QA-07). No version is bumped here.

- BREAKING (build, not behaviour): `harness::Outcome` is `#[must_use]`. A test that calls `Harness::scenario(..)` as a statement and drops the value warns, and fails under `-D warnings`: a skipped scenario made its libtest test `ok`, so the dropped `Outcome::Skipped` was a false pass (58 call sites in seven apps). End the test with the new `Outcome::require_ran()` (panics on a skip, except a skip for another known OS, so a platform-gated scenario still passes on the other host), or inspect the value. `Outcome::skipped_for_other_platform()` says which skip it was. `Harness::scenario` now reports the other-OS reason before any other skip reason, so a Windows-only scenario on a Mac is always recognised as such, whatever else it also lacks.
- Fixed (Harness bridge): a bridged libtest binary whose test printed a harness `<prefix> SKIP <name>: <reason>` line (any bracketed prefix: `[qa]`, GenRight's `[e2e]`) or a `NOTRUN` line was classified `passed` because libtest says `ok` for a returned test. It is now `skipped` with one skipped unit and the line quoted, which a journeys receipt refuses as "skipped is not a pass". A failed test stays `failed` and an `ok` with a non-zero exit stays `errored`.
- Fixed (budgets): a step kind whose recorded durations were all 0 ms derived a 0 ms enforcement limit, so every later run was `OverBudget` once the warn window closed. The derived limit is now `max(2 x p95, MIN_ENFORCE_MS)`, with `MIN_ENFORCE_MS = 100`. A host with fewer than 20 samples still enforces at the declared budget.
- Fixed (installed-app refusal): `%LOCALAPPDATA%\<Product>`, where `right-release dev` installs every Windows app, was not refused. Product folder names are `[ui] installed_dirs`, or by default the `productName` of `<app_root>/src-tauri/tauri.conf.json` (else `<app_root>/tauri.conf.json`), plus whatever `RIGHTKIT_QA_INSTALLED_DIRS` lists (a `;` list; `right-release qa` sets it from the release config's installed path). `%LOCALAPPDATA%` itself is never a root, so QA homes and `Temp` stay launchable. New: `installed::INSTALLED_DIRS_ENV`, `declare_product_dirs`, `declared_product_dirs`, `product_dir_name_ok`, `installed_roots_with`. `QaConfig::load` declares the product folders; a Rust test that never loads a config declares its own with `declare_product_dirs(["<Product>"])` or sets `RIGHTKIT_QA_INSTALLED_DIRS`.
- Fixed (`[ui] window_label` was a dead key): the in-app control server always targeted `main`, so an app whose window is `hub` could never become ready. The runner now exports the configured label as `RIGHTKIT_QA_WINDOW_LABEL` (a `RIGHTKIT_*` key, accepted on macOS) and `embedded::Control` resolves its window as the app's own `.window(..)`, then that variable, then `main` (`control::resolve_window_label`). The launch spec's `label` is a process-tracker label and is not the window label. Only the config-driven `ui_launch` step (declarative scenarios and journeys) sets the variable. A Rust test that builds its own `LaunchSpec` and calls `control::launch` goes through no config, so it must put `RIGHTKIT_QA_WINDOW_LABEL` in `LaunchSpec::env` (a `RIGHTKIT_*` key, accepted on macOS) or register `.window("<label>")`; `[ui] window_label` alone does not reach it.
- Added (`[ui] env_keys`): app-specific, non-secret environment keys a macOS launch may carry besides `RIGHTKIT_*` (the launch refused every other key). A key naming a credential is refused everywhere, declared or not. `rightkit-qa guard` requires every declared key to be a release-forbidden switch (class S1 to S4) in the app's `switches.json`, so the release scan proves it is absent from shipped binaries. New: `control::launch_declared` (`launch` is unchanged and declares none), `control::env_key_allowed`, `control::key_names_credential`. `LaunchSpec` is unchanged.
- Added (guard, config-free): `rightkit-qa guard --app-root <dir>` needs no `rightkit-qa.toml`: it finds `src-tauri/Cargo.toml` (else `Cargo.toml`) and `tauri.conf.json`, and reads every `*.rs` under the crate's `src` (a registration outside `lib.rs` was never checked). With a config and no `rust_sources`, the guard now also reads every `*.rs` instead of only `src-tauri/src/lib.rs`. New: `guard::AppContract`, `validate_app`, `assert_app_contract`, `tauri_crate_dir`, `rust_sources_under`; `ContractInput` and `validate` are unchanged.
- Added (guard rules): a `qa-native` build of an app that declares `build.devUrl` must reach tauri's `custom-protocol` feature, or QA drives the dev server instead of the built app (CodeRight, HeardRight); `qa`/`test`/`e2e` scripts that build with `qa-native` may not run `tauri dev`, and with a `devUrl` must build the frontend first; a first window not labelled `main` needs `.window("<label>")` or `[ui] window_label`.
- Added: `rightkit-qa --version` (`-V`) prints `rightkit-qa <version>`; `right-release qa policy approve-runner` runs it to bind an approved digest to a published version.
- Not here: the `outcome-dropped` and `qa-custom-protocol` preflight mirrors and the PowerShell exit-code rule (plan item 5, `@rightkit/release` preflight), and the app-side repairs (plan 3.3). Embedded code (`embedded/mod.rs`) compiles only with the `control` feature on a Mac or Windows host, so its window-label wiring is covered by the pure `resolve_window_label` tests and needs a host run.

## 0.8.0

- Added: end-to-end journeys (`journeys` module, `docs/E2E-TESTING-STANDARD.md` D3, D4, D5). `journeys::manifest` reads and validates `journeys.toml` and `journeys-map.toml` (`journeys::check`; unknown keys are refused, `data = "real"` is refused, entries must exist and stay inside the app root, adapter references must resolve, a `native-ui` journey needs a declared built binary and no dev-server build). `journeys::adapter` is the app-side helper for protocol v1: `Selection::read` (env `RIGHTKIT_JOURNEYS_SELECTION`), `Reporter::{from_env, open, start, journey, end}` appending `start`, `journey` and `end` JSON lines that carry `run_id` and `nonce` to `RIGHTKIT_JOURNEYS_RESULTS`, and `journey_from_outcomes` / `journey_from_units` (a group that matches nothing is `errored`). The helper refuses an unselected or repeated journey, a `passed` journey with no unit or with a failed or skipped unit, a `missing` status, and a results file that already holds data. `journeys::receipt` holds the `rightkit.journeys.receipt/1` types and `validate_receipt`, which recomputes counts and verdict and never believes the receipt's `verdict`: zero selected or executed, missing, duplicate, unselected, skipped, failed or errored results, stale `run_id` or `nonce`, a results or artifact digest that does not match, a launched binary not produced by the claimed tree, a dirty tree, an isolation failure, a non-zero adapter exit and an absent `results.jsonl`, manifest or evidence root (`results_unverified`, incomplete) each refuse the receipt. Rust not built or run locally; CI is the compiler.
- Added (`control` feature, QA only): IPC fixture seam. Tauri freezes `__TAURI_INTERNALS__.invoke` and app init scripts run after it, so a test cannot fake engine replies by replacing invoke; Tauri's IPC transport calls `window.fetch` per command, and that is writable. The embedded control plugin now injects `src/embedded/ipc_fixture.js` (`window.__RK_QA_IPC__ = { add(rule), clear(), log() }`, a `window.fetch` wrapper) through `js_init_script`, only when `RIGHTKIT_CONTROL_SERVICE` is set. A rule is `{cmd, args?, replies: [{kind: 'ok'|'error', value}], times?}`; `args` is a subset match; replies are used in order and the last repeats; a matched request answers with a JSON `Response` and a `Tauri-Response: ok|error` header; anything else passes to the real fetch; every IPC call is logged as `{cmd, args}`. The IPC prefix comes from `convertFileSrc('', 'ipc')`, so it is right on Windows (`http://ipc.localhost/`) and macOS (`ipc://localhost/`). It never assigns to invoke, ipc or postMessage. New `Control::ipc_fixture_add`, `ipc_fixture_log`, `ipc_fixture_clear`; a page reload drops runtime rules. Release builds lack the `control` feature and `right-release` refuses `QA_CONTROL_MARKER` binaries. Tests: `src/embedded/ipc_fixture.test.mjs` (`node --test`), and in `embedded::tests` `ipc_fixture_script_only_when_the_service_env_is_set`, `ipc_fixture_script_never_assigns_invoke_ipc_or_post_message`. Rust not built or run locally.

A refused scenario records a failed evidence bundle, removes its own home and panics with the refusal; a scenario skipped by tier or requirement does not check.
  - Public API: `storage::check_root_cap(parent, app, cap_bytes)` takes the app; new `storage::check_root_limits`, `RootLimits`, `ResolvedRootLimits`, `RootLimitKind`, `root_ceiling_bytes`, `ROOT_CEILING_ENV`, `DEFAULT_ROOT_CEILING_BYTES`. `RootOverCap` gains `kind`, `app` and `home_count`, renames `cap_bytes` to `limit_bytes`, and each `largest` entry is `(home, bytes, product)`.
- The start-of-run sweep removes dead homes that have no `.rightkit-home.json` owner marker (written before 0.2.16, or missing a file). `clean_homes` used to follow the run record's lease for them, so a cancelled run's home stayed alive and counted for 24 hours, and a home without a binding file was never touched. Such a home now goes when all of these hold: it is a plain directory directly inside `rightkit-qa` (no symlink followed, nothing outside the root); its name is `<label>-<16 lowercase hex>` or `<label>-<6 letters or digits>`; no pid its records name is alive (the run record's `ownerPid` through the binding's `runRoot`, and the pid in a home marker that has no binding); and nothing in the home, the directory included, was modified within `RIGHTKIT_QA_HOME_MAX_AGE_SECS` (default 2 h). Not checked: processes that have the home as working directory or an open file, and the run record's lease. A symlink entry is reported as retained ("symlink skipped"). Homes that have an owner marker keep their rule. Behaviour change: homes that were kept before are now removed, including those of runs cancelled within the last 24 hours.
- `rightkit-qa guard` follows the "QA control never ships" rule (`src/guard.rs`). The registration may sit under `#[cfg(feature = "qa-native")]` with or without `debug_assertions`, so release-derived dev builds (`--profile release-iterate`) can carry the server. The `compile_error!` for non-debug builds is no longer required, and the older debug-only gate is still accepted. Rejected: an unconditional registration, including a `not(feature = "qa-native")` gate; a non-optional `rightkit-control` that enables `qa-control`; `qa-native` in `default`, directly or through another feature; `qa-native` without `rightkit-control/qa-control` (or dependency-level `qa-control`); and any other feature that enables the dependency. A gate may sit on an enclosing function or block. `use` lines and comments no longer count as registrations. Each message names the file and the change to make.
- QA runs never touch real user data. New `userdata` module: `Guard` runs inside `control::launch` (home must be a created QA root under a system temp root; working directory and every absolute environment path must resolve inside it) and in the engine launch paths (`data_dir` and data/home/profile/config environment paths must be in a temp root). Refused with a typed `UserDataViolation { path, rule, detail }`: Documents, Desktop, Downloads, Pictures, Music, Movies, iCloud Drive, OneDrive, Dropbox, Google Drive, the app's real application-support / AppData / config directory, `/Volumes/*`, UNC paths, and any symlink that resolves into them. No opt-out. Behaviour change: a `RIGHTKIT_QA_HOME_ROOT` or `RUNNER_TEMP` outside a temp root, or in one of these places, is now refused at launch. `userdata::seed_from` copies seed state through a caller transform and refuses the real data of the app under test unless the scenario declares the copy scrubbed and a verification callback returns true. `StopReport::permission_dialog()` reports dialog agents in the sampled foreground names; `Control::assert_no_permission_dialog()` is a documented no-op (no window-by-owner enumeration in `rightkit-control`).
- QA home hygiene. Each home records its owner in `.rightkit-home.json`. `workspace::dispose` deletes a home only when it is a runner-created home. At run start `workspace::create` removes homes whose owner process is dead and that are older than 2 h (`RIGHTKIT_QA_HOME_MAX_AGE_SECS`), then returns `RootOverCap` (naming the largest homes) when the root holds more than 4 GB (`RIGHTKIT_QA_ROOT_CAP_BYTES`, `0` disables). `Harness` drop removes its home on pass and fail unless `with_keep_failed_home(true)` / `RIGHTKIT_QA_KEEP_FAILED_HOME=1`, which keeps only the failed run's home and prints its path and size (`suite::run` does the same). New `storage::clean_homes`, `storage::clean` and `rightkit-qa clean [--dry-run]`. `sweep_homes` no longer removes a home whose recorded pid is alive. Nothing here was compiled or run.
- Sidecar buffers are bounded. `Sidecar::events` keeps the newest frames (default 2,048; trimmed in batches once it reaches twice the limit, so it holds 2,048 to 4,095), and engine stderr keeps its last 256 KiB, cut on a line boundary where possible, with a `[N bytes of earlier stderr dropped]` marker in `stderr_tail()`. `SidecarStatus` gains `events_dropped` and `stderr_dropped_bytes`; `Sidecar::set_event_limit` and `set_stderr_limit` change the limits. A request still sees its own id as the frame arrives, so a trimmed frame cannot turn a timeout into "did not answer".
- Retention lock (regression: parallel scenarios failed with "QA retention lock is held" since 0.2.13/0.2.14). The lock guards only the prune pass, but `storage::create` held it across the prune AND the run-directory creation and failed after 5 s, so a slow prune (large tree, several processes) failed an unrelated scenario. A starter now takes the lock without waiting: if another process is pruning, it skips its own pass and starts (run ids are claimed with an atomic `create_dir`). An explicit `prune*` waits up to 120 s, then fails with a message starting `storage::LOCK_HELD` (`storage::is_lock_held`). A lock whose owner process died, or that never got an owner file within 30 s, is recovered; the lock is released on drop, including a panic. Introduced in commit 3548fc7a.
- App-home sweep. Homes under `<tmp>/rightkit-qa/` were only reclaimed through their run record, so a home whose run root was deleted (a killed process, a test run inside another home's scratch) was never found again. `storage::sweep_homes` also removes homes with no run record older than 24 h and homes of finished runs older than 24 h, then the oldest finished homes while the total exceeds 4 GB (only when removing them can meet the bound). Live runs, young orphans and directories without a `.rightkit-app.json` binding are never removed. `workspace::create` runs it at most every 10 minutes (set `RIGHTKIT_QA_HOME_SWEEP=0` to skip). New `rightkit-qa homes [--apply]` reports what it would remove (dry run by default).
- `RIGHTKIT_QA_HOME_ROOT=<absolute dir>` moves homes to `<dir>/rightkit-qa/`. The default is unchanged: homes stay on internal storage because a launchd-started macOS app cannot open its live log on an external volume (`control::launch`) and the control socket path must fit `sockaddr_un`.
- `workspace::create` now creates every directory its exported environment points at (including `WEBVIEW2_USER_DATA_FOLDER` and the suite root) plus the per-user directories platform known-folder lookups resolve under the isolated profile: Windows `AppData\Local`, `AppData\Roaming`, `AppData\LocalLow` and the `Desktop`/`Documents`/`Downloads`/`Music`/`Pictures`/`Videos` folders; macOS `Library/Application Support`, `Caches`, `Preferences`, `Logs`; Linux `.local/share`, `.local/state`, `.config`, `.cache`. Windows expands the registry's `%USERPROFILE%\AppData\Local` against the overridden USERPROFILE, so with the directory missing `SHGetKnownFolderPath` failed (Tauri "unknown path", `dirs::cache_dir()` None). Gap ledger #92 (2). A platform-neutral test asserts each exported path under the home exists as a directory.
- The live app log now goes to `<home>/.rightkit-qa/` instead of directly into the app's HOME, so apps that list or watch HOME do not see their own log writes as directory changes.
- Launch timeout errors on Windows say when the harness process is in session 0 or on a non-visible window station (SSH, service) and that a hidden WebView2 app cannot get a ready window from there; the window-ready error also reports whether the process was alive. README Windows section documents it. Gap ledger #92 (1).

- Sidecar frame shape follows the hello again. The 0.2.16 `sidecar_command` default (rightkit-jobs frames for every engine) broke GenRight's engine, which never answers that shape, so three scenarios that passed on 0.2.15 waited out their timeout. The shape is now read from the hello captured at spawn: a `contract_version` field means the rightkit-jobs contract, an `rpc_version` field (GenRight's `EngineFrame::Hello`) means the legacy GenRight frames, and a hello with neither keeps the jobs contract. The per-command `legacy_status_frames` option and `Sidecar::legacy_status_frames = true` still force the legacy frames; `Some(false)` forces the jobs contract. New `Sidecar::set_frame_shape(Option<bool>)` pins the shape for the whole sidecar in either direction and is what `sidecar_start` now uses, so an explicit `false` in a scenario overrides detection. When the hello names neither shape and a command gets no frame for its request id before the timeout, the error says the engine did not answer the frame shape that was sent, names it, and names `legacy_status_frames` as the switch. The timeout is unchanged.
- Windows background invariant. `StopReport::owned_never_frontmost` was always `false` for a hidden or background launch on Windows because nothing sampled the foreground owner. The focus monitor now reads the foreground window's owning pid (`GetForegroundWindow` + `GetWindowThreadProcessId`) every 20 ms and compares it with the started pid, registered the instant the process is spawned. The flag is `true` only when no sample found that pid in front and no foreground owner was unreadable; a moment with no foreground window counts as nothing owned in front. The check covers the started pid only, not helper processes. The macOS check is unchanged.
- The README no longer says this crate has no changelog, and states exactly what the Windows hidden launch checks.
- Windows pointer path: none of `control.rs` `move_to`/`pointer`/`click`/`screenshot_*`, `launch_env`, `QaWorkspace` creation or `process.rs` changed between 0.2.12 and 0.2.14, so this release makes no pointer change. Gap ledger #74 (Pulse hub journey, Windows: Folders radio shows no hover or pressed state under 0.2.14) is not attributed to a code path in this crate. Pulse's run with every other change kept and `=0.2.12` restored passed (CI run 38086940130), so the cause is still open; Pulse stays on `=0.2.12` until its Windows leg passes on this release.
- `sidecar_command` now speaks the rightkit-jobs contract by default (`{type:"request", id, method: name, params: input}` answered by `{type:"response", id, ok, result | error:{code,message}}`). GenRight's old frames (`method:{method:"command",...}`, `status: ok|err`) stay behind `legacy_status_frames = true`, set on `sidecar_start` for the whole sidecar or on a single `sidecar_command`. Behaviour change for scenarios that relied on the old default: add the option.
- Unit tests cover the foreground classification and the fail-closed rule on every platform.

## 0.2.15 - 2026-10-10

- `rightkit-control` is now a macOS-only target dependency with `default-features = false`; only `mac::frontmost_name` and `mac::frontmost_pid` were used, and Windows builds no longer compile it.
- Drop `libc`: orphan-sweep liveness (`storage::pid_live`) now uses `rightkit_process::AdoptedProcess::is_running` on every platform (replaces `libc::kill` on Unix and a `tasklist` spawn on Windows). A process whose state cannot be measured counts as live.
