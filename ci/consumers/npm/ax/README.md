# @rightkit/ax npm consumer (draft, npm.@rightkit/ax)

Packed-archive consumer for `@rightkit/ax` 0.3.2 (workspace version). Recipe ID: `ax-plugin-gates-report-consumer`. The unit is installed only from the sealed `file:` archive. The reviewed closure has no registry dependencies: the package declares none and imports only Node built-ins. No `@rightkit/*` package is in the closure.

Surface (exact `exports` keys, 13): `./manifest`, `./ax/static`, `./ax/conformance`, `./ax/behavioral`, `./ax/adversarial`, `./ax/ownership-review`, `./ax/report`, `./plugin/scaffold`, `./plugin/validate`, `./plugin/portable-core`, `./plugin/hooks`, `./plugin/skill-gate`, `./plugin/marketplace`. The package has no `.` export, so the consumer resolves each subpath with `import.meta.resolve` and binds the installed files to the archive through `./ax/static`, which sits one directory below the package root. It also ships the `right-ax` bin, which the consumer runs as `node cli/right-ax.mjs`.

Scenarios (13):

1. Installed manifest bound to the archive, and the exact sorted export names of all 13 modules (74 names in all), so an unintended API change fails qualification; the tarball ships no tests or fixtures and does ship the CLI, the manifest schema and the pinned plugin schemas.
2. The installed CLI: `--version` prints `right-ax <version>`, `--help` lists the commands, `plugin init <dir> --help` writes nothing, a missing target, an unknown flag, a stray positional and a target starting with `-` exit `2` before anything is written, `plugin init` then `plugin validate` succeed on a scaffolded CLI skill, an existing `plugin.json` is refused, and a vague description cannot be scaffolded.
3. `loadManifest`, `manifestPathFor` and `manifestSchema`: a valid `.rightax.json`, a missing file, invalid JSON, schema errors (a conformance example that is not an object), semantic errors (generated paths that are not exact repository-relative paths) and a duplicate adapter identity.
4. The skill description gate: the length constants, a passing description, and each failing rule (length, opening, vague text, filler, trigger phrases, frontmatter and a name that differs from its directory) with the finding shape; `parseSkillFrontmatter`.
5. `scaffoldPlugin` with its builders, `validateRepoLayout`, `detectLayout`, `loadPinnedSchemas`, `lintPluginMetadata`, and the hooks module: a CLI skill (one skill, three manifests, no `mcp.json`, no findings), an optional MCP command, hooks with a shim, refusals that write nothing, the schema, path-containment and unknown-field findings, a Claude-native layout, `buildHooksFiles` and the `validateHooks` findings (missing or escaping script, absolute machine paths, a user-home path in a script).
6. The portable core: `assemblePortableCore` with a skill, an agent and a hooks manifest, `validatePortableCore` and `validatePortableCoreContract`, `normalizeClientProjections`, `validateResourceClosure`, refusal of private or personal skills, and detection of a file the contract does not declare.
7. The marketplace: `parseSourceList` refusals, `buildClaudeMarketplace` and `buildCodexMarketplace` (git-subdir, url and vendored `local` sources), `renderMarketplaceFiles`, `buildMarketplace` with drift checking, `workspaceIsMarketplaceRoot`, and `validateMarketplace` over a repository that vendors its plugins (valid, stale generated file, vague skill description, missing local path, missing source list).
8. The static contract: all fourteen rules over a well-formed tool set (pass) and over failing sets, the live path that lists tools from a stdio MCP server inside an artifact root outside the repository (`fetchLiveTools`), the artifact being unchanged, the missing-artifact-root fatal, and `grepRepoForTokens` skipping vendor directories.
9. Conformance against a live MCP server: a tool that follows the contract passes all three probes and its structured content validates against its output schema, a tool that does not fails, a declared example replaces the synthesized arguments, typed fatals (no MCP surface, a server command outside the artifact root, an artifact root inside the repository), `buildValidArgs`, `tryParseJson`, `evaluateProbe` and `runBlockingCapabilityProbe` (including its fail-closed result without a harness binding).
10. Behavioral scenarios: scenario loading, the environment verified before any claim, claim, reason-code and budget failures, `stubTrial`, the stub run reporting `provenBy: stub`, a declared two-agent matrix with five trials each reporting `real-matrix` while an undeclared roster or a 3-and-2 split does not, a failing scenario, the no-scenario and unparsable-scenario fatals, and `runMatrix` refusing an invalid configuration before it starts any agent.
11. Adversarial cases: canary replacement in every leaf, a clean response, and failures for an echoed canary, a stack trace, a machine path, an oversized response, an unexpected status and a throwing call; invalid, duplicate and missing-digest fatals; failed sessions closed once; and a live session against the MCP server whose digest equals the conformance digest.
12. The report: `aggregateReport`, `renderMarkdown`, `toSarif` and `gateExitCode` over the real results above (a failing conformance row is never masked, the behavioral claim stays UNPROVEN, `signoff` is `null`), a passing report, a report-only gate that still fails, a forged verdict that cannot hide a failing leaf, mismatched artifact digests and no executed gates.
13. Ownership review: `OWNERSHIP_REVIEW_LIMITS`, `buildOwnershipReviewPacket` over a two-commit repository made in the scenario (bounded, advisory, no authority to approve or block), over-policy limits and unsafe refs refused, `writeOwnershipReviewPacket` never overwriting, `readOwnershipReviewJson`, `assertOwnershipReviewPacket`, and `validateOwnershipReviewReceipt` accepting a fully supervised receipt and refusing incomplete evidence, ungrounded findings, an excessive cost, another request's receipt and a tampered packet.

Everything is created under a private directory in the OS temp directory and removed at the end; nothing is written inside the install. Two kinds of child process run: `node` (the CLI, and a hand-written stdio MCP server written into the artifact root) and `git` for the last scenario, with no user or system git configuration. The MCP server is started as the bare command `node`, which must resolve on `PATH`. No network, no credentials, no user data, no URL is fetched (every URL in the marketplace fixtures uses the reserved `.invalid` TLD or is never contacted).

`resolvePluginRoot` is reached only through `validateMarketplace` and is not called by name. Not covered: `right-ax ax` and `right-ax adopt` through the CLI, a real-agent matrix (`runMatrix` against a configured agent command), `marketplace validate --fetch` (it clones from the network), and the generated Codex and Claude hosts themselves. The extra CLI commands run the same library modules that the exports reach.
