# rightkit-sync 0.2.2 registry consumer

Standalone consumer, outside the workspace, pinning `rightkit-sync =0.2.2` exactly with its default features (`helper` and `process-usage`, which is what HeardRight, ScrapeRight and Pulse's membrane runtime link). It installs the crate from the sealed archive through the offline directory registry and runs `src/main.rs`, which exits non-zero on the first failed assertion. `serde_json` is the only other dependency; the consumer uses it for the helper protocol's JSON and for the stand-in helper.

The engine is driven against the crate's in-process `MemoryBackend`. The `helper` module is driven against a real child process: this same program, started again with `--fixture-helper <zone-file>`, answers the `rightkit-sync-helper/1` line-JSON protocol over an on-disk zone, which is what the Swift CloudKit helper does on a Mac. The crate's own protocol fake is a repository-only binary that the published package does not ship, so the stand-in is part of this consumer.

## What it proves

- The engine over two devices sharing one zone with a multi-page feed: every note downloads, a concurrent edit is settled last-writer-wins, a tombstone beats a concurrent edit, clears the record's content, removes the local copy and is not uploaded again, and the pass counters (`SyncMetrics`, `SyncStatus`) add up.
- Offline and partial failure: an offline pass is `Failed` with the backend's 15 s hint and the next call inside the window is `Deferred`; a zone that accepts only part of a batch leaves the pass `Pending`; a new engine over the same on-disk ledger (`FileStorage`) uploads only the remainder. The ledger file is JSON, replaced atomically with no temporary file left behind, and owner-only on Unix. `LedgerStore` persists before it returns, rolls back a failed save, and restarts empty (`recovered_from_corruption`) from bytes it cannot decode.
- A token the backend no longer honours is replayed once, a record no mapper can decode is quarantined and counted without blocking the page, `request_full_replay_once` replays once per flag, and a local deletion the app did not report is inferred and written as one tombstone when `infer_local_deletions` is on.
- `PassHooks`: outbound records are written at the start of a pass, a response to a foreign record is written before the request is acknowledged, a failed response write fails the pass without advancing the feed, and `on_account_switch` is called on consent. `NoHooks` does nothing.
- Account handling: an auth generation that changes during a pass cancels it without committing feed progress; `Disabled` and `Unavailable` are reported; the consent gate (`require_consent_on_scope_change`) pauses a switched account with `ConsentRequired` and writes nothing to the new account, survives a restart, accepts `Merge` or `StartFresh` (the withheld set keeps existing items out of the new account, and nothing local is deleted), refuses an unsolicited, mismatched or stale answer, and is cleared by signing back in; with the gate off the ledger is reset silently.
- Conditional saves against a concurrent writer: a newer remote write between the fetch and the save wins, an older one is overwritten on top of the server's change tag, and a remote tombstone wins over the local edit. A custom `ConflictPolicy` replaces last-writer-wins (`LastWriterWins` is checked on its own), a download the app cannot land yet (`ApplyOutcome::Deferred`) is kept in the ledger and retried every pass, and `LocalStore::list_page` gives the same result at page sizes 1, 2, 3 and 100 while a store whose pages never advance fails the pass instead of looping.
- Scheduling: `sync_once` with `SyncBudget` and `SchedulePolicy` (a success waits the idle period, a failure carries the backend's hint, a deferral ends the call, a drain loop runs several passes inside its budget, consent maps to `Failure` with no next run), and the pure helpers `next_delay`, `work_outcome`, `should_continue` and `BackoffPolicy::delay_secs`, with their defaults.
- The data types: `RawRecord`, `FieldValue` (every accessor), the field-name constants, `write_tombstone` and `read_tombstone`, `SyncError` (messages, `retry_hint_secs`, `std::error::Error`), `SyncConfig::default()`.
- The `wire` module: base64 (RFC 4648 vectors, whitespace skipped, an error that names the byte), `WireRecord` and `WireValue` with the exact JSON shape and an exact round trip with `RawRecord`, `WireError` mapping both ways, and `Request`, `Response`, `ok_line` and `err_line`.
- The `helper` module over the child process: `HelperConfig` (builder, defaults, the `cloudkit` arguments), `HelperProcess` (nothing starts before the first call, one long-lived child, helper errors are data, a call after `shutdown` starts a new child), and `CloudKitHelper`, `HelperBackend` and `HelperAuth` under two engines on one zone with a multi-page feed, tags, an asset-sized byte field (300 000 bytes), last-writer-wins, tombstone-wins, a stale change tag refused with the server record, and a helper restarted after `shutdown`. Faults: a crash mid-pass (the next pass starts a new child), a throttled helper whose 77 s hint beats the base backoff, a signed-out helper (`Unavailable` with its detail), the user's toggle (`HelperAuth::set_enabled`, `Disabled`), a token expiry and a deleted zone (replayed without losing local data), a switched account (the ledger rebinds, the old account's pending deletion never reaches the new zone, the old zone is untouched), and a helper program that does not exist (`Unavailable`).

## What it deliberately does not prove

- The `cipher`, `http` and `drive` features. They are off, and no app enables them (`http` is parked).
- The real Swift CloudKit helper, real CloudKit and an iCloud account, which need a Mac with an entitled helper. The stand-in speaks the protocol; it is not the helper.
- Android scheduling (`sync_once` is checked as a pure function, not under WorkManager) and a ledger the size the runtime budget names (100 000 records).
- `MemoryBackend::delete_record` (a fixture helper that removes a record from the in-process zone with a feed entry), and the `#[doc(hidden)]` diagnostics `CloudKitHelper::debug_call` and `CloudKitHelper::backend_debug_write`. They are not part of the sync contract and are never called.
- Timing under load: the stand-in reads and writes its zone file on every request, so the run is short but not a performance measurement.

State: a per-process directory under the OS temp directory, removed at the end, and one short-lived copy of this program per simulated device. No network, no credentials, no real user data. No step sleeps; the longest wait is a 30 s request deadline that no scenario reaches.
