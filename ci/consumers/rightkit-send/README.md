# rightkit-send 0.2.0 registry consumer

Standalone consumer, outside the workspace, pinning `rightkit-send =0.2.0` exactly with its default features (no `multicast`, no `bonjour`). It installs the crate from the sealed archive through the offline directory registry and runs `src/main.rs`, which exits non-zero on the first failed assertion. `serde_json` is the only other dependency (error codes and wire types are JSON).

Default features are the configuration of a host that feeds discovery itself, which is what the crate's README prescribes for iOS. They are chosen on purpose: `multicast` announces on UDP multicast and sweeps the local networks, `bonjour` talks to the system mDNS responder, and neither belongs in a hermetic run. Pulse enables `multicast` (and `bonjour` on macOS); the code those features add is not run here.

## What it proves

- `Identity`: `generate` gives a fresh certificate and key whose fingerprint is the lower-case SHA-256 of the certificate (`net::sha256_hex`, `net::valid_pin`), `load` restores a stored pair to the same fingerprint, a certificate with another identity's key, corrupt bytes and empty bytes are refused, and `Debug` shows the fingerprint but never the key.
- `Policy::default()` and its effect: `max_file_bytes` (an oversized offer is answered 400 before any card), `max_message_chars` (a longer text is cut to that many characters, not bytes) and `answer_wait` (an unanswered request is declined and its card withdrawn).
- `Error` and the trust types: stable serialised `code` tags and payload names, `Display` text, equality, `std::error::Error`; `TrustState` parse, `as_str` and serde forms, `normalize`, and the `PROOF_*` and `MAX_UNDECIDED` constants.
- The `proto` helpers: `sanitize_component` and `sanitize_relative` (traversal, separators, control characters, length and the eight-component limit), `reserve_unique` (`name (1).ext` numbering, nested folders, nothing outside the base folder), `mime_for`, `random_hex`, `url_encode` and `url_decode`, the wire types with their protocol defaults and camelCase names, and `is_message`.
- `send::expand` and `Entry::open_reader`: files, folders (structure kept, symbolic links skipped on Unix), text entries (empty text dropped, size in bytes), a reader that is fresh on every call and reads the file as it is now, `NothingToSend` and `Unreadable`.
- `Service`: `start` (the port 0 case, `bound_port`), `snapshot` and `status`, the `/info` answer over pinned TLS, the default state (`Ask`, `Deny`, and `Allow` refused as a default), per-device `set_trust`, `set_label`, `forget` and `devices_trust`, persistence of those records across a stop and a new start on the same trust file, `peer_add_resolved` (a 64-hex fingerprint is required and stored lower-case, the TXT keys `model`, `type` and `px`, loopback addresses are not taken as peers), `peer_remove`, `forget` refused while the device is listed, `send` refused before any connection (`DeviceNotNearby`, `DeviceBlocked` by fingerprint and by alias), `cancel` and `respond` on unknown ids, `set_save_dir`, `dismiss`, `stop` (prompt, the port free at once, three restarts on the same port), `PortInUse` for a second service and for a port another program holds, and `Error::Identity` for an unusable identity.
- A real TLS exchange on 127.0.0.1 between the crate's sender `send::deliver` and a running `Service`, with the sender presenting its own certificate: the owner's card (alias, model, fingerprint, address, counts, file names, `verified`), accept and decline, progress phases and byte counts, the received file intact with mode 0644 on Unix, the transfer record on the receiving side, the trust record with `certificate` proof, a text message that is not shown before it is accepted and never written to disk, Allow with certificate proof (no card, an existing name is never overwritten), the clipboard flag, a folder with its structure, Deny (no card, nothing saved), a peer whose certificate is not the one its fingerprint names (`PeerIdentityMismatch`), a peer on plain HTTP (`PeerPlaintext`), a malformed pin (`InvalidIdentity`), and a closed port (`PeerUnreachable`).

## What it deliberately does not prove

- UDP multicast discovery and the network sweep (`multicast`), and Bonjour advertise and browse (`bonjour`). Their code is not compiled in this configuration.
- The quarantine mark on macOS and the Mark of the Web on Windows. The consumer's sender always proves its key, and for a proven sender a failed mark is only logged, so the files are kept either way; no assertion reads the mark.
- `Service::send` connecting to a listed peer. The host-fed device list refuses loopback addresses (they are this device) and the consumer sends nothing to any other address, so the same code path is exercised through `send::deliver`, which `Service::send` calls. Nothing is proven about `Service::send`'s transfer records and events.
- Senders that cannot prove their key (no client certificate): the unverified folder, the unproven size and count limits, and the connect-back proof.
- The low-level transport items of `net`: `server_config`, `accept_tls`, `connect`, `connect_within`, `read_request`, `read_body`, `write_response`, `call`, `prove_key`, `set_user_agent`, `Wire` and `Request`. `Service` and `send::deliver` call them, so they run in every exchange above, but the consumer never calls them itself and asserts nothing about them directly (`net::request_json`, `net::sha256_hex`, `net::valid_pin` and `net::set_client_identity` are called directly). `Service::refresh` is a no-op without the `multicast` feature and is not called.
- Any real device, phone, router or Local Network permission prompt.

State: a per-process directory under the OS temp directory, removed at the end. TCP on 127.0.0.1 only; each service listens on an ephemeral port on all interfaces while it runs and is stopped before the next one starts, and the process-wide client identity is set before every send. No network, no credentials, no real user data. The whole run takes a few seconds; the longest bounded wait is 20 seconds per awaited event, and the answer-wait case uses a 300 ms policy.
