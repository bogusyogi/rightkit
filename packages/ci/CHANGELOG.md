# Changelog

## Unreleased

- **`release` lane (rust-hybrid): the trusted publisher.** A dispatch-only workflow whose `publish` job, in the protected publication environment, is the only place the R2 write credential (`CLOUDFLARE_API_TOKEN`) exists. A native host signs, seals and qualifies through `rightkit-gate --to qualify`; `rightkit-gate stage --platform <p> --tier <t>` puts the sealed set and receipt in the draft release `rightkit-staging-<commit>` and dispatches this workflow. The workflow runs class A on that commit (check job), then `rightkit-gate --to release --receipt-in` per platform, which takes the receipt only for that commit and source, refuses bytes that differ from the sealed digest or were never qualified, and uploads exactly them; the staging draft is deleted after.
- **One door in app CI.** The rust-hybrid `ci` job and the `regenerate` re-check run `rightkit-gate --to compile` (class A, then every compile, lint and test scan), never the repository's gate script; `gate.path` is only the Rust-change filter. `gate.shards` and `gate.quick` are refused. The `check` job provisions class A's pinned tools (cargo-deny 0.20.2, cargo-audit 0.22.2, actionlint 1.7.12) so `rightkit-gate check` runs class A in full; a missing tool fails the check. Pins in `render.test.mjs` were retaken deliberately; the consumer recipe's shard scenario now asserts the refusal and its sha256 is re-pinned.

## 0.3.1 (2026-10-25)

- **RightKit check job in the lanes that compile or test (rightkit#833; pipeline invariant P1, lane A gap A-11).** `ci`, `qualification`, `package-smoke`, `release-candidate`, `swift-check` and `publish-npm`, on both profiles, render a `check` job right after `private-repo-guard`: it needs only the guard, checks out at depth 1, installs the repository's dependencies with a frozen lockfile and no lifecycle scripts, then runs `rightkit-gate check --commit HEAD` from the installed `@rightkit/release` (committed files only; needs 0.6.5, the first release with `check`). Every other job needs it, directly or through a job that does: `test` (node `ci`), `ci`, `quick`, `qualification`, `clean-tarball`, `candidate`, `swift-check`, `publish-npm`, the release chain's `admission` and the parallel `dev-artifact-*` jobs (`CI_NEEDS` becomes `[private-repo-guard, check]`, or `[private-repo-guard, check, quick]` with `gate.quick`). The `ci` lane's check job also prints the stale-lockfile patch, since the ci job no longer runs when the install fails first. A release-candidate checks `inputs.source_revision`; `publish-npm` checks the release tag (`github.event.release.tag_name`) it then rebuilds with `build-candidate.mjs`, verifies with `check-release.mjs` and publishes with `id-token: write`, and its check job holds no permission, environment or secret. Not rendered: `regenerate` (it repairs what the check flags, and `@rightkit/release` admits it only as `needs: [private-repo-guard]`), `sign-existing` and the `supersede` job (same policy), `publish-package-managers` (it builds and tests nothing: it syntax-checks the committed formula and publishes metadata of a released version), and the `workflows` block. `CHECK_JOB_LANES` and `checkJob` are exported from `manifest.mjs`.
  - **Breaking render change, no flag.** Every render of those lanes changes, so a repository must depend on `@rightkit/release` 0.6.5 or later before it syncs. Pins in `render.test.mjs` were taken again deliberately: the nine `SW_BASELINE` renders (`node/publish-npm` included) and the three shard-case renders; each is also asserted against its previous hash with the check job and the `check` entries removed (`withoutCheckJob`), which proves the job is the whole change. The three lanes without a job keep their hashes. Legion's own manifest renders its committed workflows byte for byte before the change; after it, `ci.yml` and `release-candidate.yml` gain exactly the job and the `needs` entries.
  - **`right-git sync` and `install` check the `@rightkit/release` pin.** When a lane that renders the check job is declared, `planSync` reads `devDependencies` (else `dependencies`) of `package.json`: an exact pin below 0.6.5 is refused at stage `dependency`, before anything is written; a range, a non-registry spec, an unreadable `package.json` or no dependency adds a warning (`plan.warnings`), which the CLI prints as `  warn: ...` on stderr without changing the exit code. A manifest whose lanes render no check job (`regenerate`, `sign-existing`, `publish-package-managers`) is not asked. `sync.test.mjs` and `cli.test.mjs` cover it; the Membrane release-chain case now pins 0.6.5.
  - **The install is not filtered to `@rightkit/release`.** `pnpm install --filter @rightkit/release...` selects workspace projects; in a consumer the package is a registry dependency, so the filter matches nothing, installs nothing and exits 0, and `pnpm exec rightkit-gate` then fails. npm and yarn call `./node_modules/.bin/rightkit-gate` by path because `npm exec` fetches an unknown name from the registry in CI.
  - **Consumer recipe.** `ci/consumers/npm/ci/consumer.mjs`, scenario `gate-shards-render-matrix-group-and-summary`, pinned the previous `quick` and `ci` `needs` lists (three assertions); they now expect `[private-repo-guard, check]`, `[private-repo-guard, check, quick]` and `[private-repo-guard, check]`. The recipe's sha256 in `ci/consumer-recipes.json` still has to be re-pinned by a person.

- **`right-git` puts out everything it wrote before it exits.** The CLI ended with `process.exit()` while stdout was still queued, so when the reader of a pipe had not caught up (`right-git sync --dry-run | tee log`, a CI log collector) the end of the diff and the `would change` line were lost, about one run in ten. The CLI now waits for stdout and stderr to take their queued writes before it returns the exit code (help, `--version`, every command and an unknown command alike); `cli.test.mjs` delays every stdout write to make the queue deterministic.

- **`gate.shards` and `gate.quick` (rust-hybrid `ci`; rightkit#950, Orthic-Labs/legion#117).** A gate that runs everything in one step per runner is as slow as its parts: Legion's macOS gate took 2h35m. The new keys split it:
  - `gate.shards: [{ id }]` adds a `matrix.shard` dimension, so the gate runs once per shard per runner as `bash <path> --group <id>`, on the same Rust cache key.
  - Last-green markers, QA evidence artifact names and the default-branch job concurrency group carry the shard id, so legs never share state.
  - `gate.quick: true` adds a `quick` job (`bash <path> --quick`, `ubuntu-24.04`, 20 minutes) that every leg needs.
  - A `ci-summary` job (`if: always()`) passes only when every leg passed, and `quick` when set. It is the stable status check, since matrix job names follow the shard list.
  - Validation: 2 to 16 shards; ids `^[a-z0-9][a-z0-9-]{0,31}$` and unique; `quick` needs `shards`; a `devArtifact` must be `parallel: true`, because one staged inside the ci job would be built once per shard.
  - Without `shards` the render is byte-identical. Three manifests are pinned by hash to the previous render (`render.test.mjs`), and Legion's own manifest renders identically. The sharded render passes the pinned actionlint 1.7.12.

## 0.3.0 (2026-10-17)

- `workflows` manifest block (Orthic-Labs/rightkit#465, #437): named workflows rendered by code beside the lane files. `kind: "custom"` takes a filename, `push`/`pull_request` triggers with `paths`, a plain `workflow_dispatch`, `pwsh`/`bash` steps with `workingDirectory`, a named artifact (retention, `if-no-files-found`, `{sha}`/`{run_id}`/`{run_attempt}`/`{os}`/`{matrix.<key>}` tokens), per-workflow sparse checkout and long paths, a per-workflow concurrency group and a `dtolnay/rust-toolchain` version pin. `kind: "swift-host"` runs `swift test` per package on Windows and macOS matrix hosts. `kind: "dispatch-matrix"` renders `workflow_dispatch` inputs, a plan job emitting a matrix, per-item jobs and a collect job; inputs reach scripts as `RIGHT_GIT_INPUT_<NAME>` environment variables. Every rendered workflow pins actions to commit SHAs, requests `contents: read`, refuses private repositories through the shared guard job, sets `persist-credentials: false` on every checkout, keeps the ownership scan and refuses any step that mentions `secrets` or interpolates untrusted event data. New `workflows.mjs`, `workflows.test.mjs`; `manifest.schema.json` documents the block. No manifest without `workflows` renders differently. `@rightkit/release`'s `right-git-ci-only` policy accepts only `<lane>.yml` files, so a repository that declares `workflows` needs that policy extended before its release check passes.
- `swift-toolchain` step (Orthic-Labs/rightkit#436): `toolchain.swift { version, sha256 }` renders, on Windows runners only, `<pm> exec right-release toolchain swift --version <v> --sha256 <pin> --github-env` (needs `@rightkit/release` with `right-release toolchain swift`). `swift-host` requires it when its `os` includes a Windows runner.
- `right-git artifacts fetch` (Orthic-Labs/rightkit#439): downloads a run's artifacts through `gh`, merges the per-job artifacts into one tree (conflicting bytes fail), verifies `--expect-sha256` (one file with `--file`, otherwise the tree digest) before anything reaches `--out`, and writes a JSON receipt with `--receipt`/`--json`. New `artifacts.mjs`, `artifacts.test.mjs`.

## 0.2.49

- One CI run per repository (Orthic-Labs/rightkit#338; 0.2.49 is still unpublished, the registry's latest is 0.2.45, so this joins 0.2.49). The `ci` lane now renders a `supersede` job as the only job with `actions: write` (job permissions `contents: read` and `actions: write`, push to the default branch only, `needs: [private-repo-guard]`, `ubuntu-24.04`, 5 minute timeout). It runs the new `supersede.mjs` (embedded verbatim through a heredoc; pure `decideSupersede` function, tested in `supersede.test.mjs`). For every older in-progress or queued run of the same workflow on the default branch, it cancels the run when it never started, when any of its jobs has failed or timed out, or when its elapsed time is under `graceFraction` (default 0.7) of the median duration of the last `medianWindow` (default 10) successful push runs; otherwise it leaves the run alone. With fewer than 3 successful runs there is no median and nothing is cancelled for being young. A failure inside the script only warns and never fails the gate. To keep a nearly done run from being overlapped, the workflow-level group of a default-branch push becomes the run's own id (so its `supersede` job always runs and it is never queued or cancelled at workflow level), and the `ci` (node: `test`) job gets a job-level `concurrency` group `<workflow>-main-<os>-<node>` with `cancel-in-progress: false` for default-branch pushes (a unique group for every other event, so pull requests are not serialised against main). A newer run therefore waits for a kept run, and GitHub drops all but the newest waiting job, so there is never more than one run in progress. `cancel-in-progress` is `${{ !(push to the default branch) }}`: pull request runs still cancel superseded runs. New optional `concurrency.graceFraction` (number above 0, at most 1) and `concurrency.medianWindow` (integer 1 to 100); not allowed with `queue`.
- `concurrency.mainPushes: "queue"` now requires a non-empty single-line `concurrency.reason` (schema and validation), rendered as a YAML comment above the `concurrency` block: `# concurrency.mainPushes queue, recorded exception to one CI run per repo: <reason>`. `queue` renders no `supersede` job and keeps the previous per-ref group and expression, and `reason` is refused without `queue`. A manifest that already uses `queue` fails validation until it records a reason. The publish workflow is untouched: it never cancels.
- Every default ci render changes (new job, group and expression); no hashed baseline covers a ci lane (`SW_BASELINE` pins only the swift-check renders), so no baseline hash changed. Needs `@rightkit/release` with the `right-git-ci-only` policy change that accepts `actions: write` in the exact `supersede` job shape; until then a repository's release check refuses the managed ci.yml.

- `signExisting.macPayloadMetadataSource` (optional): a repository-relative path to a generated payload metadata file. When set, every macOS unsigned dev packaging step (`devArtifact.mac` `sign`, `notarize` or `unsigned`, gate job and parallel `dev-artifact-mac`) stages the `.app` (wrapper layout kept) plus that file and zips them, so the file sits at the inner-zip root under the name given by `macPayloadMetadata` (which must be a bare file name); the step fails if the file is missing. Needs a `devArtifact.mac` leg. Unset, the render is byte-identical.

- rust-hybrid lane `sign-existing` with config `signExisting { macSignManifest, macPayloadMetadata, environment? }` (Orthic-Labs/rightkit#257): a manual-only `sign-existing.yml` workflow for public repositories whose signing must run on protected CI. `workflow_dispatch` inputs `run_id`, `artifact` (artifact id or name) and `source_sha`. The `sign-existing` job (default branch only, the repo's signing environment, `contents: read` and `actions: read`, macOS runner from `matrix.os`) first checks through the GitHub API that the run belongs to this repository, was built from this repository (no fork), completed successfully, and has a head sha that starts with `source_sha`; that exactly one non-expired artifact of that run matches `artifact` and records the same run id, head sha and repository; and that the source commit is an ancestor of the signing revision. Any mismatch refuses before the artifact is downloaded or a secret is read. It then downloads that artifact (pinned `actions/download-artifact`), installs the Developer ID identity exactly as `dev-mac-sign` does (same three secrets, same temporary keychain, removed afterwards), runs `right-release sign-dev-artifact` with the sign manifest and payload metadata, and uploads `signed-<artifact>-<sha>` with the signed zip, `sign-evidence.json` and `source-verification.json`. It never builds, never passes `--release` and never notarizes. The lane is not in `KNOWN_LANES` (the node profile has no template for it); unset, every other rendered workflow is byte-identical to 0.2.48, so no render baseline hash changed. Needs `@rightkit/release` 0.2.172 or later in the app. Note: `@rightkit/release`'s `right-git-ci-only` policy does not yet list `sign-existing` among its lanes, so a repository that enables the lane fails its release check until that policy accepts it.

## 0.2.40

- `profile: rust-hybrid` ci: the "Detect Rust-affecting changes" step no longer diffs a push against the previous push (`github.event.before`). A failed run followed by a commit with no Rust changes produced a green run that never ran the Rust checks for the earlier commits. Each matrix job now records the commit it last passed on (a small `actions/cache` entry written as the job's final steps) and a push or manual run is diffed against that commit. No marker, an evicted marker, or a marker that is not an ancestor of the pushed commit means `changed=true`. Pull requests still diff against the PR base. The first run after `right-git sync` has no marker and runs the full Rust checks once.

## 0.2.39

## 0.2.36

The managed `regenerate.yml` runs on `workflow_dispatch` only: checks out the default branch, runs the package script, runs the ownership scan and (rust-hybrid) the ci gate or (node) the test script on the regenerated tree, then pushes it to `right-git/regenerate-<run_id>-<attempt>` and opens a pull request with the workflow token. - `devArtifact.mac` accepts `"unsigned"`: the ci job zips `macAppPath` and uploads it as `dev-mac-unsigned-<sha>` with `retentionDays`, no signing job, no environment, no secrets. `macEntitlements` still requires `"sign"`.
- Opt-in `devArtifact.dispatch: true` adds `workflow_dispatch:` to ci.yml and lets the unsigned legs (`windows: "unsigned"`, `mac: "unsigned"`) also run on a manual dispatch of any ref. The `dev-mac-sign` job and its package step stay push-to-default-branch only, so no secret is reachable from a dispatched run. Unset renders byte-identical output.

## 0.2.33

- `ciIncremental: true` no longer sets `RUSTC_WRAPPER=sccache` (sccache refuses `CARGO_INCREMENTAL=1`); incremental builds rely on the rust-cache target directory. Unset output is unchanged.

## 0.2.32

- Add opt-in `ciIncremental` (boolean, rust-hybrid only): `Swatinem/rust-cache` with `cache-workspace-crates: true`, `CARGO_INCREMENTAL=1` on the ci gate, and an `actions/cache` step for Xcode DerivedData on macOS legs. Unset renders byte-identical output.
- Add opt-in `devArtifact` (rust-hybrid only): `mac: "sign" | "none"`, `windows: "unsigned" | "none"`, `retentionDays`, plus required `macAppPath` / `windowsGlob` (optional `macEntitlements`). On push to the default branch only, the ci job uploads unsigned Windows files as `dev-windows-<sha>`; macOS legs hand the unsigned app to a separate `dev-mac-sign` job (release environment, protection rules apply) that Developer ID-signs with hardened runtime, no notarization, no admission or ownership gate, and uploads `dev-mac-<sha>`. The release-candidate lane is unchanged.
