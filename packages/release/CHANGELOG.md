# Changelog

## 0.2.153

- Runtime budget gate is fail-closed and machine-checked. Every crate reaching `publish cargo` must carry `runtime-budget.json` or `[package.metadata.rightkit] continuous = false` + `continuous_reason` (an undeclared crate, or a manifest name that differs from `--crate`, is refused); a `continuous = false` crate whose non-test `src` matches a continuous-work pattern (`thread-spawn`, `task-spawn`, `sleep`, `timer`, `listener`, `watcher`) must name it in the reason. A continuous crate needs declared ceilings and `requiredScale`, a status pointer to a `pub` item, and per-host measurements backed by committed raw bench output written by `runtime-budgets.mjs record` (sha256 and `RESULT budget` line re-checked; zero resident memory refused); measurements go stale on any change to the crate, its workspace path dependencies (src, Cargo.toml, build.rs), new untracked files there, or its `Cargo.lock` closure, and the measured commit must be an ancestor of HEAD in the checkout. Darwin-only must agree with the release evidence host policy. The README section is generated (`runtime-budgets.mjs sync`) and compared. `runtimeBudgetAdoptionCheck` needs an installed-app measurement. New module `crate-graph.mjs` (manifest parsing, path-dependency and lock closure). All 11 listed crates ship unmeasured files and are refused until measured; 9 pure-library crates declare `continuous = false`.
- Runtime budget classes: `continuous = "held-resource"` with a `[[package.metadata.rightkit.resources]]` table (api resolving to a `pub` item, file, holds, scale, release) publishes without a measured budget when no long-lived pattern sits outside the listed files; the proof moves to app adoption (`appRuntimeBudgetAdoptionCheck` in `collectPreflight`: an installed measurement of the app per locked held-resource crate, recorded in `runtime-budget-adoption.json`, against `runtime-budget-classes.json` generated by `runtime-budgets.mjs classes`). New scanner patterns: runtime-builder, audio-stream, onnx-session, ggml, event-loop, conn-pool, resident-static, detached-child; a pattern id counts as named in a reason only as a whole token.
- Publication gate: the publishing version must be known (a missing version used to skip the comparison); every host run must carry `commit`, `host.arch`, non-empty `features` and an `artifactSha256` equal to the evidence hash, and every run on a host must qualify (a failing run is not masked by a passing run beside it); each failure names its field; a receipt commit that differs from HEAD is still refused, and the message says whether it is an ancestor and whether the unit path changed since. `publish cargo` parses the crate manifest (TOML, `version.workspace = true` supported) instead of matching the version with a regex.
- Per-file macOS signing matrix. `sign.prePackageFiles[]` entries may be `{ file, entitlements?, hardenedRuntime?, options? }` as well as plain strings, and a new `sign.nestedCode` map (`"Contents/..."` path inside the single `.app` entry -> `{ entitlements?, hardenedRuntime?, options? }`) gives chosen nested code its own settings. Signing stays inside-out (nested code deepest first, then the entries), each item signed once with its own settings. Validated by `right-release doctor`, `--dry-run` and every build before anything is signed: unknown keys, malformed or escaping paths, unsupported `--options` names, `hardenedRuntime: false` (a notarized target cannot ship it) and entitlement files that are missing, outside the config directory or not plists. `sign-macos.mjs` gains `--manifest <json>` for steps with per-file settings; its receipt records each item's entitlements digest and `--options` value and `release.mjs` rejects a receipt that disagrees with the plan. Steps with only defaults keep the previous positional invocation, so existing configs sign byte-for-byte as before. New modules: `mac-signing-matrix.mjs`, `mac-sign-core.mjs`.
- `dmg build --spec <appdmg.json>` and `targets.mac.dmg.spec`: an appdmg-style spec (`title`, `icon`, `background`, `icon-size`, `window.size`/`window.position`, `contents` for the `.app` and the `/Applications` link) is rendered by the existing hdiutil pipeline (`dmg-spec.mjs`). Explicit flags win over the spec. Fields the pipeline cannot render fail with `DMG_SPEC_UNSUPPORTED`. New `--window-position x,y` flag; the Finder window origin is no longer fixed at 100,100.
- README documents both, with the Pulse matrix and `appdmg.json` as worked examples.
- Hosted-workflow policy (`right-git-ci-only`) accepts the secrets declared in `.rightgit.json` `swift.privatePackages` (`@rightkit/git` 0.2.39 and 0.2.41), and only those, on the rendered `RIGHT_GIT_PRIVATE_TOKEN_<n>: ${{ secrets.<secret> }}` env lines (entry `<n>` names that secret) of the "Configure private Swift package access" and "Remove private Swift package access" steps, in exactly these workflow/job pairs: `ci.yml` jobs `ci`, `dev-artifact-mac` (profile rust-hybrid with `devArtifact.parallel` and a `devArtifact.mac` of sign, notarize or unsigned) and `test` (node profile); `qualification.yml` job `qualification`; `release-candidate.yml` job `candidate`; `regenerate.yml` job `regenerate`. The manifest must list the lane, and the env line must sit in the `env:` of a step of its own job. `release-candidate.yml` and `regenerate.yml` are dispatch lanes by design; `ci.yml` and `qualification.yml` refuse the secret when the file has any `workflow_dispatch`. Every lane refuses it when `devArtifact.dispatch: true`, when `on:` includes `pull_request_target` or `workflow_run` (block, flow-list, map or scalar form), when the manifest declares a swift secret that is also an Apple, publish-chain or package-manager secret name, and in every other job (the signing, qualification, admission, publish and dev-signing jobs, the secret-free jobs beside the allowed ones) and workflow (`package-smoke.yml`, `publish-npm.yml`, `publish-package-managers.yml`). The refusal message names each refused secret and why (`...requests release-capable permissions or secrets: secrets.<NAME>: <reason>`).

### Ownership command output (merged from the unpublished 0.2.152 entry)
- `right-release ownership` reports an advise-only scan as `ownership ADVISE: block N, advise M (reported, not refused)` and exits 0. It no longer prints FAILED or "move these" for advise-tier findings alone.
- Every refusal names its blocking check and the first 10 offending paths on stderr and in the JSON `blocked` field (an array of `{ check, message, count, paths }`). A failing scan lists its checks: `ownership-violation` (block-tier findings, with the move-these hint), `ownership-floor`, `ownership-problem`, `ownership-coverage` (coverage gaps with their reasons), or `ownership-unknown`. Coverage gaps were the source of the bare FAILED output: they already refused (the JSON `error` said so) and now say why. The dirty protected checkout refuses as `clean-checkout`, naming its paths; `--json` still refuses on a dirty tree with that cause. Exit codes are unchanged.

## 0.2.143

- `install-app` bundle swap can be truly atomic. When a `rightkit-swap` helper (rightkit-fs 0.4.0, `renamex_np(RENAME_SWAP)`) is found, the staged bundle is exchanged with the installed one in a single kernel step, so `<dest>/<App>.app` is never absent, even under SIGKILL. The old bundle then sits at the staged path and is moved to the Trash only after the new one re-verifies; on re-verify failure (or SIGINT/SIGTERM) the exchange is reversed. Helper lookup order: `RIGHTKIT_SWAP`, `<package>/bin/darwin/rightkit-swap`, then `PATH`. With no helper, or `ENOTSUP`/`EINVAL` (non-APFS volume), it falls back to the previous two-rename + journal path and emits a `swap-fallback` event. The `replaced` and `done` JSON events record `swap: "atomic"` or `swap: "two-rename"` (`"rename"` for a first install with nothing to exchange). The recovery journal records the mode (`swap`, plus the staged inode for atomic) and `--recover` handles both. The helper is not yet bundled in this package, so installs use the two-rename path unless `RIGHTKIT_SWAP` or `PATH` provides it.

## 0.2.142

- SwiftPM/macOS DMG ordering: with `notarize.appBeforePackage: true` and no `targets.mac.package`, right-release builds the DMG itself (`dmg-build.mjs`) after the `.app` is notarized and stapled, refusing to pack an app that fails `stapler validate`, then Developer ID signs the DMG (receipt `macos-dmg-signing.json`) before the existing DMG notarization. Options via `targets.mac.dmg` (`dmg: false` or a `package` step keeps a custom flow). Preflight now fails when a prePackage hook builds a DMG while `appBeforePackage` is on (heuristic: `dmg`/`hdiutil` in its command or arguments).
- `sign.prePackageFiles` no longer crashes with EISDIR on a directory. `.app` bundles are signed inside-out (nested code without entitlements, then the bundle) and the signing receipt is verified with a bundle tree digest (shared `macos-file-evidence.mjs`); other directories fail with a clear error.

## 0.2.141

- `install-app` probes `xcrun --find stapler` first. On clean macOS hosts without Xcode/CLT it no longer fails: the ticket is accepted when `spctl -a -t exec -vv` reports Notarized Developer ID (and, with `--dmg`, `spctl -a -t open --context context:primary-signature` accepts the DMG), and the `verified` event records `ticket: "spctl-only"`. With stapler present, and with `--dev`, checks are unchanged.

- `install-app` bundle replacement is crash-safe. The new bundle is `ditto`-staged on the destination volume (`.<App>.rightkit-install-<pid>.app`) and verified (codesign --verify --deep --strict, Team ID, bundle id) before anything installed is touched. A JSON journal (`.<App>.rightkit-install.json`, atomic write + fsync) records installed, backup, staged and mount paths and phase. The swap is two `rename(2)` calls (old to `.<App>.rightkit-backup-<pid>.app`, staged to `<App>.app`); the old bundle goes to the Trash only after the new one is re-verified, and a failed re-verify now rolls back to the backup. A kill between the renames can no longer leave the app absent.
- Recovery runs at the start of every `install-app` and as `install-app --recover [--dest <dir>] [--app-name X.app]`: missing app plus backup restores the backup; app plus backup rolls forward if the new bundle verifies, else back; leftover staging is removed and any stale DMG mount recorded in the journal is detached (retrying helper). Idempotent; a journal owned by a live installer is skipped.
- SIGINT/SIGTERM during install roll back an unfinished swap, detach the DMG, and exit 130/143. A ditto failure now happens during staging, so the message reads "previous app untouched".

## 0.2.140

- Ownership: Swift `//` and `/* */` comments in Package.swift no longer declare dependencies.
- `install-app --dev` installs a Developer ID-signed, NOT notarized build from `--dmg`, `--zip` (`ditto -x -k`), or `--app`. It still requires `codesign --verify --deep --strict`, a Team ID (and no team change versus the installed copy), and a bundle-id match; it skips only `spctl` and `stapler`, runs `xattr -dr com.apple.quarantine` on the newly installed bundle only, prints `DEV BUILD (not notarized)`, and adds `dev: true` to every JSON event. Quit-by-signal, Trash move, `ditto`, and `open -g -j` relaunch are unchanged. Without `--dev`, only `--dmg` is accepted.
- SwiftPM/macOS: new opt-in `targets.mac.notarize.appBeforePackage: true` notarizes and staples the `.app` (receipt `macos-app-notarization.json`) right after signing and before the package step builds the DMG, so a copied-out app passes offline `stapler validate`; the DMG is then notarized and stapled as before. `notarize.file` is unchanged (no breaking config change); new helper `notarizeAppBundle` in `macos-notarization.mjs`.
- Every `hdiutil detach` (DMG build, install-app) retries "Resource busy" 5 times with 0.5s to 4s backoff, logging each retry, and uses `-force` only as the last resort (`hdiutil-detach.mjs`).
- Clean-tree gates (`assertCleanSource`, committed-checkout ownership check) ignore right-release's own untracked files in the `.right-release/locks/` directory (every platform), so repos that do not ignore `.right-release/` no longer fail preflight. Nothing else in the vault is exempt.
- `install-app --dmg`: when the app has no stapled ticket (standard Tauri flow staples only the DMG), accept it if `stapler validate` passes on the DMG, `spctl -a -t open --context context:primary-signature` accepts the DMG, and `spctl -a -t exec -vv` reports the mounted app as Notarized Developer ID (may go online). codesign --deep --strict, Team ID continuity and bundle-id checks are unchanged. The JSON `verified` event records `ticket: "app-ticket" | "dmg-ticket"`.
- Docs: SwiftPM builds use `right-release build --platform mac|win`; `release --tier patch --no-upload` is rejected because build is tier-neutral (tier is chosen only at `upload`). README and the `release.mjs` usage text corrected.
