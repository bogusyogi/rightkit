# Changelog

## Unreleased

- **Retire signed ownership exceptions; exceptions are plain git-reviewed entries (Orthic-Labs/rightkit#262; version 0.2.169).** Under the proportional-trust rule, matching how trust-sync was retired in 0.2.162. Exceptions are plain entries in `.rightkit/ownership-exceptions.json`: `{ capability, package (alias: crate), reason, owner, date }`, optionally narrowed by `fingerprint` and `path`. The scanner (`evaluate` in `ownership.mjs`) marks every finding matching an entry `excepted` with no signature, trust, enrolled key, expiry or tracking reference involved; an entry that matches no finding is reported as a stale **warning** (`exception #N (...): stale, matches no current finding`); a missing field or a legacy signed record is a problem. `right-release ownership-approval` (draft, sign, verify, import; Touch ID and native-helper paths) is now a no-op that prints that it is retired and that the exceptions file is edited directly. `verifyException` and `signPayloadForNative` are removed from `ownership-approval.mjs` (key-log, trust-registry, floor and provenance code is unchanged). The ownership report's `exceptionRequests` now lists stale entries. Evidence results carry the stale warnings. The agent write hook (`@rightkit/build-control-policy` `ownership-write-hook.mjs`) no longer blocks edits to the exceptions file; the protected trust file stays blocked. Tests of the signed flow were rewritten for plain entries, stale warnings and the retired command (not run here). `docs/OWNERSHIP-ENFORCEMENT.md` documents the format; the Rust mirror in `crates/rightkit-ownership` still carries the signed evaluation and is a follow-up.

- **Bundle the rightkit-ffmpeg decode sidecar (Orthic-Labs/rightkit#246; version 0.2.168).** Optional `targets.mac.mediaSidecar` / `targets.win.mediaSidecar` (`media-sidecar.mjs`, `media-sidecar-catalog.mjs`) for apps that ship the verified LGPL `ffmpeg` and `ffprobe` as a Tauri `externalBin` (Ember). Config: `{ arch?, variant? = "decode", tools? = ["ffmpeg","ffprobe"], stageDir? = "src-tauri/binaries", bundleDir? (mac: "Contents/MacOS" | "Contents/Resources"), notices: { dir, sourceOfferContact }, stage?: { cmd, args? }, catalog? }`; `notices` is required, so the LGPL text and source offer cannot be forgotten. The plan takes one approved catalog row per tool from the `rightkit-ffmpeg` crate the app compiled against (cargo metadata, offline; or `catalog`); a missing, pending, stale, digest-less or ambiguous row refuses the release. Before the app is built the row's notice files and a generated `FFMPEG-SOURCE-OFFER.txt` (licence, FFmpeg source URL and archive SHA-256, recipes, component notices, contact) are written to `notices.dir` and the optional `stage` command runs (the app's `rightkit_ffmpeg::stage_external_bin` call, which owns the content-digest check). macOS: the two executables are added to `sign.nestedCode` (hardened runtime, inside-out with the bundle, notarized with the app), the nested signing receipt must show each `strict-valid` with the bytes now on disk, and the built app must contain the source offer. Windows: the staged `.exe` files are signed by `sign-windows` in the raw-EXE step, before Tauri packs the installer, so they appear in the `raw-exe` receipt. A `media-sidecar.json` receipt (catalog row ids and content digests, pre-sign and signed SHA-256 and size, notice digests, signing mode) is written to the state root; `build-release.mjs` refuses to seal without it, checks it against the configuration (and, on Windows, against the raw-EXE receipt) and puts it in the sealed manifest as `mediaSidecars`; `verifyPublicationRelease` re-validates it. `media-sidecar.mjs` and `media-sidecar-catalog.mjs` are part of the pipeline fingerprint. Linux: the planner and triple table accept `linux` and will work as soon as the crate catalog has approved Linux rows, but the catalog has none yet (they need a Linux build) and right-release has no Linux release target, so Linux is not shippable from this change. Tests (fakes only): `media-sidecar.test.mjs`. Not built or run; see the README section "Bundled FFmpeg decode sidecar".
- **Android: native libraries, Play internal-track upload and `dev --platform android` (Orthic-Labs/rightkit#214; version 0.2.168).** Completes the Android lane begun in #158 (the signed AAB build, signer pin and seal already existed).
  - Native build (`android-ndk.mjs`): optional `targets.android.ndk` runs one `cargo ndk` before Gradle: `-t <abi>` per ABI (release default `arm64-v8a`; `x86_64` is the emulator ABI and is opt-in for a release), `-o <jniLibs>`, `build --release`, plus fixed `--manifest-path`, `-p`, `--features`, `--platform` positions. There are no free-form arguments, so a release cannot be pointed at a debug profile. `jniLibs` must be a relative path inside the app named `jniLibs`; it is a generated directory and is emptied before every real build so a stale `.so` or an ABI no longer configured never ships (a dry run only plans). The sealed AAB scan still covers every `.so` that ends up in the bundle. `android-ndk.mjs` is part of the Android pipeline fingerprint.
  - Upload (`android-play-upload.mjs`): `right-release upload --platform android --release <sealed-id> [--config ...] [--apply]` publishes the sealed AAB to the Google Play internal track through the Play Developer API (`edits.insert`, `edits.bundles.upload`, `edits.tracks.update`, `edits.commit`; a failed edit is deleted). It is build-free: the only input is the sealed release, verified by `verifyPublicationRelease` (primary checkout, clean tree, sealed commit equals HEAD, ownership evidence, sealed `android-aab-upload-key-v1` receipt) and then re-scanned from the sealed bytes: a debug-signed, unsigned, unpinned or QA-marked bundle is refused (`PLAY_AAB_DEBUG_SIGNED`, `PLAY_AAB_UNSIGNED`, `PLAY_AAB_SIGNER_MISMATCH`, `PLAY_AAB_REFUSED`). **Dry run is the default**: without `--apply` it verifies everything local, prints the exact API plan, reads no secret and makes no network call. No tier: the internal track has no patch/update feed. Config: `distribution: { provider: "google-play", packageName, track: "internal", releaseStatus?: "completed" | "draft", releaseName?, serviceAccount: { credential } | { file } }`; any other track, a `dev`/`qa`/`test`/`debug` package, an unknown key or an inline service account is refused. A marker `.right-release/state/<id>/android/verified-play-internal.json` (versionCode, edit id, AAB sha256) stops a second upload of the same sealed release.
  - Secrets: the service-account JSON uses the same stores as the signing passwords (macOS Keychain `rightkit-android-<name>`, a protected token file elsewhere, or a 0600 file outside the repository; store with the same command `androidSecretStoreCommand` prints). It is parsed in memory, its `token_uri` must be Google's token endpoint, and the RS256 assertion and the access token exist only in memory: never on argv, never in a file, never in a log or error (Google's error text is bearer/JWT-redacted and truncated). Key material in the environment (`-----BEGIN ... PRIVATE KEY-----`, `"private_key":`, `PLAY_*`/`GOOGLE_PLAY_*` key, token or service-account names) refuses the command by name.
  - Dev (`android-dev.mjs`): `right-release dev --platform android [--serial <adb serial>] [--build-only] [--dry-run]` with `development.targets.android = { ndk?, build: [...], install: { kind: "adb", apk, package, activity?, serial? } }`. The native step uses Cargo's built-in `dev` profile (ABIs default to `arm64-v8a` and `x86_64`), the build commands must be debug tasks (`bundle/assemble/install...Release`, publish and upload tasks and signing properties are refused), and the install is `adb -s <serial> install -r -d <apk>` then `pm path` verification and an optional `am start`. The device is chosen by serial only (config, `--serial` or `RIGHTKIT_ANDROID_SERIAL`; "the only attached device" is never assumed and a missing serial is refused before the build), and the package's last segment must be `dev`, `qa`, `test` or `debug`. The dev environment drops `RIGHTKIT_ANDROID_SIGNING_PROPERTIES`. `adb` comes from `RIGHTKIT_ADB`, `ANDROID_HOME`/`ANDROID_SDK_ROOT` platform-tools, or the PATH.
  - Tests (fakes only; no emulator, keystore, network or Play account): `android-ndk.test.mjs`, `android-play-upload.test.mjs`, `android-dev.test.mjs` (node:test, like the package's other suites).
- **Source QA receipt carried to the signing job (Orthic-Labs/rightkit#183).** `right-release build` in the signing job (a different runner from the one that ran `right-release qa --stage source`) now reads the carried receipt instead of recording `qa.status: missing`. Set `RIGHT_RELEASE_QA_RECEIPT` to the receipt file or to a directory holding `source.receipt.json`; when it resolves to an existing file it is used in place of the local `.right-release/qa/<release>/<platform>/source.receipt.json`, and when it does not the local path is read as before. The carried receipt is verified exactly like a local one (MAC, QA floor, policy bundle, commit, tree, repository identity, lockfile closure, release-config hash, required checks) and must also name this build's release id and platform; a match records `qa.status: passed` with the receipt digest, any mismatch records `rejected` with the reason. The signing job needs the same MAC key (`RIGHTKIT_QA_RECEIPT_KEY` as a per-run secret on hosted CI). New `right-release qa --stage source ... --carry-to <dir>` also writes the sealed receipt to `<dir>/source.receipt.json` so it travels in the candidate handoff artifact. The rust-hybrid release-candidate signing jobs set `RIGHT_RELEASE_QA_RECEIPT` to `<downloaded candidate>/qa` (@rightkit/ci 0.2.46). The app's candidate build or QA step must place the receipt at `<RIGHT_GIT_ARTIFACT_ROOT>/qa/source.receipt.json`. Tests: `release-qa-carried.test.mjs`.
- **Installed QA stage opens the sealed artifacts (Orthic-Labs/rightkit#184).** With `qa.installed: { installDir? }` in the release config, `right-release qa --stage installed` prepares the sealed installer before running the QA runner (new `release-qa-installed.mjs`). macOS: mounts the one sealed DMG read-only, not browsable, at a throwaway mount root under the OS temp directory and exposes the `.app` inside the mount; nothing is copied to `/Applications`. Windows: runs the one sealed NSIS setup `.exe` silently (`/S /D=<dir>`, /D last) into a throwaway directory under the OS temp directory, and cleanup runs the installed uninstaller (`/S _?=<dir>`) and removes the directory. Because an installer registers the app for the current user, the Windows path is refused unless on GitHub-hosted CI or `RIGHT_RELEASE_QA_ALLOW_INSTALL=1` (a VM or throwaway host); an `installDir` outside the temp root needs that opt-in even on CI. The runner gets `RIGHT_RELEASE_QA_INSTALLED_APP`, `RIGHT_RELEASE_QA_INSTALLED_DIR`, `RIGHT_RELEASE_QA_INSTALLED_KIND`, `RIGHT_RELEASE_QA_INSTALLED_ARTIFACT` and a throwaway data root `RIGHT_RELEASE_QA_ROOT`, and the `qa.args.installed` placeholders `{installedApp}`, `{installedDir}`, `{qaRoot}`. Cleanup (detach with retry, uninstall, remove) runs even when the runner throws. Without `qa.installed` the stage behaves as before. Tests: `release-qa-installed.test.mjs` (fake `hdiutil` and installer; no real mount or install).
- Orthic-Labs/rightkit#139 (`right-release dev` hardcodes `release-iterate`) is already fixed in 0.2.167 (`DEVELOPMENT_PROFILE = "dev"`); no change here. It needs 0.2.167 published.
- `right-release dev` macOS install: explicit CI-only ad hoc signing for unsigned candidate/qualification lanes (Orthic-Labs/rightkit#168; the lane passed on 0.2.124 and broke when development signing began requiring a Keychain identity). Opt in with `development.targets.mac.install.signing: "ci-adhoc"` or `RIGHTKIT_DEV_SIGNING=ci-adhoc`. It is refused unless `GITHUB_ACTIONS=true`, `CI=true` and `RUNNER_ENVIRONMENT=github-hosted`, and is never inferred from a missing identity; any other value is `DEV_MAC_SIGNING_MODE_INVALID`. The bundle is signed ad hoc inside-out (`--sign -`, only the `com.apple.security.cs.*` and audio-input entitlements, no provisioning profile, which an ad hoc signature cannot carry), verified `--strict --deep` and `Signature=adhoc`; the TeamIdentifier and identity-based designated-requirement checks are skipped because an ephemeral runner has no TCC state to keep stable. The signing result and install log carry `adhoc: true`, `mode: "ci-adhoc"`, `releaseArtifact: false` and a `receipt`, so it cannot be mistaken for a release artifact. Default behaviour (Keychain Developer ID identity required, ad hoc refused) is unchanged. The rust-hybrid RC template's `candidate` job and the `dev-qualification` job set `RIGHTKIT_DEV_SIGNING: "ci-adhoc"` (@rightkit/ci).
- **right-release Android lane (#158).** `right-release build --platform android` builds a signed AAB through the configured Gradle `bundle<Variant>Release` command (`targets.android.gradle`). The upload keystore path and alias come from config; passwords come from the OS credential store or a 0600 file outside the repo, reach Gradle only as the path of a transient 0600 properties file (`RIGHTKIT_ANDROID_SIGNING_PROPERTIES`), and are refused if found in the environment. The AAB is read in-process: every native library goes through the QA control/devtools/remote-debugging/wdio/dev-inspect rules, web assets through the browser-QA mock scan, and the bundle must be signed by exactly the pinned upload certificate (`signing.expectedCertSha256`; the debug certificate is refused). `build-release.mjs` now seals it: `--platform android` re-hashes the AAB against `android-aab.json` (`verifyAndroidReceipt`), requires the receipt signer to be the pinned upload certificate, seals the file with `androidSealEntry` (role `aab`) and the receipt under `signing.receipts`, and records `uploadCertSha256` in the signing identity. Publication (publication-artifacts.mjs `verifyPublicationRelease`) accepts the sealed `android-aab.json` receipt only when its contract is exactly `android-aab-upload-key-v1`, its signer equals the sealed `uploadCertSha256` (never the debug certificate), and its AAB sha256, size and name equal the single sealed `aab` entry.
- New `right-release apple-profile-create` (`apple-profile-create.mjs`, Orthic-Labs/rightkit#140): idempotently ensures a macOS bundle id, the ICLOUD capability with CloudKit, the team's Mac devices and an Apple Development certificate (reuses one with a local private key, or generates an RSA key + CSR locally and stores the key in the login Keychain or `--key-out`), then issues a `MAC_APP_DEVELOPMENT` profile and writes it to `--out` with mode 0600. Dry-run is the default; a real run needs `--apply` and macOS. The ASC API cannot create or assign iCloud containers, so the issued profile is decoded and must carry every `--icloud-container`, otherwise the new profile is deleted and the manual developer.apple.com steps are printed. Inline PEM in config or environment is refused on every host.
- Ownership write hook (`ownership-write-hook.mjs` in build-control-policy; the release package carries no copy of the parser): the dependency-command parser for `pnpm`, `npm`, `yarn` and the Rust package tool now stops at shell operators and redirections (`|`, `||`, `&&`, `;`, `&`, `>`, `>>`, `<`, `2>&1`, `N>file`, `&>`, `$(...)`, backticks, subshell parentheses) and drops a redirection target, so `pnpm install --frozen-lockfile 2>&1 | tail -2` is no longer refused as dependencies `2>&1`, `|`, `tail`. A real add after an operator is still screened (Orthic-Labs/rightkit#136).
- Ownership fingerprint `tauri.rs.standard-command-fn` (rightkit-device) no longer flags a thin app wrapper that delegates to a static `*SERVICE` (`DEVICE_SERVICE.get_or_create()`, `.get/.set/.delete`), which is the pattern rightkit-device's README tells apps to keep (Orthic-Labs/rightkit#116, MailRight `commands/license.rs:249`). An own copy (keyring, uuid) is still flagged. Negative sample added.
- Hosted-workflow policy (`right-git-ci-only`): the admitted signing gate accepts `needs: [admission, candidate, dev-qualification]` as well as `[admission, candidate]` (Orthic-Labs/rightkit#107, @rightkit/ci 0.2.46 `candidate.devQualification`). The extra need only adds a gate: in-app journeys run on the dev build, and the signed candidate stays QA-free.
- Runtime-budget scanner skips `use`, `pub use` and `pub(crate) use` declarations (including multi-line `{ ... }` lists) when matching `CONTINUOUS_PATTERNS`: an import cannot start work. A crate whose `lib.rs` only re-exports `ServerOptions` or `ConnectionPool` no longer matches `listener` or `conn-pool` there; real code is still scanned.
- QA adoption is now a release gate (`assertQaAdoption` in `qa-contract.mjs`, called from `release.mjs`): an app with no QA lane (`right-qa.config.mjs`, `@rightkit/qa`, or `rightkit-qa`) is refused; a lagging `@rightkit/qa`, `@rightkit/qa-chrome` or `rightkit-qa` pin warns and a breaking-bump lag refuses. Only non-app repositories are exempt, via `qa-adoption-exemptions.json`. See the README section "QA adoption (mandatory)".

## 0.2.167

- `right-release dev` compiles with Cargo's built-in `dev` profile; `release-iterate` is retired (Adrian, 2026-10-16, after an Astra review). `DEVELOPMENT_PROFILE` is now `dev`, the dry-run plan and `RIGHTKIT_CARGO_PROFILE` carry `dev` (nothing in RightKit or RustRight reads that variable; it is informational), and the Tauri bundle lookup goes through the new `cargoProfileDirectory()`: Cargo writes `dev` and `test` to `target/<triple>/debug`, never `.../dev`, and `bench` to `release`. Dev signing, features and installer steps are unchanged. Tauri's dev mode follows the `custom-protocol` feature, not the profile, so the app's own `tauri build` command keeps embedding assets. Apps still pass `--profile release-iterate` in their own `right-release.config.mjs` and must drop it (or pass `--profile dev`) when they adopt the template.
- New `templates/cargo-profiles.toml` (shipped: `templates` is now in `files`): the standard `[profile.dev]`, `[profile.dev.package."*"]` and `panic = "unwind"` for dev and release. `cargo-profile-contract.mjs` reads it, and `right-release` refuses a release when an app's workspace-root `Cargo.toml` deviates: a missing, changed or extra key in those tables, an extra `[profile.dev.*]` table, `panic` other than `unwind` in dev or release, `[profile.test]` overrides, or a `release-iterate` profile (or a profile inheriting it). Every manifest with a top-level `[workspace]` table is a profile root, and so is every standalone package manifest outside any workspace, because an app can ship binaries from several workspaces (Pulse ships `hub/src-tauri`, `engine` and `membrane/engine`). Only declared non-shipping workspaces are exempt: the fixed `qa/` and `benchmarks/` prefixes, plus an optional `cargoProfileExempt: ["relative/dir", ...]` array in the app's `right-release.config.mjs` (string literals inside the app only; anything else is an `invalid-exempt` finding). Findings list `file:line [rule] message` per app.
- The same scan flags the two source patterns a debug-assertions dev profile makes wrong: `cfg_attr(not(debug_assertions), windows_subsystem = ...)` (set `windows_subsystem = "windows"` unconditionally, or an installed dev app opens a console on Windows) and an environment-variable read within 12 lines after a `cfg(debug_assertions)` attribute or `cfg!` (move it to the app's test-mode feature; a reviewed site takes a `rightkit-allow: debug-assertions-env` comment). The env check is a heuristic. Directories named `tests`, `examples`, `benches` and `reference` are skipped.
- Coverage: `cargo-profile-contract.test.mjs` (conforming workspace, legacy `release-iterate` plus abort app, extra keys and tables, nested workspaces, invalid TOML, both source patterns); `development.test.mjs` follows `dev` and `target/<triple>/debug`; `release.test.mjs` fixtures carry the template tables.

## 0.2.166

- Test hermeticity: the package test suite no longer reaches the live RightKit build broker. A new test-only guard, `test-support/broker-guard.mjs` (not shipped: outside `package.json` `files`), loads through `pnpm test` (`node --import`), at the top of `release.test.mjs` and `right-suite-contract.test.mjs`, and in child Node processes through `NODE_OPTIONS`. It hooks the one launch boundary every release subprocess crosses and the broker socket connect. Temp-directory fixture clients still run, since the suite builds them as POSIX shell stubs. Real end-to-end runs need `RIGHTKIT_TEST_REAL_BROKER=1` set on purpose. `broker-guard.test.mjs` covers the classifier, the refusal, the stub, the NODE_OPTIONS propagation and the fixture passthrough.
- The temp fixtures that leaked into the broker (`right-release-test-*`, `rightkit-cargo-contract-*`, `rightkit-cargo-scan-*`) now run their Cargo metadata through the stub, so no per-test workspace is submitted to the broker. No assertion was removed.

## 0.2.163

- Disk schedule binds to a stable per-user root. `disk schedule install` copies the installed `@rightkit/release` package and its runtime dependencies (symlinks dereferenced, so pnpm layouts copy cleanly) into `%LOCALAPPDATA%\Orthic Labs\rightkit-release\current` (Windows) or `~/Library/Application Support/Orthic Labs/rightkit-release/current` (Mac), smoke-tests the staged copy (`--version`), swaps it in by rename (the previous `current` is restored if the swap fails; a staged copy that does not run never replaces a working one), and binds the launchd job or Task Scheduler entry to `current/node_modules/@rightkit/release/cli/right-release.mjs`, never to a pnpm store, pnpm global hash directory or checkout. The source is `--cli`/`RIGHT_RELEASE_INSTALLED_CLI`, else the running package when it is not a checkout, else the discovered installed package. `disk schedule status` reads the registered target and reports a missing or non-stable target (`PROBLEM: ... MISSING`, exit 1) instead of crashing. `disk run` opens with a self-check (own package and dependencies intact, registered schedule bound to the stable root): a failure is printed, logged as `disk.run.selfcheck.fail`, and the run still sweeps but exits 2.
- Workspace roots are an allowlist, not a blocklist. For `/Volumes/D/claude` and `D:\claude` a top-level entry is known when git tracks it in the workspace repo, it is a nested git checkout (has `.git`), or its name is in `workspaceAllowlist` (seeded from the current Mac root). `disk check` warns on every other entry with its size and age. `disk sweep` moves an unknown entry only when nothing inside it changed for 3 days (`unknownStaleDays`) and no process holds a file in it (lsof on Mac, rename probe on Windows), into the same-volume holding dir (the 3-day purge removes it later). Never touched: symlinks, nested checkouts (re-checked at apply time), tracked paths, allowlisted names, protected segments. A root that is not itself a git repository root (tracked set unprovable) is not swept and `check` says so.
- One scratch root per machine: `/Volumes/D/scratch` and `D:\scratch` (`scratchRoots`). Every child older than 3 days and idle moves to holding; the directory is created by `schedule install`, `sweep` and `run` when missing.
- Tests on temp trees cover each rule (fresh unknown, nested repo, tracked dir, allowlisted dir, recent file deep inside, open handle, stale unknown, stale scratch child), the stable-root install, the atomic reinstall, the failed-smoke case, the binding checks and the self-check.

## 0.2.162

- `ownership trust-sync` is retired (Adrian's decision, recorded in `decisions.md`): no release, ownership, admission, sealed-evidence or QA check refuses on a missing or stale pinned policy bundle. `validateOwnershipFloor` now returns `warnings`; a pinned `policyBundle` that differs from the running bundle (or a bundle that cannot be computed) is a warning (`ownership policy bundle ... differs from the bundle pinned in protected trust`), printed as `WARNING` and in the JSON `warnings` field, and never changes `ok`, `floorOk` or the exit code. Scanner and catalog minimum floors, key-log, registration and coverage checks are unchanged. The bundle is still computed and pinned-compared; `ownership trust-compare` adds the drift warning with a semantic diff (scanner version, scanner files added/removed/changed, catalog, registry, allowlist and QA floor digests) and still exits 0. `right-release ownership trust-sync [--check]` is a no-op that prints why and exits 0, before taking any lock or running anything; the desktop delegation, approval dialog and `trustSync`/`trustSyncGate` code are gone from `ownership-key-command.mjs` (the confirm/summary/presence helper modules remain, now unused). QA receipts still bind to the running bundle digest at write time, which does not involve trust. Consequence: nothing now copies a proposed dependency allowlist into protected trust, so proposals stay advisory; the write-hook and scan messages say so.
- Disk policy: new sweep target `qa-evidence-runs` (Mac `/Volumes/D/claude/*/.cache/rightkit-qa/*`, Dell `D:\claude\*\.cache\rightkit-qa\*`): QA evidence run dirs older than 3 days are moved to the per-volume holding dir like any other sweep. Writers may now carry their own `staleDays` (a `--days N` argument still overrides all of them) and `skipTracked: true`, which skips anything `git ls-files` reports under the candidate (reason `tracked`; a git failure keeps the item). No marker file is required yet: every direct child of `.cache/rightkit-qa` qualifies; add a `marker` rule once rightkit-qa 0.5.0 names one.

## 0.2.141

- `install-app` probes `xcrun --find stapler` first. On clean macOS hosts without Xcode/CLT it no longer fails: the ticket is accepted when `spctl -a -t exec -vv` reports Notarized Developer ID (and, with `--dmg`, `spctl -a -t open --context context:primary-signature` accepts the DMG), and the `verified` event records `ticket: "spctl-only"`. With stapler present, and with `--dev`, checks are unchanged.

- `install-app` bundle replacement is crash-safe. The new bundle is `ditto`-staged on the destination volume (`.<App>.rightkit-install-<pid>.app`) and verified (codesign --verify --deep --strict, Team ID, bundle id) before anything installed is touched. A JSON journal (`.<App>.rightkit-install.json`, atomic write + fsync) records installed, backup, staged and mount paths and phase. The swap is two `rename(2)` calls (old to `.<App>.rightkit-backup-<pid>.app`, staged to `<App>.app`); the old bundle goes to the Trash only after the new one is re-verified, and a failed re-verify now rolls back to the backup. A kill between the renames can no longer leave the app absent.
- Recovery runs at the start of every `install-app` and as `install-app --recover [--dest <dir>] [--app-name X.app]`: missing app plus backup restores the backup; app plus backup rolls forward if the new bundle verifies, else back; leftover staging is removed and any stale DMG mount recorded in the journal is detached (retrying helper). Idempotent; a journal owned by a live installer is skipped.
- SIGINT/SIGTERM during install roll back an unfinished swap, detach the DMG, and exit 130/143. A ditto failure now happens during staging, so the message reads "previous app untouched".
