# Changelog

## 0.6.9

- **Rule tiers (Adrian, 2026-10-26): the apps build again on the rule set they were green on.** `app-check.mjs` `TIERS`: the *compile* tier is the 13 rules 0.6.6 published (`COMPILE_TIER_IDS`); every rule added since (C3, SC, CA, LG, SF-01, OW-05, OW-06) is *release* tier until the synthesis waves make it true in every app, and is promoted in RightKit, never per app and never through a baseline. The compile tier is what compile admission owes: the RustRight broker, the pre-push hook, `rightkit-gate check`, `--to compile|package`, `right-release build|dev|test`. The release tier is every rule and scan: `rightkit-gate --to qualify` runs `check --rule-tier release` before installed QA (`receipt.stages.qualify.ruleTier`), and `right-release release|qa|upload|publish|publish-update|github|sign-*|create-mac-updater|sign-candidate` owe it (`RELEASE_TIER_COMMANDS`). `check --rule-tier compile|release` (default compile; `--tier` stays the upload tier); `--list` names each rule's tier; the summary line names the tier. The class A `shellcheck` scan and actionlint's shellcheck requirement, added after 0.6.6, are release tier too. RightKit's own preflight keeps every rule.
- **Every build tool is a door (Adrian, 2026-10-26).** The agent hook (`door-policy.mjs`) now denies `xcodebuild` (every action, and a bare call, which builds), `xcrun` wrapping them, `swift build|test|run`, `swiftc`, Gradle tasks other than the read-only reports (`gradle`, `gradlew`, `gradlew.bat`), `vite build` and the bundlers (webpack, rollup, esbuild, tsup, parcel), and a package script whose name says it builds (`pnpm build`, `npm run tauri`, `pnpm run build:mac`). Read-only forms stay allowed (`xcodebuild -list`, `swift package resolve`, `gradle tasks`, `pnpm run lint`). The denial names the door stage and platform (`--to package --platform ios|android` for a mobile build).
- **iOS and Android are door platforms.** `rightkit-gate --to check|compile|package|release --platform ios|android`: class A first, compile, then `right-release build --platform <p>` (the signed, sealed IPA or AAB; there is no source-QA lane for mobile), then `--to release` uploads the sealed build from the host to the store's test track (`right-release upload --platform <p> --release <id> --apply`: TestFlight, Play internal track) after the release tier passes; no patch|update tier, no publisher environment. There is no mobile qualify stage: it is never recorded, never faked; qualification is the store's test track. The `stage` command (publisher hand-off) stays mac|win.
- **Runner-aware dispatch.** `rk-pipeline dispatch` counts the hosted publish runs GitHub has queued, waiting or running (`publish.yml`, `publish-app.yml`) and holds with exit 3, sending nothing, while the count is at `ci/rk-pipeline.json` `dispatch.maxInFlightRuns` (2: each hosted qualification takes one macOS and one Windows runner); a count gh cannot give refuses (exit 2) rather than dispatching blind.
- **Astra review, 2026-10-26 (before publication).** Every class A failure latches before class B starts, whichever branch produced it (a missing advisory database or a failed deny metadata could be followed by a compile). A bare, `--all` or pre-push gate run runs the app rules first, in the tier asked for, and plans nothing while they are red; `check` is no longer the only entry that does. `cargo package --list` is deferred, named, on broker hosts (rustright classifies `package` as a build, so from the primary checkout it would re-enter the admission running it; rightkit#1216) and runs in the release tier on a direct host. The rustright probe fix covers the broker's `cargo` shim too. The Cargo-input guard walks every ancestor directory for `.cargo/` and `rust-toolchain` and fails closed when git cannot list the inputs. `qa --stage source` (inside the package stage) owes the compile tier; `qa --stage installed` the release tier. `--to qualify --platform ios|android` is refused with the reason (exit 2) instead of exiting 0 having done nothing. The agent hook judges `bash -lc` and other combined short flags, `xcrun --sdk … <tool>`, `swift --package-path … build`, every Gradle task on the line, `vite --config … build`, and the `test`, `e2e` and `qa` scripts. `rk-pipeline dispatch` validates `maxInFlightRuns`, counts an ambiguous dispatch as in flight, and refuses a malformed count. `publish-app.yml` installs with `--ignore-pnpmfile` as well as `--ignore-scripts`, so no repository code runs before class A.
- **Nested apps go through the door.** A door run started from a directory that holds a release config (apps/coderight-tauri, apps/coderight-ios, apps/cutright, tauri-app-next) is for that app: every right-release stage runs there, the sealed set is read from there, and the receipt is keyed `<commit>--<dir>` (`receiptKey`), so two apps of one repository never share a receipt. The publisher hand-off (`stage`) reads the same.
- **The rustright probe runs where its scan runs.** Tool version probes run outside the repository, but the RustRight client refuses any directory that is not a Cargo workspace inside a repository (`RK_NOT_PRIMARY_CHECKOUT`), so on every broker host each cargo scan read as `TOOL_MISSING` (rightkit#1215, third cause). The `rustright cargo --version` probe now runs in the scanned tree; every other probe stays outside.
- The gate refuses a broker-managed host whose broker is unreachable only when the snapshot carries a Cargo manifest: a JS-only app, or a git hook's minimal PATH, owes the broker nothing and the class A scans never compile. A push of ref deletions alone runs no app rules and plans nothing, as the hook already skipped the check for it.
- The crate package-list scan (`cargo-package-list:<crate>`, what a published crate would carry) is release tier: it is not planned at compile admission. On a broker host the release tier defers it, named, never passed, until both brokers classify a locked `package --list` as an observation (rightkit#1216); a direct host (CI) runs it. Before this, the deferral landed in the gate's failures and blocked every push of an app with a publishable crate on a broker host (Astra, second pass).
- A push of ref deletions alone returns before the app rules and before any plan: it carries no content. A mixed push (a deletion and an update) is a push of content.
- Nested apps, second Astra pass: sidecar configs are handed to right-release as absolute paths (it runs in the app root); the staging draft is `rightkit-staging-<commit>--<app key>` per app and the publisher unpacks the sealed set under the app root; the receipt and staging key encodes `_` as `_u` before `/` as `__`, so apps/a__b and apps/a/b never share one; a cwd below an app (apps/foo/src) belongs to that app.
- `--plan` takes no `--to` stage (it planned and then compiled). A broker-managed host whose broker is unreachable runs no class B scan even with no Cargo manifest in the snapshot: npm tests and scripts can compile native code. `right-release web-build`'s direct entry runs only under a door run (a dry run plans and runs nothing).
- Third Astra pass: `right-release web-build` checks the door before it imports the config (a `.mjs` config is code), dry run included, and the exported runner checks it again, so no in-process caller spawns a step around it; `--to dev|test` run right-release in the resolved app root (a cwd below apps/foo is apps/foo); a malformed pre-push line blocks the push before the deletion-only shortcut. The installed-copy test asks `right-release check` for the release tier it compares against.

## 0.6.8

- **The snapshot export carries the checkout's origin.** `rightkit-gate` exports the gated commit without `.git`, and rustright binds the tracked `.rightkit-local-build.json` grant to the origin URL in `.git/config`, so `cargo metadata` in the export was refused on every broker host and no push passed the pre-push hook since 2026-10-22 (rightkit#1215). The export now holds a config-only `.git` naming the source checkout's `remote.origin.url`; it is not a repository to git, and a checkout without a remote exports none. The export also moves off the system volume: the broker refuses a workspace there (`RK_INTERNAL_DRIVE_REFUSED`), so on a host with a disk-policy scratch root (`/Volumes/D/scratch`, `D:\scratch`) the export is created under it; `RK_GATE_TMPDIR` still overrides, and `os.tmpdir()` stays the fallback where no scratch root exists.
- `door.mjs` (public): `requireDoor(command)` / `doorRefusal()` let an app's own config-declared build step (a payload assembler, an installer packager) refuse unless a live `rightkit-gate --to` run for HEAD launched it, the same door check `right-release` makes for itself. Apps restore their assembly steps behind it instead of keeping side doors around class A.

## 0.6.7

- **Docs: the gate's executor, stated as implemented.** The `bin/rightkit-gate.mjs` header and the README said a host without RustRight refuses the Rust gate or defers it to host qualification; `gate-executor.mjs` has run direct cargo through the same gates on such a host (a cloud session, a CI runner) since the one-door change, and the deferral code is gone. Both now say so: the broker where the machine has it, a refusal only on a broker-managed machine whose broker is unreachable, direct cargo elsewhere.
- **`source-closure` (SF-01): a sealed qualification record whose sources changed fails before the build.** New module `source-closure-rules.mjs`. Any committed `*.json` record `{ sourceClosure: { sources: { path: sha256 }, digest } }` fails when a listed source is missing or its bytes no longer hash to the recorded digest, or when `digest` is not sha256 over the canonical JSON of `sources`. A digest over a projection is declared in `.rightkit/source-closures.json` only by naming a RightKit-approved transform identity (`APPROVED_TRANSFORMS`: the two Legion provider-registry projections, cited to Legion's producers, and the lossless `text-lf/v1`); each binds its source path, families, dropped keys and an input schema that refuses unknown fields, and is applied to the current bytes and compared. A repository never supplies pointers or a reason-only exemption. Closure membership a producer would now add is not judged (it is computed by repository code). Legion's `qualification/provider-accuracy/index.json` failed so only after a full Windows build (runs 40149636641, 40158717069).
- **`mandatory-foundation` (OW-05) no longer passes an app that omits `rightkit-mandatory.json`, or that excuses a row without a ratified ruling.** A root `right-release.config.(mjs|json)`, or one beside `src-tauri/tauri.conf.json`, makes the repository an app; without its declaration it fails (`mandatory-foundation|rightkit-mandatory.json|declaration`). A nested app with its own declaration is checked from its directory. A `notApplicable` row is excused only by `appAmendments.<app>.notApplicable.<row>` for the `app` the declaration names and its profile, reason verbatim (rightkit#1140); otherwise it is a finding and the row applies. `checkApp` takes an optional `declaration`.
- **`ownership-exceptions` (OW-06) ties each ledger entry to a ratified ruling**, `appAmendments.<app>.exceptions` (capability, package or crate, path when named, RightKit issue, expiry no later than the ruling). No ruling is ratified yet, so every committed ledger entry is a finding until RightKit ratifies it. RightKit's own `desktop-app-template` M22 row (rightkit#994) is listed KNOWN in `ci/app-check-baseline.json`.
- **Audit closures (Neon, 2026-10-25).** RightKit's own rules and the exports import check run only after the app rules and every class A scan passed (a red tree executes none of its own code), and the import check refuses any commit other than the checkout's HEAD instead of proving it with HEAD's bytes; like CI it passes `--report` (into the git common dir), so build-output exports go to the sealed-byte check instead of failing every RightKit check with INCOMPLETE. The import check exports with read-tree + checkout-index, so an export-ignored package cannot leave the required set. `--only` says it is a partial view, not a class A result, and a green one exits 3 (`PARTIAL_EXIT`), never 0, so any caller admitting only exit 0 rejects it. `check --worktree` refuses the HEAD-bound import check while the working tree differs from HEAD (tracked edits or unignored untracked files). The pnpm-audit scan runs the strictest of every declared `pnpm audit <flags>` script (one scope only when all agree, the lowest level), never the first match. RightKit pins katex ^0.18.2 through a workspace override (GHSA-238p-pmpm-9mq7, published after f8dcf77; micromark-extension-math 3.1.0 still asks for ^0.16), so its own audit is green again. `--to release` only uploads: every earlier stage must stand in the receipt for the sealed bytes on disk, so the publisher never rebuilds or requalifies (found by scripts/sim/door-lifecycle.mjs). The agent hook judges shell grouping and reserved words, `$(...)`/backtick bodies, variable indirection (both readings when an assignment may not reach the command), xargs-supplied arguments and redirections (found by scripts/sim/door-policy.mjs, which executes each command with PATH shims as its oracle); scripts written and then run remain outside what a text hook can see. `check` judges the declared compile inputs a RustRight broker captured (RIGHTKIT_COMPILE_INPUTS: the ignored paths listed in the captured tree's `.rightkit/compile-inputs.json`, each JavaScript file must parse, each JSON file must parse, no file may hold a secret, no links) and prints the same per-path digest the broker records; before this the contract was only honoured by test stand-ins. Shell scripts are a class A scan (shellcheck 0.11.0, pinned in CI and the publisher; actionlint needs it). CI setup runs installs and `pnpm fetch` with pnpmfile hooks and scripts off. Regressions, each failing on the old code: commit-bound Cargo scans, probe isolation, self-check order and binding (commit and dirty worktree), export-ignored package, partial exit (in process and from the packed tarball), strictest audit policy, shellcheck's historical SellRight findings.

- **pnpm-audit keeps the consumer's own policy.** The class A audit ran `pnpm audit --prod --audit-level high`, weaker than RightSites' declared `pnpm audit --prod` (every severity). It now runs the flags of a root script that is exactly `pnpm audit <flags>` (only `--prod`, `--dev`, `--audit-level`), and with none declared, every dependency at every severity.

- **The compile stage stages sidecars first.** `rightkit-gate --to compile` runs `right-release stage-sidecar --config <file>` (under the live door run) for every committed `right-release.config.(json|mjs)` that declares `sidecars`, before any compile: a Tauri crate with `externalBin` refuses to build without them (PostRight's first run through the door failed exactly there). A failed staging compiles nothing.

- **Class A reads only the requested commit.** The snapshot is exported with `git read-tree` + `checkout-index` into a private index, not `git archive`, so files marked `export-ignore` are scanned too; and every class A scan of a commit or tree (cargo-metadata, cargo-deny, cargo-audit and the rest) runs in that export, never in the live checkout. Tool version probes run in an empty directory outside every repository with pnpm hooks and corepack auto-pinning off, so a probe never reads the repository's own configuration. `desktop-app-template` carries its advisory ledger, citing RightKit's existing approvals for the same advisories.

- **App advisory exceptions under the same policy as RightKit's.** A Cargo workspace whose `deny.toml` or `.cargo/audit.toml` ignores an advisory needs `<workspace>/.rightkit/advisory-exceptions.json` (owner, evidence, unexpired `reviewBy`, exact locked `affectedVersions`, the exact direct `dependents`, a real `path`, and `approvedBy` from a person); `deny.toml` and `audit.toml` must match it. Class A scan `advisory-exceptions:<workspace>`. `parseToml` reads hex, octal and binary integers (cargo-deny licence clarify hashes).

- **Class A, completely.** `actionlint` requires `shellcheck` (it otherwise skips every `run:` script silently and passes): a missing shellcheck fails the scan; CI lanes and `publish-app` install shellcheck 0.11.0 pinned beside cargo-deny and cargo-audit. `json-parse` reads `tsconfig*`, `jsconfig*` and `.vscode/*.json` as JSON with comments, as their own spec does; every other `.json` stays strict. For the RightKit repository, `rightkit-gate check` also runs RightKit's own rules (`scripts/preflight.mjs`: consumer recipes, npm surface, version copies, dispatcher pins, consumer locks, generated docs) when the gate is that repository's in-tree copy; a gate checking any other repository never runs its code. Receipts bind the class A tool versions (cargo-deny, cargo-audit, actionlint, shellcheck). Central baseline entries for apps that now carry their own `.rightkit/app-check-baseline.json` are removed, with mailright's stale `switches-inventory` entry.

- **One trusted publisher for every app: RightKit's `publish-app` workflow.** App repositories are private and run no Actions, so `rightkit-gate stage --tier <t>` dispatches `bogusyogi/rightkit` `publish-app.yml` (app, app_dir, commit, tier, platforms). Its one job, in the protected `app-publication` environment, is the only holder of the publication credentials: it re-runs class A on the commit, unpacks the staged archive outside the checkout (links, special files and any path outside `.right-release/sealed/<id>/<platform>/` refused), and runs `rightkit-gate --to release --receipt-in`, which takes the installed-QA result recorded for exactly those sealed bytes (the publisher cannot rerun an installer) and uploads them.
- **Side doors closed (independent review).** A flag-first `right-release --platform <p>` (a build) now needs a live door run; the agent hook judges `bash -c`/`sh -c`/`eval`/`xargs` payloads and cargo global options (`-C`, `--config`, `--color`, `-Z`), and denies `right-release cargo-target`, `dmg build`, `addon build`, flag-first `right-release` and direct calls of the build engine. `--receipt-in` is read only after the publisher check.

- **One door for every compile, dev included.** `rightkit-gate --to dev|test [-- <args>]` runs class A over the working tree, then `right-release dev|test` under a live door run; `right-release dev`, `test` and `stage-sidecar` refuse any other caller, and the agent hook denies them and `tauri dev` with that door.
- **Receipts travel between pipeline jobs and release belongs to the trusted publisher.** `--receipt-out` / `--receipt-in` carry a receipt to another runner, taken only for the same commit, tree, lockfiles and gate, with the sealed bytes unchanged; check, compile and package are not rerun for intact sealed bytes. `--to release` runs only in the publication job of the `release` workflow (`RIGHTKIT_PUBLISHER=github-environment` on GitHub Actions); `rightkit-gate stage --platform <p> [--tier <t>]` hands a qualified sealed set to it through the draft release `rightkit-staging-<commit>`.

- **Class A advisory scans are deterministic and offline.** `cargo-deny` runs `--offline --config <overlay>` and `cargo-audit` runs `--db <path> --no-fetch`, both against the RustSec commit pinned in `advisory-db.json`, materialised once per machine by `advisory-db.mjs` at `<cache>/advisory-db/<commit>` (`RK_ADVISORY_CACHE_ROOT` overrides the cache root); a machine that cannot fetch the pin and has no cache refuses (`ADVISORY_DB`). The pin commit is part of the scan command, so moving it re-runs the scans; the same commit no longer passes today and fails tomorrow, or goes red on a GitHub 503.

- **Ownership class rules: the app check enforces the mandatory foundation set and validates the ownership exception ledger (plan items 0.5 and 0.6).** Code is placed by class, never by consumer count. New module `ownership-class-rules.mjs`; its `OWNERSHIP_CLASS_RULES` are appended last to the app check, so `rightkit-gate check`, `right-release check`, the pre-push hook, the start of every checked `right-release` command and RightKit's own preflight run them (the check now runs 27 rules, preflight 37). `mandatory-foundation` (OW-05): in an app (a root `rightkit-mandatory.json`), every owner of a foundation row of `ownership-mandatory-set.json` for the app's profile must be a non-dev dependency; a missing owner, a dev-only one, or an unknown or unratified profile is a finding with identity `mandatory-foundation|rightkit-mandatory.json|<owner>`. Schema findings carry an identity, so an app can ratchet them in `.rightkit/app-check-baseline.json` (issue and a sunset of at most 90 days); an entry past its `expires` date is a finding with no identity, so no baseline silences an expiry. - **Disk hygiene runs hourly as one job, `disk run --auto`.** The scheduled job runs every hour: launchd `StartInterval` 3600 on macOS (replacing the daily `StartCalendarInterval` plist), one repetition trigger of one hour on Windows (replacing the daily trigger). `--auto` runs the full pass once a day, on the first run after 03:30 local time, and the light pass on every other run. Bare `disk run` is always the full pass. The light pass is stat-only: it reads the free space of the floors, sweeps the writers marked `light` and the scratch roots, and nothing else; it sizes no writer, walks no workspace, looks for no stray target and purges nothing, except in the emergency below. `disk schedule status` exits 1 when no full pass is recorded or the last one finished more than 26 hours ago. `--auto` finds that full pass by reading the log backwards in growing windows (4, 16, 64 MiB, then up to 256 MiB), so a busy day's sweep lines cannot hide it and make every hour a full pass; a missing log means the job never ran, and a log that exists but cannot be read keeps the run light, with the read error shown by `disk run` and `disk schedule status`. Every run event logs the agent volume's `freeBytes` with its `floorId`. The usage line lists `run [--auto|--light]`, `run-root <name> [--days N] [--release]` and `schedule install|uninstall|status`.
- **Emergency purge only when the agent volume is below its soft floor, and only after a calibration is recorded.** A floor flagged `agentVolume` that warns purges the holding folders on that volume with no undo window (`days 0`) and logs `disk.run.emergency`; holding on another volume keeps its window. A warning from any other floor or writer never purges. The purge has no undo window and the floors are proposals, so it also needs a calibration: `disk check --calibrate` appends `disk.calibrated` (every floor with its `thresholdBytes` and `freeBytes`) to the run log when no `agentVolume` floor is warning, and records nothing and exits 1 while one is (lower the floor in `disk-policy.json` or free space first, so a chronically low volume is a decision). An emergency runs only when the log holds a calibration that lists every `agentVolume` floor of the current policy with the same `thresholdBytes`; changing a threshold makes it stale. Otherwise the run is an ordinary run (normal holding window, normal sweep), logs `disk.emergency.skipped` with `reason` `uncalibrated`, `calibration-stale` or `log-unreadable` (any read error but a missing log), and prints `EMERGENCY SKIPPED`. The calibration is found by the same backwards log scan as the full-pass line, so a busy day's sweep lines cannot bury it. `disk schedule install` prints the pre-install steps and `disk schedule status` prints `calibration: recorded <age> ago` or `NOT RECORDED (emergency purge disabled)`.
- **Floors are a list per platform with an explicit holding source and agent volume.** `floors.<mac|win>` is a list of entries with `id`, `path`, `label`, `warnFreeBytes`, optional `warnFreePercent` and `hardFreeBytes`, and the flags `holdingSource` (the one floor whose volume holds cross-volume parking, the Mac internal disk; more than one is refused) and `agentVolume`. ## 0.2.143

- `install-app` bundle swap can be truly atomic. When a `rightkit-swap` helper (rightkit-fs 0.4.0, `renamex_np(RENAME_SWAP)`) is found, the staged bundle is exchanged with the installed one in a single kernel step, so `<dest>/<App>.app` is never absent, even under SIGKILL.
